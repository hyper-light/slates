# Slates product and codebase audit — 2026-09-29

## Verdict

Slates has a substantial design, unusually serious protocol tests, and meaningful implementation work across the whole product. It is not yet justified to treat the working tree as a safe, complete laptop-to-global filesystem service. The immediate blockers are permission enforcement at landing, unsafe memory lifetimes exposed through safe Rust APIs, hostile-input admission, and recovery that changes the meaning of an object. The fleet also has integration paths whose cost grows with the number of objects or members and delays consensus progress.

This audit records **32 findings** and a separate performance and scale improvement programme. A finding is not a request to layer in a fallback, add locks, add an external runtime, infer a merge, or put consensus on filesystem writes. Those would contradict the product. The fixes must strengthen the existing ownership, bounded-work, register, and grant mechanisms.

The most urgent finding is **AUD-29-01**: a grant issued for one target can authorize execution against another target. A valid issuer proof at grant creation does not fix missing binding checks at grant use. **AUD-29-08** exposes freed runtime state as a valid-looking static reference. These are product safety defects, not polish.

## 1. Product understood before code was judged

The governing contract is [SLATES_DESIGN.md](../wip/SLATES_DESIGN.md), particularly §1, R1–R10, D-7–D-9, D-14–D-17, D-26–D-27, and §§4.2–4.16. [GAPS.md](../wip/GAPS.md) and [TBD_FIXES.md](../wip/TBD_FIXES.md) distinguish current implementation from historical gates.

Slates gives coding agents normal filesystem paths backed by isolated, copy-on-write RAM state. A volume may be scratch or a lazy overlay of a host directory. The host disk remains the source of truth for untouched base entries; private edits stay in RAM. Snapshots and clones share state. Ordinary programs must observe the specified filesystem semantics through the platform bridges.

A green volume accepts work through declared operations. It returns accept, identical, or precise conflict. It does not guess a text merge. A landing is a separate operation: present the precise changes, obtain a human grant, acquire authority for the target, preserve outsider changes, write only within the granted target, and report the achieved result and durability.

The fleet retains the same semantics. Shard ownership and bounded channels serve local work; fenced registers and placed content retain objects; a regional Raft council and cross-region root group agree configuration. Consensus is for membership, placement configuration, promotion, and home changes. Putting Raft on every file write would violate D-14 and would make local and wide-area latency requirements incompatible.

The promised scale is not “a small cluster eventually.” The design's §2 scale envelope names thousands of hosts, 32–192 cores per host, 256 GiB–2 TiB RAM, billion-file bases, and millions of loaded inodes. The user's global-scale requirement makes admission, scheduling, failure domains, retained metadata, and recovery costs first-class acceptance conditions.

| Product operation | Required observable guarantee | Implementation reviewed |
|---|---|---|
| Provision | Typed refusal or isolated volume; uncontended p99 below 50 µs | machine, mem, rt, ipc, client, server admission |
| Use a normal path | Correct namespace, bytes, links, attributes, handles, barriers, permissions | vfs, base, bridge-core and OS bridges |
| Snapshot / clone | Stable chosen version, bounded retention, no mutation through shared roots | vfs snapshots, image/export, server records |
| Merge | Declared operations only; exact verdict; replay and retry preserve the result | merge, merge_service, verbs, register holders |
| Place / take over | Acknowledged state survives the promised failures with its policy intact | archive, db, cluster, fleet, head, takeover |
| Land | Exact reviewed state, intended consumer, canonical target, outsider safety, honest durability | CLI/control authorization, server landing, land engine |
| Use an SDK or MCP | Async progress, bounded input and pending work, typed errors, no grant authority | client, Python, Node, MCP |
| Deploy globally | Bounded work independent of unrelated objects; consensus remains live under bulk load and failure | transport, fleet coordinator, council/root, retention, CI |

Slates is not a sandbox, persistent storage after total RAM loss, or a general multiwriter distributed POSIX filesystem. Those exclusions do not relax the guarantees above.

The review followed complete product paths and inspected their underlying modules, refusal handling, tests, CI, and recorded measurements. ## 3. Severity and prioritized findings

**P0:** can break the human disk-write permission boundary.  
**P1:** memory unsoundness, wrong state or lost work, daemon termination, indefinite operation, or scale liveness failure.  
**P2:** important enforcement, efficiency, evidence, or product-truth weakness.

A priority is not a measured frequency. Boundary tests should be cheap even when the boundary is rare.

### AUD-29-01 — P0 — Landing execution does not enforce the grant's target, volume, or consumer

**Evidence: Source.** [server landing](../../crates/server/src/landing.rs), land_verb_unix around line 228 and issue_grant around 561; [grant table](../../crates/land/src/grant.rs), GrantRecord / Grants::check around 45 / 123; [manifest encoding](../../crates/land/src/manifest.rs), Manifest::encode around 170.

The durable grant records a volume, snapshot, target and principal. The runtime grant passed to the engine contains none of those bindings. Execution checks write rights on the requested volume, opens the requested target, and checks only the runtime grant's state, expiry and, for Once, manifest hash. The manifest hash covers relative entries and their witnesses, not target-root identity. Session grants do not even compare the manifest.

A caller with a usable grant id on that owner shard can retarget a create-only plan to another empty directory with the same manifest. A session grant can cover a different plan or writable volume on that shard. A target path replaced between presentation and execution is not bound to the reviewed directory identity either. The keyed proof authenticates grant issuance, but execution never enforces the fields it was meant to authorize.

**Required change:** carry a closed grant binding through use: stable target identity, volume, chosen state, intended consumer/session, scope, expiry and issuer authority. Compare it before any write-capable action and at resumption. Bind the granted target by identity, not just a string.

**Acceptance:** a granted create into A, then a retry into B, a replaced A, another volume, another consumer, and a widened session all refuse with zero host writes. Include same-content plans so manifest equality cannot hide the defect. §§4.13/4.15, R1/R10.

### AUD-29-02 — P1 — The landing snapshot argument is recorded but not used

**Evidence: Source.** [server landing](../../crates/server/src/landing.rs), lines 252–283; [landing engine](../../crates/land/src/engine.rs), land around 1530.

The server converts the requested snapshot into the database record, but passes the live mutable Volume to land. The engine plans and reads that volume's current overlay. It receives no selected snapshot. The recorded snapshot can therefore describe different bytes from those presented or written. There is no lookup validating the supplied snapshot in this path.

**Required change:** resolve and pin the requested immutable state before planning; make the engine's source explicit. Replanning, approval, execution and audit must refer to that same state, with defined advancement of subsequent live edits.

**Acceptance:** snapshot S, edit the live volume, land S and assert the old bytes were presented/written and later edits remain private. Unknown and foreign snapshots must refuse before writes. §4.15.

### AUD-29-03 — P1 — Target landing leases are shard-local, not target-global

**Evidence: Source.** [LandingState](../../crates/server/src/landing.rs), lines 63–77; [Leases](../../crates/land/src/grant.rs); [land](../../crates/land/src/engine.rs), lease take/release around 1565.

Each owner shard has its own Leases table. Two volumes on different shards can land concurrently into the same host target and each acquire its local lease. Database landing-lease records do not provide an enforced cross-shard target authority in this execution path. A path-string key alone is also insufficient against target aliases.

**Required change:** route a canonical target identity to one host-local lease owner, through the existing bounded ownership mechanism. Carry its fencing token through every write and resume. This is target landing serialization, not a new lock on ordinary filesystem writes.

**Acceptance:** two separately owned volumes and two aliases of one target produce one holder and one typed refusal. Include expiry, paused old holder, cancellation, and restart. §4.15 step 3.

### AUD-29-04 — P1 — A delete can remove an outsider's replacement

**Evidence: Source.** [engine delete](../../crates/land/src/engine.rs), lines 1107–1134.

A regular-file delete opens and fstats the file, closes its descriptor, then unlinks its name. An outsider may replace that name between the check and unlink. The new file is deleted without validation. If open_file returns NotFile, the code unlinks directly, without checking that the symlink or special entry is the witnessed object.

This is a separate issue from the replacement engine's exchange-and-verify logic. A passing replacement crash oracle does not prove deletion safety.

**Required change:** make removal a name transition that retains the displaced object, verify that exact object, and restore/refuse when it differs. Apply an equivalent identity discipline to symlinks, directory removal, recursive clear and rename.

**Acceptance:** inject outsider replacement at every host instruction around each removal. The outsider's bytes and name must survive; stale removal must conflict. §4.15, D-26.

### AUD-29-05 — P1 — Landing hides cleanup and durability failures, then can advance the source

**Evidence: Source.** [engine sync_all](../../crates/land/src/engine.rs), around 1345; land_under_lease around 1670–1740; [server finish](../../crates/server/src/landing.rs), around 427.

sweep errors become zero via unwrap_or(0). sync_all silently skips a touched directory when opening it fails without setting dirs_synced false. Some sync errors merely change the durability struct; the terminal state is computed principally from entry reports/crash classification. The server reply discards the engine's durability and degradation detail. Successfully written entries can be advanced out of the private overlay despite incomplete syncing.

**Required change:** classify every sweep/open/sync error. Preserve retryable divergence until the specified boundary is achieved, and return actual durability/degradation and concurrency facts in the public outcome. Distinguish an intentional supported durability level from a failed requested level.

**Acceptance:** inject directory-open failure, ENOSPC, sync failure and cleanup failure after writes; assert accurate public results and a subsequent resume that reaches the reference without losing private work. §4.15 steps 6–8.

### AUD-29-06 — P1 — Finishing a session landing marks its durable grant consumed

**Evidence: Source.** [server finish](../../crates/server/src/landing.rs), around 418; [Grants::consume](../../crates/land/src/grant.rs), around 155.

The engine consumes only Once grants. The server appends GrantStateChanged::Consumed for every supplied grant, including Session. Runtime and retained state disagree immediately. Grant listing and recovery can declare a live session grant spent; a restarted daemon cannot preserve the session contract.

**Required change:** publish the actual grant transition, with the intended consumer/session from AUD-29-01. Make the landing result and its terminal grant transition one correctly published operation where the recovery contract requires it.

**Acceptance:** issue a session grant, land twice, restart between landings, and verify continued validity only for its bound session/volume/target; Once is consumed exactly once. §§4.8/4.15.

### AUD-29-07 — P2 — Awaiting landing plans are neither bounded nor removed by successful use

**Evidence: Source.** [server landing](../../crates/server/src/landing.rs), present around 325, finish around 390, issue_grant around 561.

A presentation inserts an awaiting record at one landing id and advances next_landing. Execution allocates a fresh id; finish removes that fresh id, not the presentation's id. issue_grant leaves the awaiting record in place. Repeated plans retain target strings and metadata indefinitely, even after successful landings. The broader unpruned grant-record table is already an existing gap; this awaiting-map path adds a distinct leak.

**Required change:** a bounded, admitted plan lifecycle with an explicit presentation reference, expiry, consumption/revocation, and recovery behavior. Refuse before allocation when its derived capacity is spent.

**Acceptance:** many plan/grant/land cycles return the retained-plan count to the defined floor; abandoned plans expire, and capacity refusal changes no state. R3, ban 8.

### AUD-29-08 — P1 — Safe runtime APIs return references to state that is freed

**Evidence: Source; unsafe witness intentionally not executed.** [LocalRuntime](../../crates/rt/src/runtime.rs), Drop around 437 and context around 502; [SimRuntime::context](../../crates/rt/src/sim.rs), around 1083; [ShardContext::keep](../../crates/rt/src/shard.rs), around 402; [registry::reclaim_context](../../crates/rt/src/registry.rs), around 398.

context returns a static reference, but Drop reconstructs and drops the backing Box. Safe Rust can keep that reference after the runtime dies and call counters or other methods on freed memory. keep likewise returns a static reference to an object owned by the reclaimable context. A kept Send/Sync value can escape to another thread even though the context itself cannot. Public safe reclaim_context additionally accepts a numeric shard id without proving owning-thread or stopped-loop authority.

**Required change:** owner-bound borrows or generational handles whose use validates lifetime. Make reclamation private to an ownership proof. Do not repair this by leaking contexts forever or introducing Arc.

**Acceptance:** compile-time lifetime tests reject escaping references; Miri runs owner teardown with held handles, stale wakers and kept values. Audit every API returning static state from a reclaimable owner. §§4.2/4.3, R2.

### AUD-29-09 — P1 — Shared mapping APIs do not enforce the atomic/plain-byte aliasing rule

**Evidence: Source; Miri proof still required.** [shared mappings](../../crates/mem/src/shared.rs), bytes / atomic_u64 around 100–120 and word_view around 255.

The safe API can return a plain shared byte slice and an atomic view over the same bytes. A caller can retain the former while storing through the latter. word_view's SAFETY comment requires all other accesses to those bytes to be atomic, but bytes exposes unrestricted non-atomic access. Cross-process mappings make this discipline more important, not less.

**Required change:** establish interior mutability at the storage boundary and typed, disjoint ownership of byte ranges versus atomic words. Safe callers must not be able to create conflicting access. Check SparseObject and every IPC/anchor mapping user as siblings.

**Acceptance:** memory-model tests exercise retained byte views, atomic mutation, mixed widths, concurrent access and teardown. A comment is not an enforced invariant. §§4.2/4.7.

### AUD-29-10 — P1 — Buddy free accepts a forged block and corrupts its accounting

**Evidence: Run.** [buddy allocator](../../crates/mem/src/buddy.rs), free around 134; [arena](../../crates/mem/src/arena.rs), free.

Allocate 4,096 bytes from an 8,192-byte region, then free offset 1 / length 4,095. free accepts it, reports 8,191 free bytes, and coalesces an 8,192-byte block. The next 8,192-byte allocation panics in the debug probe. Floor division and rounded order are not exact block validation.

**Required change:** validate alignment, exact allocated length/order, range and allocation incarnation before changing free lists or totals. Prefer unforgeable owner handles; a publicly constructible extent also needs stale-reuse protection.

**Acceptance:** forged length/offset, interior free, cross-arena free, duplicate free and stale extent after reuse all refuse with unchanged accounting and subsequent valid allocation behavior. §4.2.

### AUD-29-11 — P1 — Generation wrap revives stale handles; packed wakers have a smaller alias boundary

**Evidence: Run plus Source.** [slab](../../crates/mem/src/slab.rs), generation updates around 77 / 274 / 296; [handle encoding](../../crates/mem/src/handle.rs), pack around 98 and matches around 139; [runtime wake validation](../../crates/rt/src/shard.rs), handle_wake around 1263.

With generation_base = u32::MAX, one remove/reinsert yields generation zero; an ancient generation-zero handle resolves to the new object. The runtime encoding stores and compares only 24 generation bits, so its alias boundary is 2^24 reuses of one slot, before the full 32-bit wrap. The comment describing the event as counted does not make masked equality detect it.

**Required change:** retire slots before exhausting the generation space of every representation and return the design's typed GenerationExhausted refusal. Preserve exhaustion across runtime/shard reuse. Never wrap or mask away the evidence of a stale handle.

**Acceptance:** initialize directly near both boundaries; exercise stale slab handles, wakers, cancelled tasks and recycled shard ids without running millions of iterations. §4.2, §4.3.

### AUD-29-12 — P1 — Runtime startup and drop can orphan worker threads

**Evidence: Source.** [Runtime::start / shutdown](../../crates/rt/src/runtime.rs), around 291–418.

Runtime owns JoinHandles but has no Drop that cancels and joins its workers. Dropping it detaches workers. A later thread-spawn failure drops already-created handles through the question-mark return. A worker whose ShardContext::build fails returns default counters; start can still return success with a nonfunctional shard. shutdown also converts thread panic into default counters.

**Required change:** transactional startup with worker readiness acknowledgements and rollback; explicit owned terminal state for all workers; typed failure reporting. Destruction must not silently detach active runtimes.

**Acceptance:** fail each preparation/spawn/context-build step, drop without explicit shutdown, and prove no live worker or registry slot remains. A failed shard must not be advertised as started. §4.3, ban 9.

### AUD-29-13 — P1 — Archive parsing admits decompression and reconstruction before memory admission

**Evidence: Source.** [archive read_chunk / decode_payload](../../crates/archive/src/archive.rs), around 481–532; [manifest reader](../../crates/archive/src/manifest.rs), around 289; [takeover restore](../../crates/server/src/verbs.rs), around 5225–5237.

The compressed payload's raw_len is used as the decompressor's output capacity without a per-chunk or cumulative admitted bound. Raw chunks do not require declared raw_len to equal their content length. Recursive manifest parsing has no depth bound. restore expands holes into Vecs and reconstructs the whole volume before the server reserves the volume's content budget.

A valid outer checksum does not make attacker-chosen sizes trustworthy; the sender can compute its own checksum. A small encoded object can demand a much larger heap or stack. An enrolled peer is authenticated, not trusted.

**Required change:** admission-aware decoding with caps on raw chunk size, total reconstructed content, entries, extents, names, depth and transient bytes; checked conversion and fallible allocation. Stream admitted output into the owning arena and use an iterative bounded manifest walk.

**Acceptance:** maximal raw_len, huge holes, repeated compressed references, deep nesting and metadata amplification refuse within a measured memory/CPU bound before allocation. §§4.2/4.9/4.11.

### AUD-29-14 — P1 — Archive restore ignores each extent's file offset

**Evidence: Run with raw-chunk fixture; Source.** [restore_file](../../crates/archive/src/restore.rs), around 47.

The implementation appends every extent and never reads extent.offset. A one-byte extent at file offset eight restores as [65], not eight zeros followed by A. Out-of-order and overlapping extents have no validation. The returned bytes may disagree with both the manifest metadata size and the hashed extent description.

**Required change:** either validate the canonical contiguous extent contract and refuse every gap/overlap/misordering, or honor checked file offsets and explicit holes under the design's sparse-file rule. Check final size against metadata.

**Acceptance:** sparse, out-of-order, overlapping, truncated and overflowing extent lists cannot silently restore different bytes. Verify through archive decode and the actual successor materialization path. §4.11, AC-7.3.

### AUD-29-15 — P1 — The manifest decoder accepts noncanonical and ambiguous trees

**Evidence: Run for trailing bytes and invalid component; Source for duplicate/order behavior.** [Node::decode / read](../../crates/archive/src/manifest.rs), around 282–321; [restore walk](../../crates/archive/src/restore.rs), around 71.

decode does not check exhaustion of input. Directory names are only checked for UTF-8, not valid single components; "../outside" is accepted. Sortedness and uniqueness are not enforced. restore builds string paths and inserts into maps, so duplicate paths can overwrite earlier nodes or metadata. Merkle verification can authenticate an ambiguous tree without resolving these semantic defects.

This audit does not claim a demonstrated host-path escape: downstream name validation may refuse it. Acceptance by the supposedly canonical format boundary is already wrong.

**Required change:** exact decoding, validated components, ordered unique entries, unambiguous inode/type/metadata rules, and canonical extents before publishing an Archive.

**Acceptance:** trailing bytes, dot/dot-dot, separators, NUL, duplicate names, unsorted names and path collisions refuse typed. Valid encodings retain deterministic identities. §§4.9/4.11.

### AUD-29-16 — P1 — Rename onto a base directory does not use the base-aware emptiness check

**Evidence: Source.** [Volume::rename](../../crates/vfs/src/volume.rs), around 1360–1393; [Overlay::rename](../../crates/vfs/src/base.rs), around 1427; compare Overlay::rmdir around 1390 and empty_for_rmdir around 659.

A materialized base directory starts with a merged node and an unloaded child listing. rmdir loads that listing and checks both overlay entries and base whiteouts. rename instead tests DirNode::is_empty. It can treat a directory with untouched disk children as empty and replace it. Overlay::rename does not load the target directory's child listing before delegating.

The same functions swallow target lookup errors with .ok() / let _ instead of distinguishing NotFound from stale, host or admission failure. That obscures the guarantee that a refused rename changes nothing.

**Required change:** one base-aware target validation path for rename and rmdir, with explicit handling of NotFound only. Secure all mutation resources before removing either source or target.

**Acceptance:** rename a directory over a nonempty lazy base directory before reading its children; expect NotEmpty and both trees unchanged. Repeat after listing, watcher invalidation, CoW and injected allocation/host refusal. §4.5, POSIX equivalence.

### AUD-29-17 — P1 — Takeover reconstructs a weaker volume policy and drops access state

**Evidence: Source; existing broader catalog-transfer gap.** [HeadValue](../../crates/server/src/head.rs), around 27; [materialize_taken_over](../../crates/server/src/verbs.rs), around 5317.

The placed head carries content identity, holders, name, size, name policy and owner. It does not carry require_locked or the access list. Reconstruction assigns require_locked = false, Role::Plain, Scratch base, no lease, and an empty access list. A volume that required locked residency can recover under weaker guarantees; granted consumers lose access. Lazy-base semantics also need an explicit coverage contract before becoming scratch.

Special green takeover has its own path; this finding is about the ordinary head reconstruction and missing complete policy, not an allegation that every green always becomes Plain.

**Required change:** place the complete durable catalog/policy state under the design's register classes and reconstruct it exactly. Refuse takeover that cannot meet an immutable policy. Define explicit base coverage and attachment/session reconciliation.

**Acceptance:** N=1 recovery and simulated/live fleet takeover preserve locked policy, rights, ownership, base coverage and object kind, or return the specified typed refusal. §§4.2/4.8/4.10/4.13.

### AUD-29-18 — P1 — Green recovery silently substitutes empty or shortened acknowledged state

**Evidence: Source.** [rebuild_green](../../crates/server/src/verbs.rs), around 6197.

A corrupt origin logs an error and installs Green::new. A corrupt chain entry stops replay but still installs the shorter engine. A decoded increment's submit outcome is ignored, as is settlement of recovered retention. The durable volume/chain record is not replaced by a typed unavailable/quarantined state that prevents serving a shorter acknowledged history.

“Logged” is not equivalent to fail-closed. This path can present empty or older content under the same volume id and allow further work to branch from it.

**Required change:** validate the entire recovered prefix, every accepted outcome, final head identity/version and memory charge before exposing the green. Corruption or resource refusal must fence it, preserving evidence for reviewed recovery.

**Acceptance:** corrupt origin, middle increment, wrong accepted version, replay conflict and insufficient retention all prevent serving or mutating the green; healthy replay exactly matches the reference. §§4.8/4.16, D-27.

### AUD-29-19 — P1 — “Async begin” can block an SDK event loop until the synchronous deadline

**Evidence: Source.** [Client::begin / send](../../crates/client/src/client.rs), around 754 / 1358; [Node async wrapper](../../crates/sdk-node/async.mjs); [Python async entry](../../crates/sdk-python/src/lib.rs).

begin calls send, which spins on a full command ring until reply_ns, and may reconnect through a loop that uses thread::park_timeout. rebind_if_needed may also perform blocking work. The SDK invokes these primitives synchronously before returning the Future/Promise. The nonblocking completion reader does not make request admission nonblocking.

**Required change:** a try-begin operation that returns an admitted id or typed pending-credit/reconnect state; event-loop readiness and deadline scheduling own further progress. Keep the synchronous facade over that same state machine.

**Acceptance:** fill the command ring and restart the daemon while an independent event-loop ticker runs. The ticker continues within its declared latency bound while calls wait or refuse. R6, §4.7.

### AUD-29-20 — P1 — Async SDK requests have no terminal path on daemon loss or reader failure

**Evidence: Source.** [Node _await / _ensureReader / _pump](../../crates/sdk-node/async.mjs), around 195–236; [Python finish / pump](../../crates/sdk-python/src/lib.rs), around 1282–1379.

Slow calls are retained until completion fd readiness yields a reply. The pump calls take_ready/poll_reply, which does not perform the synchronous exchange's stalled-reply recovery. No reply deadline timer drives pending calls. Node discards socket errors and has no end/close rejection path; an exception from takeReady escapes the callback outside its per-entry try block. Python cancellation leaves its pending entry until a reply arrives; if the daemon never replies it remains retained.

**Required change:** bounded owned pending operations with deadline, cancellation, reader-error and reconnect transitions. On terminal channel failure, settle every pending operation with a typed result. An Unpublished retry must preserve its request identity.

**Acceptance:** daemon death, fd closure, pump error, cancellation and no-reply fault each settle/release every pending request. Run restart histories through both published SDKs, not just the Rust sync client. §§4.3/4.7/4.9, ban 9.

### AUD-29-21 — P1 — Client request sequences wrap into “already acknowledged”

**Evidence: Run plus Source.** [Client::fresh_id / call_plain / session](../../crates/client/src/client.rs), around 701 / 638 / 544; [ClientWindow](../../crates/wire/src/request.rs), around 61–90.

The client increments a u32 sequence with wrapping_add. The server uses ordinary sequence <= watermark and max comparisons. After acknowledging u32::MAX, sequence zero is permanently Acknowledged and cannot be recorded as a new request. Reusing a sequence before acknowledgement also risks meeting an earlier completion.

This is not necessarily a decades-away boundary. At a hypothetical sustained 20,000 requests/s, 2^32 requests take approximately 2.49 days; that rate is an arithmetic scenario, not a measurement of this implementation.

**Required change:** refuse exhaustion before reuse and rotate to a new authenticated session identity through a defined transition, or revise the wire identity with exact recovery semantics. Do not use ambiguous modulo comparisons over unbounded histories.

**Acceptance:** seed the client/window near the last id and test begin, acknowledgements, Unpublished retry, forwarding and resume across exhaustion. §4.9, RIFL.

### AUD-29-22 — P1 — Buffered client replies can be silently discarded while still awaited

**Evidence: Source.** [Client::buffer / take_ready](../../crates/client/src/client.rs), around 815–844.

buffer removes the oldest reply once pending exceeds twice the ring slots. Its justification assumes ring capacity bounds total outstanding requests. A ring bounds simultaneous queued slots, not completed replies retained by a caller that continues to admit/drain requests without resolving older ids. The public API has no outstanding-operation registry enforcing that premise.

A caller can repeatedly begin and drain ready ids, retain their RequestIds, and cause the oldest pending result to disappear. Its later poll returns None indefinitely. Boundedness achieved by dropping an awaited result violates correctness.

**Required change:** admit requests against explicit pending capacity; distinguish protocol-only acknowledgements from caller-owned operations. Refuse new work before an awaited result would be evicted.

**Acceptance:** hold an early result while sending/draining more than the derived pending bound. The early result remains obtainable; new admission refuses safely. Include cancelled calls and acknowledgement replies. §4.9, ban 9.

### AUD-29-23 — P1 — MCP HTTP admits unbounded headers and one peer can stop all service

**Evidence: Source.** [HTTP transport](../../crates/mcp/src/http.rs), serve around 51 and read_request around 104.

MAX_BODY does not bound request lines, header lines, cumulative header bytes or header count. Each read_line grows a String without a cap. Connections are served serially for their entire keep-alive lifetime, with blocking reads and no request/idle deadline. One idle client prevents another from being accepted. A truncated body or broken connection returns an error through serve and ends the server.

**Required change:** bounded incremental parsing and connection ownership on the existing runtime; derived limits/deadlines; isolate per-connection failures from the listener. Reject malformed or contradictory Content-Length / transfer framing.

**Acceptance:** long unterminated line, many headers, slow body, idle keep-alive and connection reset stay within bounds and do not prevent an independent valid client from completing. §§4.9/4.12, R3/R6.

### AUD-29-24 — P1 — Loopback MCP does not validate Origin or Host before dispatch

**Evidence: Source; browser exploit not executed.** [HTTP parser/respond](../../crates/mcp/src/http.rs).

The parser ignores Origin, Host, request target and Content-Type. Any accepted POST body is dispatched as MCP JSON. Loopback binding does not identify the agent or exclude requests initiated by a web page. The endpoint's daemon client can execute authority-bearing tools without an HTTP caller binding.

**Required change:** enforce the documented local MCP authority boundary: validated origins and hosts, explicit enrollment/bearer binding where required, and capability/roots scope before dispatch. Do not put a grant verb on this surface. Check stdio record-size limits too.

**Acceptance:** foreign-origin, rebound host and unbound POST refuse before any tool effect; intended clients work under scoped authority. Complete the already-open roots/delegated-scope work. §§4.12/4.13.

### AUD-29-25 — P1 — Production landing executes synchronous whole-plan work on an owner shard

**Evidence: Source plus Scale inference.** [land_verb_unix](../../crates/server/src/landing.rs), land call around 280; [engine](../../crates/land/src/engine.rs), plan / validate / write_all / sync_all.

The server calls the whole engine directly while borrowing the volume and store. Host reads, writes, directory traversal and syncing execute synchronously before returning. The request supplies cores = 1, max_depth = 1 and variance = 0 rather than a measured production scheduling plan. Cooperative executor scheduling cannot preempt an ordinary function that never yields.

A large granted landing can monopolize its owner shard, delaying unrelated provisioning, lease checks and shutdown. The standalone engine's performance results do not demonstrate production fairness.

**Required change:** an owned, resumable landing operation with bounded host-I/O work and explicit terminal/cancellation steps, driven by the custom completion runtime. Charge transients and preserve the exact grant and target fence.

**Acceptance:** large landing concurrent with uncontended provisioning/reads/lease expiry. Publish p99/p999/max and maximum shard step, and prove every slice stays within the derived budget. §§4.3/4.15, R9.

### AUD-29-26 — P1 — Saturated Raft term permits two leaders in one term

**Evidence: Run.** [start_election](../../crates/cluster/src/raft.rs), around 1127; pre-vote term calculation around 1041.

start_election uses saturating_add for current_term and overwrites voted_for with self. Restore accepts a legal publication at u64::MAX. In a three-voter probe, node 1 becomes leader with node 2's vote. Node 2 then starts an election at the same maximal term and becomes leader with node 3's vote. Node 1 is still leader. Output: first=Leader;second=Leader;same_term=true.

The boundary is externally encodable; a authenticated peer's term field is not a trusted machine-derived counter. This is a concrete Election Safety counterexample outside the explorer's small term range.

**Required change:** typed term exhaustion before campaign, persistent vote changes or outgoing next-term messages. Audit log index, configuration generation and promotion epoch exhaustion with the same discipline.

**Acceptance:** maximal-term recovery, higher-term message, pre-vote, campaign and transfer histories preserve one-vote-per-term and Election Safety. §§4.8/4.9, T-8.13.

### AUD-29-27 — P2 — Transport packet-number exhaustion is not refused

**Evidence: Source.** [SentTracker::next_pn](../../crates/transport/src/conn.rs), around 262; compare [Sealer](../../crates/transport/src/seal.rs), which checks nonce exhaustion.

next_pn saturates at u64::MAX and returns that value repeatedly. A packet number used as an AEAD nonce input must not repeat under the same keys. The checked control-seal counter is a good precedent; the session tracker does not carry that terminal refusal. FlowController's credit ceilings also add window values with unchecked arithmetic.

This audit did not run billions of sends or reproduce key reuse on a live socket. The source boundary must nevertheless close before an externally seeded or recovered counter can reach it.

**Required change:** enforce the session format's packet-number ceiling and key/session transition before reuse. Check credit additions and reject invalid maximal offsets before mutating accounting.

**Acceptance:** initialized-near-limit tracker/session tests prove unique packet numbers or typed termination, and hostile maximal credit/consumed fields never panic or wrap. §4.10a, no-panic law.

### AUD-29-28 — P1 — Consensus heartbeats wait behind every shard's record and content work

**Evidence: Source plus Scale inference.** [run_record_plane](../../crates/server/src/fleet.rs), around 6058–6123; run_record_period and materialize_adopted_objects.

One coordinator awaits council drive, root drive, configuration following, every owner shard's record period, takeover rounds, adopted-content materialization, then sleeps a heartbeat interval. Its next election/check-quorum/replication drive depends on all that work completing.

The period therefore contains a term proportional to owed objects and their network/storage deadlines. Async awaits let other tasks run, but they do not let this coordinator reach its next consensus drive. A large export backlog or failed holder can produce election/lease churn in an otherwise healthy configuration group.

**Required change:** independently scheduled, bounded owners for consensus/control and bulk placement/recovery, with explicit lifecycle and per-class admission. Share sessions through a bounded multiplexing owner rather than exclusive endpoint lending. No orphan tasks and no second laptop mode.

**Acceptance:** inject bulk load, slow holders, packet loss, recovery and cooperative-budget violations while measuring actual maximum gaps between heartbeat/check-quorum drives. Unrelated content load must not enter the control latency bound. §§4.3/4.8/4.9.

### AUD-29-29 — P2 — Configuration fan-out copies full state before version checks

**Evidence: Source plus Scale inference.** [fan_configs_to_shards](../../crates/server/src/fleet.rs), around 5984–6032.

Every period clones placement, full members, root configuration and lease state; it clones them again for each other shard. The receiver checks configuration versions only after those allocations/copies. members_snapshot also copies the membership for pruning. Quiet configuration has nonzero cost proportional to fleet membership, root homes and shards.

For S shards, N members and H root-home entries, these terms are O(S × (N + H)) per host per period. If every host carries the full roster, aggregate membership copying can reach O(N²S). This is a structural complexity result, not a measured wall-clock prediction.

**Required change:** fan unchanged configuration epochs by handle/reference publication under the existing ownership rules; send changed bounded state only to shards that need it. Lease evidence has its own cadence and expiration semantics.

**Acceptance:** count copied/encoded bytes and allocations for unchanged and changed configurations across increasing N/H/S. Verify identical routing/fencing and self-healing when a bounded fan channel refuses. D-7, D-14, R8.

### AUD-29-30 — P2 — Full consensus-state serialization remains on the acknowledgement path

**Evidence: Source plus Scale inference; existing incremental-publication work.** [Retained::capture / publish](../../crates/server/src/retention.rs), around 59 / 246; [RaftNode::saved](../../crates/cluster/src/raft.rs), around 915.

A retention publication clones saved Raft logs/window state and encodes base and current configurations for both groups, along with other retained authorization/recovery state. It serializes the full record, builds another checksum-bearing payload, and publishes it into the anchor. Compaction is implemented; that does not make publication incremental or bounded per changed entry.

This cost affects votes, appends and configuration acknowledgement latency and grows with retained state. Under capacity pressure the publication fails after protocol mutation, requiring fencing rather than admitting a bounded change up front.

**Required change:** measure clone/encode/hash/copy cost separately; derive admission against the published representation before mutation; evaluate an atomic bounded delta/publication scheme with periodic canonical checkpoints. Preserve publish-before-ack and exact recovery.

**Acceptance:** restart at every publication step and compare the complete prefix/vote/configuration; report per-operation cost across log, membership and root-home sizes, including capacity refusal. §§4.8/4.9.

### AUD-29-31 — P2 — The structural wall is a source-string check, not the claimed syscall-linkage proof

**Evidence: Source.** [xtask structural](../../xtask/src/main.rs), around 267–440; [workspace lint configuration](../../Cargo.toml); [clippy configuration](../../clippy.toml).

The gate walks dependencies for a list of forbidden crates and scans source text for particular symbol spellings. It does not prove that every write-capable syscall in the linked dependency graph resides only behind land. Aliased imports, different syscall wrappers, macro-generated code and transitive dependencies can evade a string list. Clippy strengthens selected symbol rules, but does not establish the stated R1 proof.

**Required change:** make the enforced claim match the mechanism. Add Rust structural fixtures covering alternate spelling/alias/macro paths, explicit dependency capability review, and architecture/export restrictions that make write authority difficult to construct. Retain real hermeticity tracing as an independent oracle. Do not claim a linker proof from source grep.

**Acceptance:** deliberately forbidden fixture variants are rejected; allowed read-only exceptions remain scoped and justified. The end-to-end tracer checks every granted-target boundary. R1/R2, AC-0.1.

### AUD-29-32 — P2 — The published capability and test-gate story can overstate current assurance

**Evidence: Source; existing gaps.** [README](../../README.md), around 76–105 / 156 / 259; [CI](../../.github/workflows/ci.yml), around 332–387 / 534–553; [conformance record](../wip/conformance.md); [benchmark record](../wip/BENCHMARKS.md).

README still describes an old build in which the grant command, locked residency, live Linux FUSE and fleet wiring were absent, alongside top-level present-tense claims about automatic recorded edits and immediate remote snapshots. The code and gap ledger now differ from those statements. Users cannot infer which workflows are actually supported.

Callgrind runs benchmarks but the inspected configs have no regression thresholds/baseline comparison enforcing the claimed instruction-count ratchet. Host-specific wall-clock ratchets skip on runners without baselines. “Nightly” lanes run on main pushes, not a scheduled nightly trigger; TSan remains explicitly owed. No executable i686 test lane was found in CI. Platform conformance has substantial reviewed exceptions and skipped scopes.

**Required change:** publish a short generated capability/status table tied to executable acceptance tests, distinguish historical evidence from current-tree coverage, establish deterministic regression gates with recorded baselines, and state schedule/platform limitations accurately. Complete the design-required tooling only through its authorized Rust/CI scope.

**Acceptance:** capability text cannot drift from its reviewed implementation/evidence record; deliberate benchmark regressions fail; missing baselines cannot look like passed performance gates; 32-bit narrowing and live bridge semantics receive appropriate behavioral tests. R4/R5/R8/R9, Part 6.

The ledger records a pipeline wired on 2026-09-29, so “no pipeline exists” would be wrong. The unresolved question is whether the live endpoint ownership/round lifecycle permits the core to use its window effectively under WAN conditions. Count actual sent-ahead batches and concurrent append flights on the daemon; a configured window or passing pure-core test is insufficient.

### 4.2 Raft improvements in priority order

1. **Close term/index/epoch exhaustion and recovery validation first.** AUD-29-26 is an actual safety counterexample. Extend bounded histories to direct boundary seeds, snapshot/install, fast-window recovery and retained membership.
2. **Separate control cadence from object backlog.** AUD-29-28 is the highest liveness priority. Election parameters derived from RTT are meaningless if application work delays the timer drive by an unrelated amount.
3. **Make live follower progress ownership explicit.** One session has bounded, prioritized concurrent exchanges now. Replace exclusive whole-endpoint lending with a bounded peer/session owner serving requests by class. Keep one authoritative progress state per follower; late success/refusal/snapshot replies must not regress it.
4. **Measure effective replication flow control.** Bound bytes and messages in flight per follower using admitted memory and measured BDP, not a batch count alone. Distinguish probe, replicate and snapshot progress so a rejected probe or lost snapshot cannot wedge a follower.
5. **Bound snapshot and configuration publication end to end.** An entry batch cap does not bound a whole configuration snapshot. Build, encode, send, verify, install and retain it in cooperative admitted slices; measure catch-up during ongoing configuration changes.
6. **Retain membership failure-domain intent.** Regional voters and root representatives must be eligible, live, caught up and appropriately placed. The existing “root representatives chosen by id order” gap is important. Optimize measured quorum RTT subject to that intent; lowest id is not a fault-domain policy.
7. **Backpressure uncommitted configuration work.** Compaction removes committed prefixes. It does not bound a minority leader's uncommitted tail or the memory consumed by learners and repeated proposals. Refuse before an admitted budget is exceeded; preserve typed caller retry.
8. **Keep publish-before-ack exact.** Optimize AUD-29-30 only with crash/restart oracles that retain term, vote, committed prefix, snapshot, configuration and accepted windows together.
9. **Audit every takeover against the register invariants.** Couple council decisions to the existing TotalOrder, Continuity, StaleNeverCommits, ReadSafety and NoLoss history checks. A stable failure-detector belief is availability evidence; it is not permission to lose fencing history.
10. **Benchmark the real decision workload.** Keep one log for leader-origin configuration commands unless the multilog record changes. Keep fast-track enablement based on the recorded workload/loss crossover. Do not advertise a research mechanism as an unconditional WAN speedup.

No new coordination service, global per-file index or consensus-on-write path is proposed.

### 4.3 Scaling risks beyond consensus

**Formation and peer ownership.** The direct-contact rule in [fleet.rs](../../crates/server/src/fleet.rs), around 3980, includes bounded neighborhoods, voters and staged peers, which is appropriate. Formation contacts everyone and peer tasks are created from the roster. The API/source distinction matters: bounded steady active contacts does not prove bounded total task/roster/socket memory or safe simultaneous restart traffic. Count dormant tasks and partially formed sessions too. At fleet size N, all-to-all formation can create O(N²) attempted relationships.

**Placement and the source of a remote attach.** Current archive restoration is eager. A metadata-only attach followed by lazy content lookup is still owed, as [restore.rs](../../crates/archive/src/restore.rs) itself states. Remote content has to be verified, admitted, bounded and served without copying the whole volume before it can attach. The design's source directory can be enormous precisely because only loaded state should cost RAM.

**Failure domains and repair amplification.** f+1 copies protect the declared host-failure model, not automatically rack, zone or region loss. Candidate selection must encode failure-domain constraints. Measure concurrent owners failing, correlated holder loss, repair traffic, lost-copy detection, scatter/copyset overlap and memory needed to repair while existing promises remain live. Placement shortfall must refuse or degrade explicitly, never quietly lower durability.

**Routing and identity churn.** Id-routed ownership is the correct starting point. Location hints, moved homes, retired incarnations, membership maps, pending handshakes, completion records and forwarding retries all need derived retention bounds. Whole-RAM replacement and overlap of old/new identities are explicitly open in [TBD_FIXES.md](../wip/TBD_FIXES.md). A late authenticated old announcement must not undo a new identity/location.

**Hot objects.** A green volume has one serialization owner; Meta-scale aggregate throughput does not imply unbounded throughput for one shared green. Measure conflict-heavy submit, rebase and metadata histories on that owner. Bound admission and report pressure while preserving deterministic order.

**Leases and clocks.** Keep leases tied to clock-domain and observed confirmation evidence, not a cached belief that can outlive a pause. The working tree includes active lease repairs. This audit does not claim those repairs passed. Re-run stopped-owner, stopped-successor, delayed-message, changed-cohort, joint-configuration and ordinary latest-read histories with those edits.

**Network service classes.** Priority labels alone cannot guarantee control latency if receive parsing, decryption, reconstruction, session ownership or executor steps share an unbounded bottleneck. Test class isolation at every stage, including packets from an authenticated peer whose bulk demand exceeds admission.

## 6. Required acceptance programme

This is a prioritized programme, not a new CI job added by this audit.

### 6.1 First close the laptop safety contract

1. Zero-write negative histories for grant target/consumer/volume/snapshot binding, alias targets, expired sessions and stale landing holders.
2. Instruction-by-instruction outsider interference and crash/resume oracles for replace, delete, symlink, rename, rmdir and clear.
3. Miri lifetime/alias tests and direct boundary seeds for runtime reclamation, kept objects, shared words and packed wakers.
4. Allocator/handle histories against a serial model with invalid frees, stale reuse, exact charges and capacity refusal.
5. Hostile archive and wire tests that assert both refusal and an allocation/CPU bound.
6. SDK restart, no-reply, cancellation, ring-full and reader-error histories with a concurrently running loop ticker.
7. Exact catalog/rights/policy recovery and green replay identity checks.

### 6.2 Then demonstrate one code path across scale

| Dimension | Required sweep | Observable contract |
|---|---|---|
| Hosts / shards | N=1 differential, increasing regional membership to the stated thousands-host envelope; 32–192 shard/core configurations where hardware permits | Same replies, seals, identities, refusals and recovery semantics; per-host control work is bounded |
| Loaded state / base | Tiny private state over huge base; increasing loaded inodes to millions | Provisioning independent of base size; RAM and metadata follow admitted loaded state |

## 8. Recommended order of work

1. Close grant binding and exact-snapshot landing, target authority and outsider deletion safety. These decide whether the product is permitted to touch a user's disk at all.
2. Close runtime/mapping soundness, allocator validation and exhaustion. Otherwise all higher-level test results rest on unsafe foundations.
3. Bound and validate archive/wire admission; fence incomplete recovery and preserve exact policy and rights.
4. Make SDK admission/completion/cancellation and MCP service terminal, bounded and honestly async.
5. Separate fleet control progress from bulk work; prove live pipeline use and bounded metadata/retention costs.
6. Establish current capability truth and the missing ratchets/platform/scale evidence, then optimize from recorded measurements.

No implementation defect is closed by this document. Findings must become failing behavioral tests, minimal design-consistent repairs, and sibling sweeps. Existing gaps remain open until their actual acceptance contracts pass.
