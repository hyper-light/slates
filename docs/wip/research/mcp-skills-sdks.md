### 2.1 MCP as of September 2026

Definitions. MCP (Model Context Protocol) is a JSON-RPC 2.0 based protocol by which an AI "host" application (client) discovers and invokes tools, reads resources, and fetches prompts from a "server". JSON-RPC 2.0 is a stateless, transport-agnostic RPC envelope: requests carry `jsonrpc:"2.0"`, `method`, `params`, `id`; notifications omit `id`; responses carry exactly one of `result` or `error`; reserved error codes are -32700 (parse), -32600 (invalid request), -32601 (method not found), -32602 (invalid params), -32603 (internal), and -32000..-32099 (server-defined); spec dated 2010-03-26, last updated 2013-01-04 [B: JSON-RPC 2.0 specification, jsonrpc.org].

#### 2.1.1 Revision history and what changed

- **2024-11-05**: first dated revision (the baseline that 2025-03-26's changelog diffs against): JSON-RPC 2.0 messages; stdio and "HTTP+SSE" transports; tools, resources, prompts, sampling, roots, logging, progress, cancellation, pagination [B: MCP changelog 2025-03-26, "changes since 2024-11-05"].
- **2025-03-26**: OAuth 2.1 authorization framework (PR #133); Streamable HTTP transport replaces HTTP+SSE (PR #206); JSON-RPC batching added (PR #228); tool annotations "like whether it is read-only or destructive" (PR #185); `message` on `ProgressNotification`; audio content type; `completions` capability [B: MCP changelog 2025-03-26].
- **2025-06-18**: JSON-RPC batching removed (PR #416); structured tool output (PR #371); MCP servers classified as OAuth Resource Servers with Protected Resource Metadata (PR #338); clients MUST implement RFC 8707 Resource Indicators (PR #734); elicitation (PR #382); `resource_link` content in tool results (PR #603); `MCP-Protocol-Version` header required on HTTP after negotiation (PR #548); lifecycle SHOULD to MUST; `_meta` on more types (PR #710); `context` on `CompletionRequest` (PR #598); `title` fields separate from programmatic `name` (PR #663) [B: MCP changelog 2025-06-18].
- **2025-11-25**: OpenID Connect Discovery for authorization-server discovery (PR #797); icons on tools/resources/templates/prompts (SEP-973); incremental scope consent via `WWW-Authenticate` (SEP-835); tool-name guidance (SEP-986); `ElicitResult`/`EnumSchema` rework (SEP-1330); URL-mode elicitation (SEP-1036); tool calling inside sampling (SEP-1577); OAuth Client ID Metadata Documents (SEP-991); experimental tasks (SEP-1686); stderr allowed for all stdio logging (PR #670); 403 on invalid Origin (PR #1439); input validation errors are tool-execution errors, not protocol errors (SEP-1303); SSE polling/disconnect-at-will (SEP-1699); RFC 9728 alignment (SEP-985); JSON Schema 2020-12 default dialect (SEP-1613); SDK tiering (SEP-1730) [B: MCP changelog 2025-11-25].
- **2026-07-28** (the revision the site labels "latest" on 2026-09-03; the "draft" changelog is empty: "Changes since the most recent release will accumulate here"). Major changes, quoted headings: (1) remove protocol-level sessions and `Mcp-Session-Id` (SEP-2567); (2) "Make MCP stateless: remove the `initialize`/`notifications/initialized` handshake" — every request carries `_meta` `io.modelcontextprotocol/protocolVersion` and `io.modelcontextprotocol/clientCapabilities`, clients SHOULD send `clientInfo`, servers SHOULD return `serverInfo` in result `_meta`; mismatches return `UnsupportedProtocolVersionError` (SEP-2575); (3) `server/discover` MUST be implemented (SEP-2575); (4) `subscriptions/listen` replaces the HTTP GET stream and `resources/subscribe`/`unsubscribe` (SEP-2575); (5) `ping`, `logging/setLevel`, `notifications/roots/list_changed` removed; log level per request via `_meta` `io.modelcontextprotocol/logLevel`; (6) tasks moved out of core into the official extension `io.modelcontextprotocol/tasks`, `tasks/result` replaced by polling `tasks/get`, `tasks/update` added, `tasks/list` removed (SEP-2663); (7) Multi Round-Trip Requests (MRTR) replace server-initiated requests: servers return `InputRequiredResult` (`resultType:"input_required"`) and the client retries with `inputResponses` (SEP-2322); (8) all results carry a required `resultType` (`"complete"` or `"input_required"`); (9) SSE resumability and `Last-Event-ID` removed [B: MCP changelog 2026-07-28]. Minor: `extensions` field in capabilities; OpenTelemetry `traceparent`/`tracestate`/`baggage` in `_meta` (SEP-414); deterministic `tools/list` order for prompt-cache hits; required `Mcp-Method`/`Mcp-Name` HTTP headers and `x-mcp-header` parameter mirroring (SEP-2243); required `ttlMs` and `cacheScope` on list/read results (SEP-2549); resource-not-found code changed -32002 to -32602; RFC 9207 `iss` validation (SEP-2468); `application_type` in DCR (SEP-837); credentials keyed by issuer (SEP-2352); `inputSchema`/`outputSchema` may use any JSON Schema 2020-12 keyword and `structuredContent` may be any JSON value (SEP-2106); `notifications/elicitation/complete` removed; error-code allocation policy (-32000..-32019 legacy/implementation, -32020..-32099 reserved for spec; `HeaderMismatch` -32020, `MissingRequiredClientCapability` -32021, `UnsupportedProtocolVersion` -32022) [B: MCP changelog 2026-07-28]. Deprecated (min 12-month window, SEP-2596 lifecycle policy): Roots, Sampling, Logging (SEP-2577; suggested migrations: pass paths as tool params, call LLM APIs directly, log to stderr/OTel); HTTP+SSE transport; `includeContext` values `thisServer`/`allServers`; OAuth Dynamic Client Registration in favor of Client ID Metadata Documents (PR #2858) [B: MCP changelog 2026-07-28].
- Era vocabulary used by the spec: "Modern" = per-request metadata (2026-07-28 and later); "Legacy" = `initialize` handshake (2025-11-25 and earlier); "Dual-era" = supports both. Compatibility matrix: Modern client + Legacy server "Fails"; Legacy client + Modern server "Fails" (server rejects `initialize`; HTTP 400 for missing headers); Dual-era client or server "Works" against either era; a dual-era server "MAY serve both eras concurrently on the same endpoint or process", selecting legacy semantics when the first message is `initialize` [B: MCP 2026-07-28 versioning page].
- Statelessness rules that matter for a daemon: "Servers MUST NOT rely on prior requests over the same connection to establish context"; "State that needs to span multiple requests ... MUST be referenced by an explicit identifier the client passes on each request"; an open stdio process "is not a conversation or session: clients may interleave unrelated requests on the same transport" [B: MCP 2026-07-28 basic/index]. The tools page adds non-normative "Stateful Tools" guidance: return an explicit opaque handle from a creation tool, validate authorization on every call, state the retention policy in the tool description, and return a tool-execution error for expired handles [B: MCP 2026-07-28 server/tools].

#### 2.1.2 Transports

- **stdio (2026-07-28)**: server reads JSON-RPC from stdin, writes to stdout; "Messages are delimited by newlines, and MUST NOT contain embedded newlines"; server "MUST NOT write anything to its stdout that is not a valid MCP message"; stderr MAY carry UTF-8 logs; client shuts down by closing stdin, waiting, then escalating (SIGTERM then SIGKILL on POSIX; `TerminateProcess`/Job Objects on Windows); servers "SHOULD exit promptly when their standard input is closed"; cancellation is `notifications/cancelled`; unexpected exit: client SHOULD restart and re-send `subscriptions/listen` [B: MCP 2026-07-28 transports/stdio]. Directly relevant to slates: "The wire format (one newline-delimited JSON-RPC message per line over a reliable bidirectional byte stream) works unchanged over Unix domain sockets, TCP connections, or any similar channel", and custom transports over such streams "SHOULD reuse this framing" [B: MCP 2026-07-28 transports/stdio and transports overview "Custom Transports"]. Backward compatibility probe on stdio: send `server/discover` first; a `DiscoverResult` or a recognized modern error means modern; any other error or timeout means legacy, and the fallback "MUST NOT be keyed to one specific error code" [B: MCP 2026-07-28 transports/stdio].
- **Streamable HTTP (2026-07-28)**: one MCP endpoint accepting POST; each JSON-RPC request/notification is its own POST; client sends `Accept: application/json, text/event-stream`; server answers with a single JSON object or a request-scoped SSE stream; notifications get `202 Accepted`; the GET stream, `Mcp-Session-Id`, DELETE, and `Last-Event-ID` are gone (legacy GET/DELETE get `405`); required headers `MCP-Protocol-Version`, `Mcp-Method`, and `Mcp-Name` (for `tools/call`, `resources/read`, `prompts/get`), with Base64 sentinel encoding `=?base64?...?=` for non-ASCII values; header/body mismatch is `400` + JSON-RPC `-32020`; unknown method is `404` + `-32601`; closing the SSE stream is the cancellation signal; servers MUST validate `Origin` (403 on invalid) to stop DNS rebinding, SHOULD bind 127.0.0.1 locally, SHOULD authenticate; SHOULD send `X-Accel-Buffering: no` and periodic SSE comment keep-alives [B: MCP 2026-07-28 transports/streamable-http].
- **HTTP+SSE (2024-11-05)**: deprecated since 2025-03-26 and formally "Deprecated" under the lifecycle policy in 2026-07-28; "New implementations SHOULD NOT adopt it" [B: MCP 2026-07-28 transports/streamable-http].
- **Authorization (HTTP only)**: based on OAuth 2.1 draft-ietf-oauth-v2-1-13, RFC 6750, RFC 8414, RFC 8707, RFC 9728, RFC 9207, and draft-ietf-oauth-client-id-metadata-document-00; MCP server = OAuth resource server; servers MUST implement RFC 9728 Protected Resource Metadata; clients MUST send `resource` (RFC 8707) and use `Authorization: Bearer`, never the query string; tokens MUST be audience-validated; "Implementations using an STDIO transport SHOULD NOT follow this specification, and instead retrieve credentials from the environment" [B: MCP 2026-07-28 basic/authorization].
- Client-side extras: Claude Code accepts transports `http`, `sse` (deprecated), `stdio`, and `ws` (WebSocket, via `claude mcp add-json ... {"type":"ws"}`); scopes local (`~/.claude.json`), project (`.mcp.json`), user; OAuth with automatic client registration; "tool search" defers loading tools until first use; default MCP output warning at 10,000 tokens and hard limit 25,000 tokens (`MAX_MCP_OUTPUT_TOKENS`), with a per-tool `_meta["anthropic/maxResultSizeChars"]` override [B: Claude Code MCP docs, code.claude.com/docs/en/mcp, fetched 2026-09-03].

#### 2.1.3 Primitives (2026-07-28 unless stated)

- **Tools**: fields `name` (SHOULD be 1-128 chars from `[A-Za-z0-9_.-]`, case-sensitive, unique per server), `title`, `description`, `icons`, `inputSchema` (MUST be a JSON Schema object; 2020-12 default; no-arg tools use `{"type":"object","additionalProperties":false}`), `outputSchema`, `annotations` ("clients MUST consider tool annotations to be untrusted unless they come from trusted servers"). Results: `content[]` of `text`, `image`, `audio`, `resource_link`, or embedded `resource`; `structuredContent` (any JSON value; SHOULD also be serialized into a text block for backward compatibility; MUST conform to `outputSchema` when given); `isError: true` for tool-execution errors that the model should see, versus JSON-RPC errors (`-32602` unknown tool) for protocol errors. Servers "SHOULD return tools in a deterministic order". List results carry `nextCursor`, `ttlMs`, `cacheScope` [B: MCP 2026-07-28 server/tools]. Tool annotation names are `readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint` (introduced 2025-03-26, PR #185) [B: MCP changelog 2025-03-26; schema `ToolAnnotations`] (defaults verified in 2.1.6 below).
- **Resources**: `uri`, `name`, `title`, `description`, `mimeType`, `size`, `icons`, `annotations` (`audience` in {user, assistant}, `priority` 0.0-1.0, `lastModified` ISO 8601); `resources/read` returns `contents[]` each with `text` or base64 `blob`; a directory read MAY return several contents; templates use RFC 6570 URI templates via `resources/templates/list`; URI scheme guidance: `https://` only when the client can fetch directly, `file://` for "resources that behave like a filesystem" (need not be a physical filesystem) with XDG MIME `inode/directory` for directories, `git://`, and custom schemes per RFC 3986; not found is `-32602` (clients SHOULD still accept legacy `-32002`); an empty `contents` array MUST NOT be used for a missing resource; servers MUST sanitize `file://` paths against traversal [B: MCP 2026-07-28 server/resources].
- **Prompts**: `name`, `title`, `description`, `arguments[] {name, description, required}`, `icons`; `prompts/get` returns `messages[] {role: user|assistant, content}`; prompts are "user-controlled ... For example, as slash commands"; argument completion via the completion utility [B: MCP 2026-07-28 server/prompts]. Claude Code exposes prompts as `/mcp__<server>__<prompt>` and resources as `@server:scheme://path` mentions [B: Claude Code MCP docs].
- **Sampling, roots, logging**: deprecated in 2026-07-28 (SEP-2577) [B: changelog]. **Elicitation**: survives, but only inside MRTR `inputRequests` (`elicitation/create`, form mode with `requestedSchema`, plus URL mode); servers MUST NOT send `inputRequests` the client did not declare capability for; `requestState` is opaque to clients and "attacker-controlled input" to servers, to be HMAC/AEAD-protected with principal, TTL and request digest if it influences authorization [B: MCP 2026-07-28 patterns/mrtr].
- **Progress / cancellation / pagination**: `progressToken` in `_meta` opts into `notifications/progress`; cancellation is `notifications/cancelled {requestId, reason}` on stdio and stream-close on HTTP; servers MAY ignore cancellation for unknown/completed requests and MUST NOT respond after honoring it; "Implementations SHOULD establish timeouts for all sent requests" and SDKs "SHOULD allow these timeouts to be configured on a per-request basis"; pagination is opaque-cursor (`nextCursor`; empty string is a valid cursor; invalid cursor is `-32602`) for `tools/list`, `resources/list`, `resources/templates/list`, `prompts/list` [B: MCP 2026-07-28 patterns/cancellation; server/utilities/pagination].
- **Subscriptions**: `subscriptions/listen` with a `notifications` filter (`toolsListChanged`, `promptsListChanged`, `resourcesListChanged`, `resourceSubscriptions: string[]`); server MUST first send `notifications/subscriptions/acknowledged` carrying `io.modelcontextprotocol/subscriptionId` (= the JSON-RPC id of the listen request), then only the requested notification types; graceful server close is a normal result to the listen request; on stdio the client must re-subscribe after reconnect [B: MCP 2026-07-28 patterns/subscriptions].
- **Tasks (long-running)**: official extension `io.modelcontextprotocol/tasks` (spec in modelcontextprotocol/ext-tasks). Client declares it in per-request `clientCapabilities.extensions`; server advertises it in `server/discover`; server MAY answer `tools/call` with `resultType:"task"` carrying `taskId`, status, `ttlMs`, `pollIntervalMs` ("The task must be durably created before sending the response"); statuses `working`, `input_required`, `completed`, `failed`, `cancelled` (last three terminal); methods `tasks/get` (returns `result` or `error` on terminal), `tasks/update` (client supplies `inputResponses`), `tasks/cancel` (cooperative); optional `notifications/tasks` via `subscriptions/listen`; `tasks/list` and blocking `tasks/result` no longer exist [B: MCP Tasks extension overview; changelog 2026-07-28].
- **Batching**: added 2025-03-26, removed 2025-06-18; request `id` MUST NOT be null and MUST NOT collide with an in-flight id from the same sender [B: changelogs; MCP 2026-07-28 basic/index].
- **Extensions model**: identifier `{vendor-prefix}/{name}` with reverse-DNS vendor prefix (e.g. `com.example/my-extension`); negotiated through the `extensions` map in capabilities; official ones: OAuth client credentials, enterprise-managed authorization (ext-auth), MCP Apps `io.modelcontextprotocol/ui` (ext-apps), Tasks (ext-tasks); "Extensions are always disabled by default and require explicit opt-in" [B: MCP extensions overview].

#### 2.1.4 Conformance and inspector tooling

- `@modelcontextprotocol/conformance` (GitHub Action pinned in SDK CI as `modelcontextprotocol/conformance@v0.1.11`): client mode runs your client binary against reference servers (`--command`, `--scenario`, `--suite all|core|extensions|backcompat|auth|metadata|draft`); server mode tests an HTTP URL (`server --url http://localhost:3000/mcp`); `--spec-version 2025-11-25|2026-07-28`; `--requirements <revision>` runs "exactly what a spec revision requires, frozen at its release" (`requirements/<revision>.yaml`); "dated versions through `2025-11-25` use the stateful lifecycle (initialize handshake), while ... `2026-07-28` uses the stateless lifecycle (per-request `_meta`)"; the `server-stateless` scenario "alone is over twenty" checks (including `sep-2575-server-implements-discover`); `--expected-failures` baselines; `tier-check` assesses SDK tiers per SEP-1730; rust-sdk is exercised with a `STATELESS=1` env, go-sdk with `-stateless`, csharp-sdk at a `/stateless` endpoint [C: modelcontextprotocol/conformance README, fetched 2026-09-03]. Gap: server mode is URL-based, so a stdio-only server must be fronted by the HTTP binding (or tested in client-mode reference flows) to use the suite.

- Official SDK state: TypeScript SDK v2 "implements the 2026-07-28 MCP spec", runs on Node.js, Bun, and Deno, v1.x in maintenance [C: modelcontextprotocol/typescript-sdk README]; Python SDK v2 "supports the 2026-07-28 MCP specification (and every earlier revision)", Python 3.10+, transports stdio, Streamable HTTP, SSE [C: modelcontextprotocol/python-sdk README]; Rust SDK `rmcp` 3.2.0 (see next).

#### 2.1.5 rmcp architecture and the cost of an own MCP layer

- rmcp 3.2.0, edition 2024, workspace `rust-version = "1.88"`, `rust-toolchain.toml` channel 1.96 [C: modelcontextprotocol/rust-sdk Cargo.toml and rust-toolchain.toml, main, fetched 2026-09-03]. Mandatory dependencies include `tokio` (features `sync`, `macros`, `rt`, `time`), `tokio-util`, `futures`, `serde`/`serde_json`, `thiserror`, `indexmap`, `tracing`, `pin-project-lite`, `chrono` [C: crates/rmcp/Cargo.toml]. Feature-gated transports: `transport-io` (stdio via `tokio/io-std`), `transport-child-process`, `transport-streamable-http-server` (+ `-session`, `server-side-http` with `http`, `http-body`, `sse-stream`, `tower`, `rand`, `uuid`), `transport-streamable-http-client` (+ `-reqwest`, `-unix-socket` via `hyper`/`hyper-util`), `transport-worker`, `auth` (oauth2 crate), `request-state` (HMAC-SHA256 seal/open for MRTR `requestState`), `elicitation`, `schemars` [C: crates/rmcp/Cargo.toml]. The README describes it as "An official Rust Model Context Protocol SDK implementation with tokio async runtime" [C: rust-sdk README].
- Arc and tokio coupling, from `crates/rmcp/src/service.rs` (10 `Arc<` occurrences): `Peer` holds `request_id_provider: Arc<dyn RequestIdProvider>`, `progress_token_provider: Arc<dyn ProgressTokenProvider>`, `info: Arc<std::sync::RwLock<Option<Arc<R::PeerInfo>>>>`, `client_request_metadata: Arc<OnceLock<ClientRequestMetadata>>`, `request_metadata_required: Arc<AtomicBool>`, `subscription_channels: Arc<std::sync::RwLock<SubscriptionChannelMap<..>>>`; `RunningService { service: Arc<S>, handle: Option<tokio::task::JoinHandle<QuitReason>> }`; `type ProgressTimeoutWatchers = Arc<tokio::sync::RwLock<HashMap<ProgressToken, mpsc::Sender<()>>>>`; request plumbing is `tokio::sync::oneshot`/`mpsc`, `tokio::task_local!`, `tokio::select!`, `tokio::time::timeout`, `tokio::task::JoinSet`, and `tokio::spawn` (or `spawn_local` under the `local` feature) [C: rmcp service.rs, main, fetched 2026-09-03]. Consequence: rmcp cannot be hosted on a non-tokio runtime, and its `Peer`/`RunningService` handles are Arc-based by construction; neither is compatible with slates' "no Arc unless unavoidable, shared-nothing, own runtime" rules without a shim task that owns a tokio runtime just for MCP.
- What an own minimal 2026-07-28 server needs (derived from the normative pages cited above): newline-delimited JSON-RPC codec (no batch); `_meta` validation (missing required fields is `-32602`; unsupported version is `-32022` with `supported[]`; missing client capability is `-32021`); `server/discover`; `tools/list`, `tools/call`, `resources/list`, `resources/templates/list`, `resources/read`, `prompts/list`, `prompts/get`; opaque cursors; `ttlMs`/`cacheScope` on list/read/discover results; `resultType` on every result; `notifications/cancelled` handling; optional `progressToken` support; optional `subscriptions/listen` with acknowledgment and `subscriptionId` correlation; error-code discipline (-32020..-32099 reserved). The Streamable HTTP binding adds one POST route with `Accept` negotiation, `MCP-Protocol-Version`/`Mcp-Method`/`Mcp-Name` validation with Base64 sentinel decoding, JSON-or-SSE responses, `Origin` checking, and stream-close-as-cancel. Dual-era support (needed while legacy clients exist, see 2.1.1 matrix) adds the `initialize`/`initialized` handshake, `ping`, `Mcp-Session-Id` minting and DELETE, the GET SSE stream, `resources/subscribe`/`unsubscribe`, `logging/setLevel`, and `-32002` for missing resources [B: MCP 2025-11-25 and 2026-07-28 transports/versioning pages]. Validation exists: the conformance `--requirements 2025-11-25,2026-07-28` run and `server-stateless` (>20 checks) give a frozen acceptance test for both eras [C: conformance README].

### 2.2 Skills: the Anthropic format, the open spec, install locations, packaging, and "skills over MCP"

Definitions. An "Agent Skill" is a directory whose `SKILL.md` carries YAML frontmatter (metadata) followed by Markdown instructions, optionally with `scripts/`, `references/`, and `assets/`. "Progressive disclosure" is the three-tier loading rule: only name and description at session start, the `SKILL.md` body on activation, bundled files only when referenced.

#### 2.2.1 Anthropic's Agent Skills format (platform docs, fetched 2026-09-03)

- Required frontmatter: `name` (max 64 characters; lowercase letters, numbers, hyphens only; no XML tags; "Cannot contain reserved words: 'anthropic', 'claude'") and `description` (non-empty; max 1,024 characters; no XML tags; "must include both what the Skill does and when Claude should use it") [B: platform.claude.com Agent Skills overview].
- Loading levels and token costs, quoted from the overview table: Level 1 metadata "Always (at startup)", "~100 tokens per Skill"; Level 2 instructions "When Skill is triggered", "Under 5k tokens"; Level 3+ resources "As needed", "None until accessed" — "Scripts run through bash, and only their output enters context" [B: overview]. Best practices: "Keep SKILL.md body under 500 lines"; write descriptions in third person; gerund names (`processing-pdfs`); references one level deep; a table of contents for reference files longer than 100 lines; forward slashes only; "no 'voodoo constants'" (Ousterhout) in bundled scripts; evaluation-driven authoring with at least three evaluations [B: platform.claude.com best-practices].
- MCP inside skills: "If your Skill uses MCP (Model Context Protocol) tools, always use fully qualified tool names ... Format: `ServerName:tool_name`" [B: best-practices, "MCP tool references"].
- Where skills run: Claude API (upload via `/v1/skills`, reference `skill_id` in the `container` parameter together with the code execution tool; "No network access"; workspace-wide), Claude Code (filesystem: `~/.claude/skills/` personal, `.claude/skills/` project, plus plugins; "Full network access"), claude.ai (zip upload per user). "Custom Skills do not sync across surfaces" [B: overview, "Where Skills work" and "Limitations"].
- Relationship to MCP stated by Anthropic: skills "complement Model Context Protocol (MCP) servers by teaching agents more complex workflows that involve external tools and software" (engineering post of 2025-10-16, updated 2025-12-18 to note that Agent Skills became an open standard) [B: Anthropic engineering, "Equipping agents for the real world with Agent Skills"].

#### 2.2.2 The open Agent Skills specification (agentskills.io, fetched 2026-09-03)

- Frontmatter table: `name` (required; 1-64 chars; lowercase alphanumerics and hyphens; no leading, trailing, or consecutive hyphens; "Must match the parent directory name"), `description` (required; 1-1024 chars), `license` (optional), `compatibility` (optional; 1-500 chars; environment requirements), `metadata` (optional; string-to-string map), `allowed-tools` (optional; space-separated; "Experimental. Support for this field may vary") [B: agentskills.io/specification].
- Body: "There are no format restrictions"; optional directories `scripts/`, `references/`, `assets/`; "Keep your main SKILL.md under 500 lines"; progressive disclosure: metadata "~100 tokens", instructions "< 5000 tokens recommended", resources "as needed"; keep file references one level deep; validation with the reference library: `skills-ref validate ./my-skill` [B: agentskills.io/specification].
- Implementer guidance (for a client, and for how slates should expect to be read): catalog tier "~50-100 tokens per skill"; scan `<project>/.<client>/skills/`, `<project>/.agents/skills/`, `~/.<client>/skills/`, `~/.agents/skills/`, and "Some implementations also scan `.claude/skills/`"; "project-level skills override user-level skills"; gate project skills on workspace trust; catalog as an `<available_skills>` block with `name`, `description`, `location`; activation by file read or an `activate_skill` tool (constrain `name` to an enum); protect skill content from context compaction; optional subagent delegation [B: agentskills.io "How to add skills support to your agent"].
- Adoption (client showcase on 2026-09-03 lists 46 products): Claude Code, Claude, ChatGPT & Codex, Cursor, Gemini CLI, GitHub Copilot, VS Code, JetBrains Junie, OpenCode, OpenHands, Goose, Amp, Letta, Factory, Kiro, Roo Code, Mistral Vibe, Spring AI, Tabnine, Databricks Genie Code, Snowflake Cortex Code, Pulumi Neo, Hermes Agent, OpenClaw, Mux, Emdash, Superconductor, Piebald, TRAE, Qodo, Laravel Boost, and others [B: agentskills.io/clients].

#### 2.2.3 Where skills are installed, per agent

- Claude Code: Enterprise (managed settings), Personal `~/.claude/skills/<skill-name>/SKILL.md`, Project `.claude/skills/<skill-name>/SKILL.md`, Plugin `<plugin>/skills/<skill-name>/SKILL.md`; legacy `.claude/commands/<name>.md` files are equivalent ("Custom commands have been merged into skills"). Claude Code "follow[s] the Agent Skills open standard" and extends it with `when_to_use`, `argument-hint`, `arguments`, `disable-model-invocation`, `user-invocable`, `allowed-tools`, `disallowed-tools`, `model`, `effort`, `context: fork`, `agent`, `background`, `hooks`, `paths`, `shell`; `license` and `compatibility` are "accepted but not acted on"; outside Claude Code "you can use only the fields in the Agent Skills spec". Dynamic context injection runs `` !`command` `` before the model sees the body; substitutions include `$ARGUMENTS`, `${CLAUDE_SKILL_DIR}`, `${CLAUDE_PROJECT_DIR}`, `${CLAUDE_PLUGIN_ROOT}`. Budget rules: the skill listing budget "scales at 1% of the model's context window" (`skillListingBudgetFraction`), the combined `description` + `when_to_use` text is truncated at 1,536 characters, and after auto-compaction each re-attached skill keeps its first 5,000 tokens within a combined 25,000-token budget; a `.claude-plugin/plugin.json` inside a skill folder turns it into a plugin that "can bundle agents, hooks, and MCP servers" [B: code.claude.com/docs/en/skills, fetched 2026-09-03].
- OpenAI Codex: follows "the open agent skills standard from agentskills.io"; scans `.agents/skills` in the cwd, parent folders, and repo root, `~/.agents/skills`, `/etc/codex/skills`, and built-ins; optional `agents/openai.yaml` (`allow_implicit_invocation`, default true); explicit invocation `$skill-name`; the initial skills list is limited "to approximately 2% of context window or 8,000 characters" [B: OpenAI Codex skills docs (developers.openai.com/codex/skills, redirecting to learn.chatgpt.com/docs/build-skills), fetched 2026-09-03].
- Cursor: `.agents/skills/` and `.cursor/skills/` (project), `~/.agents/skills/` and `~/.cursor/skills/` (user), plus legacy `.claude/skills/` and `.codex/skills/`; optional `paths` globs; recursive scan; nested project skills are scoped to their package [B: cursor.com/docs/context/skills].
- Gemini CLI: precedence built-in < extension < user (`~/.gemini/skills/` or `~/.agents/skills/`) < workspace (`.gemini/skills/` or `.agents/skills/`), `.agents/skills/` winning within a tier; "Based on the Agent Skills open standard"; activation through an `activate_skill` call with a UI confirmation [B: geminicli.com/docs/cli/skills].
- Cross-client conclusion: `.agents/skills/<name>/` (project) and `~/.agents/skills/<name>/` (user) are read by Codex, Cursor, Gemini CLI, and are the convention the spec's implementer guide recommends; `.claude/skills/` is read by Claude Code and, for compatibility, Cursor [B: sources above].

#### 2.2.4 Plugin and marketplace packaging (Claude Code)

- A plugin is a directory with an optional `.claude-plugin/plugin.json` (`name` doubles as the skill namespace, `description`, optional `version`, `author`, `homepage`, `repository`, `license`) and components at the plugin root: `skills/<name>/SKILL.md`, `commands/`, `agents/`, `hooks/hooks.json`, `.mcp.json`, `.lsp.json`, `monitors/monitors.json`, `bin/` (added to the Bash tool's PATH), `settings.json`; plugin skills are invoked as `/plugin-name:skill-name`; a single-skill plugin may place `SKILL.md` at the plugin root; local testing with `claude --plugin-dir ./my-plugin` (also accepts a `.zip`) or `--plugin-url`; `claude plugin validate ./plugin` [B: code.claude.com/docs/en/plugins].
- Marketplace: `.claude-plugin/marketplace.json` with `name`, `owner {name, email?, url?}`, `plugins[] {name, source, description?, version?, ...}`; sources: relative path, `{"source":"github","repo":"owner/repo","ref"?,"sha"?}`, `{"source":"url","url":"...git"}`, `{"source":"git-subdir",...}`, `{"source":"npm","package":"@org/plugin","version":"2.0.0"}`, `{"source":"archive","url":"...","sha256":"..."}` (v2.1.224+), `{"source":"command",...}` (v2.1.229+); users run `/plugin marketplace add owner/repo`; enterprise controls `strictKnownMarketplaces`, `extraKnownMarketplaces`, `enabledPlugins`; Anthropic runs `claude-plugins-official` (curated) and `anthropics/claude-plugins-community` (submissions) [B: code.claude.com/docs/en/plugin-marketplaces; plugins docs].
- Plugin-bundled MCP servers use `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}`, `${CLAUDE_PROJECT_DIR}` placeholders and their tools are named `mcp__plugin_<plugin-name>_<server-name>__<tool-name>`; the `npm` marketplace source means the same npm package that ships the TypeScript SDK can be the plugin artifact [B: code.claude.com/docs/en/mcp; plugin-marketplaces].

#### 2.2.5 What "skills over MCP" can mean, concretely

- (a) Skill documents as MCP resources. Resources carry `uri`, `name`, `title`, `description`, `mimeType`, `size`, `annotations {audience, priority, lastModified}`; contents are `text` or base64 `blob`; templates use RFC 6570 (`skill://{name}/{path}`); `resources/read` on a directory-like URI may return several contents; the spec explicitly allows `file://`-style resources that "do not need to map to an actual physical filesystem" with `inode/directory` for directories, and custom schemes per RFC 3986 [B: MCP 2026-07-28 server/resources]. In Claude Code the user pulls a resource into context with `@server:scheme://path` [B: Claude Code MCP docs]. Markdown skill bodies are `text/markdown`; the spec does not define a skill-specific MIME type (gap, see section 5).
- (b) Skills as MCP prompts. `prompts/get` returns `messages[]` (user/assistant roles; text, image, audio, `resource_link`, embedded resource content); prompts are "user-controlled ... For example, as slash commands"; Claude Code maps them to `/mcp__<server>__<prompt>` [B: MCP 2026-07-28 server/prompts; Claude Code MCP docs]. A prompt can embed the skill body directly or return a `resource_link` to (a).
- (c) Tools that return instructions. Tool results are `content[]` (text blocks with optional `audience`/`priority` annotations) plus optional `structuredContent`; the model-controlled path means the model can ask for guidance itself; the spec's "Stateful Tools" guidance (opaque handle returned from a creation tool and echoed on later calls) is the same handle discipline slates needs for volumes [B: MCP 2026-07-28 server/tools]. No official document prescribes "tools that return skills"; this is a pattern, not a standard (flagged).
- Anthropic's published guidance on combining the two: skills "complement" MCP by teaching multi-tool workflows [B: Skills engineering post]; skill text must reference MCP tools as `ServerName:tool_name` [B: best-practices]; "Code execution with MCP" (2025-11-04) presents MCP servers as code APIs in a filesystem tree the agent explores, reports one worked example going "from 150,000 tokens to 2,000 tokens ... 98.7%" (that example only), and ties it to skills: the agent can "persist their own code as reusable functions" with a `SKILL.md` [B: Anthropic engineering, code-execution-with-mcp]; "Advanced tool use" (2025-11-24) measured, in Anthropic's internal tests, a five-server MCP setup (GitHub, Slack, Sentry, Grafana, Splunk) dropping from ~55K to ~8.7K tokens (85%) with the Tool Search Tool and `defer_loading: true`, accuracy "Opus 4 improved from 49% to 74%, and Opus 4.5 improved from 79.5% to 88.1%", programmatic tool calling 43,588 to 27,297 tokens (37%) "on complex research tasks", and tool-use examples 72% to 90% on complex parameter handling [B: Anthropic engineering, advanced-tool-use]. Claude Code's tool search is "enabled by default" and defers MCP tool loading until first use [B: Claude Code MCP docs].
- Practical constraints that shape the recommendation: Claude Code caps MCP tool output at 25,000 tokens by default (warning at 10,000; `MAX_MCP_OUTPUT_TOKENS`; per-tool `_meta["anthropic/maxResultSizeChars"]`) [B: Claude Code MCP docs]; the skills listing budget is 1% of context and description text is capped at 1,536 characters [B: Claude Code skills docs]; SKILL.md bodies should stay under 5,000 tokens / 500 lines [B: agentskills.io; platform docs]. A resource or prompt that returns a whole skill body therefore fits comfortably inside a single MCP result.

### 2.3 Python SDK with async

- Options: (a) pure Python over a local transport (asyncio streams): each request pays a socket round trip (5-30 µs) plus Python call overhead, so it cannot meet the provisioning target but is trivially portable; (b) a PyO3 extension exposing the shared-memory ring directly, with completions delivered on a file descriptor the event loop awaits (`loop.add_reader` on Unix; a socket on Windows because `ProactorEventLoop` does not support `add_reader` and `SelectorEventLoop` accepts only sockets) [B: asyncio platform docs, fetched 2026-09-04]; (c) `pyo3-async-runtimes`, which requires a Rust async runtime (tokio or async-std) inside the extension [C: pyo3-async-runtimes docs]. vorpal's precedent is a Rust-owned thread pool plus `loop.call_soon_threadsafe` with no tokio [C: survey-vorpal.md §7.2].
- Free-threaded Python: "Since version 0.23, PyO3 supports building Rust extension modules for the free-threaded Python build"; "Since PyO3 0.28, PyO3 defaults to assuming Python modules created with it are thread-safe" (opt out with `gil_used = true`); `#[pyclass]` data is protected by runtime borrow checking, which can raise under concurrent access; "The free-threaded build uses a completely new ABI and there is not yet an equivalent to the limited API for the free-threaded ABI", so free-threaded wheels are version-specific (`cp314t`) [B: PyO3 guide, free-threading, fetched 2026-09-04].
- abi3: one wheel per OS/arch for all Python versions from the minimum; costs: "PyO3 can't use optimizations which rely on being compiled against a known exact Python version", and the buffer API needs 3.11+; the guide recommends an `abi3` wheel for the minimum version, a `cp314t` wheel for free-threaded 3.14, and an `abi3t` wheel with 3.15 [B: PyO3 guide, building and distribution, fetched 2026-09-04].
- Decision inputs: Python floor 3.12 (the author's other projects; the buffer API under abi3 needs 3.11+ so zero-copy reads into `memoryview` work); wheels: `abi3-py312` for GIL builds, `cp314t` for free-threaded; type stubs and `py.typed`; a sync facade that runs the same ring protocol without an event loop; published with maturin via uv.

### 2.4 TypeScript SDK with async

- Node-API is "ABI stable across versions of Node.js"; Node-API 9 covers v18.17+/20.3+/21+, version 10 covers v22.14+/23.6+ [B: Node-API docs, fetched 2026-09-04]. napi-rs 3.x provides `AsyncTask` on the libuv threadpool and `ThreadsafeFunction`; `napi_get_uv_event_loop` returns the libuv loop pointer so an addon can register a `uv_poll_t` on the completion socket and resolve a Promise on readiness (libuv's poll handle requires a socket on Windows) [B: Node-API docs; C: libuv docs (from memory, verify `uv_poll` platform notes)]. External buffers (`napi_create_external_buffer`/`arraybuffer`) give zero-copy views with a finalizer; some embedders (Electron) disallow them, so a copying fallback is required [B: Node-API docs, from memory].
- Packaging: platform packages via `optionalDependencies` exactly as vorpal does (napi-rs conventions, `os`/`cpu`/`libc` fields, postinstall hard link, OIDC publishing) [C: survey-vorpal.md §1.5, §7.1]; Node floor: the oldest active LTS at release (Node 20 is in maintenance until April 2026, Node 22 active; the floor is therefore 22 at the time of writing, revisited per release) [C: Node release schedule, from memory]; Bun and Deno implement Node-API with documented gaps (verify per release); a pure-TS fallback over the control channel (Unix socket path on Linux/macOS or `\\.\pipe\` on Windows via `net.connect`) exists for environments without native addons at socket-round-trip latency; ESM and CJS dual packaging; Promises, `AbortSignal`, and async iterators as the idioms.

### 2.5 Local rendezvous and security without disk entries

Decided in `low-latency-ipc-and-runtime.md` §4: Linux abstract-namespace `AF_UNIX` + `SO_PEERCRED` + `SCM_RIGHTS`; macOS `shm_open` object (kernel namespace, mode 0600) and `os_sync_wait_on_address`, with `getpeereid`/`LOCAL_PEERTOKEN` on an optional control socket; Windows `Local\` section and events with DACLs and `GetNamedPipeClientProcessId` on the optional control pipe; discovery by `SLATES_ENDPOINT` then the per-user well-known name; multi-user machines are isolated by uid/SID in the names and by the peer credential check; a rendezvous file served from inside the mounted VFS (RAM) is the cross-platform last resort. Precedents: Docker's daemon socket and named pipe with docker-py/dockerode, EdenFS's Thrift over a Unix socket [C: docker docs; C: EdenFS].

### 2.6 API conventions across the three SDKs

- Idempotent operations with client-supplied request ids (RIFL) so retries return the original result; a structured error taxonomy modeled on gRPC status codes (INVALID_ARGUMENT, NOT_FOUND, ALREADY_EXISTS, PERMISSION_DENIED, RESOURCE_EXHAUSTED for ENOSPC/quota, FAILED_PRECONDITION for stale leases, ABORTED, UNAVAILABLE, DEADLINE_EXCEEDED) with a POSIX errno field where an OS error is the cause [B: gRPC status codes doc]; streaming results as async iterators (directory listings, archive export as a byte stream); cancellation and deadlines on every call; one vocabulary everywhere: volume, snapshot, clone, attach, detach, archive, restore, destroy, resize; protocol versioning with append-only evolution and an explicit major; docstrings with the same example in Rust, Python, and TypeScript.

## 4. Recommendation for slates

- **MCP layer**: own, minimal implementation on our runtime (vorpal's pure `handle_line` shape) speaking the 2026-07-28 stateless protocol (`server/discover`, per-request `_meta`, `resultType`, `ttlMs`/`cacheScope`, `subscriptions/listen`) with dual-era support for legacy `initialize` clients for at least the 12-month deprecation window; transports: stdio (newline-delimited JSON) and Streamable HTTP bound to 127.0.0.1 with Origin validation; validated with the official conformance suite (`--requirements 2025-11-25,2026-07-28`, `server-stateless`). Runner-up: rmcp (tokio and `Arc` throughout; would need a tokio runtime hosted in a shim task).
- **Tool catalog** (façade-first, one closed action set per skill): `slates.volume` (create, clone, snapshot, list, stat, resize, destroy), `slates.attach` (attach with chosen path, detach, list attachments), `slates.archive` (archive, restore, export as resource_link), `slates.fs` (read, write, list, move, delete for agents without a shell), `slates.status` (health, capacity, locked bytes, machine profile); every tool annotated with `readOnlyHint`/`destructiveHint`/`idempotentHint`; results carry `structuredContent` with stable codes; volume handles are explicit opaque ids echoed on every call (the spec's stateful-tool guidance).
- **Skills over MCP**: the raw `SKILL.md` documents (Agent Skills spec fields only, plus Claude Code extensions in a separate file) are exposed as `skill://slates/<name>/SKILL.md` resources (`text/markdown`) and as `prompts/list` entries returning the skill body, and the `slates.help` tool returns the same body on request; one source directory generates all three; skills also install to `.agents/skills/` and `.claude/skills/` (project) and the user equivalents through `slates skills install`, and ship as a Claude Code plugin with the bundled MCP server.
- **Python SDK**: PyO3 extension with the ring + fd completion design, `abi3-py312` and `cp314t` wheels, asyncio/uvloop/trio support through fd readiness, a sync facade, stubs and `py.typed`, maturin + uv publishing. Runner-up: pure Python over the control socket (kept as fallback).
- **TypeScript SDK**: napi-rs addon with `uv_poll` completion and external-buffer zero-copy reads (copy fallback), platform packages, Node 22 floor, ESM/CJS, pure-TS fallback over the control channel.
- **Rendezvous and API conventions**: as in §2.5 and §2.6.

## 5. Risks and unknowns

- The MCP spec is moving quickly (a stateless redesign in 2026-07-28); the conformance suite is the protection.
- `uv_poll` on Windows requires sockets; Electron forbids external buffers; both handled by fallbacks.
- PyO3 free-threaded ABI has no limited-API equivalent yet; version-specific wheels are required for `t` builds.
- The Node LTS floor and Bun/Deno Node-API status are from memory; verify at release time.
