# Sub-50-microsecond provisioning: local IPC, wake primitives, shared memory, and the async runtime

Research memo for slates. Date: 2026-09-03. Status: work in progress (sections are appended as they are finished).

Evidence tiers used throughout:
- [A] peer-reviewed paper (OSDI/SOSP/NSDI/ATC/EuroSys/ASPLOS/PPoPP/PACT/SIGCOMM, ACM TOCS) or PhD thesis
- [B] textbook, standard, or official kernel/vendor documentation
- [C] widely deployed implementation or its design document
- [D] blog post or individual benchmark (gap-filler only)

Every number is given with its platform and conditions; anything without a measured source is marked MUST-MEASURE.

## 1. Questions answered

1. What does the latency budget look like, from measured numbers, for every kernel and hardware primitive a provisioning request could touch (syscall entry/exit with and without mitigations, futex/eventfd/pipe wakes, Unix-domain and TCP-loopback round trips, io_uring submission modes, context switches, cross-core cache-line transfers, minor page faults), on Linux, macOS (Apple silicon) and Windows?
2. Which IPC designs demonstrably reach well under 50 µs end-to-end, what wake strategy do they use, and which cross-platform primitives exist for waiting on a shared-memory word, creating shared memory without a disk-backed file, rendezvous without a filesystem entry, and authenticating the peer? Which primitives create filesystem entries on each OS and which do not?
3. Which async runtime should the daemon use: tokio, glommio, monoio, compio, an embassy-style static executor, or a custom thread-per-core executor with arena-slot wakers (and how big is the custom option)?
4. What does a "create volume" request actually cost, step by step, once the wake is paid, and what should be pre-allocated and NUMA-placed at daemon start so that the wake dominates the budget?
5. How expensive is launching a tool process (fork/vfork/posix_spawn/CreateProcess), why must the daemon stay off that path, and how would an optional Linux launcher build a private mount namespace?
6. How do Python asyncio and Node/libuv clients await a completion without a Rust async runtime in the client, and what does each event loop support per OS?

Short answers (details and citations follow in Section 2, numbers in Section 3, decision in Section 4):

- The only primitives that fit inside a 50 µs end-to-end budget with margin are shared-memory rings polled by a spinning core (sub-microsecond) or a spin-then-park scheme whose park/unpark path is a single futex-class wake (single-digit microseconds when the target core is not in a deep idle state). Every socket, pipe or named-pipe round trip costs 5-30 µs by itself on measured systems and is unusable for the hot path, though fine for one-time rendezvous.
- Per OS: Linux = memfd + abstract-namespace AF_UNIX rendezvous + shared (non-private) futex; macOS = POSIX shm_open object (kernel namespace, no filesystem entry) + os_sync_wait_on_address with the SHARED flag (public since macOS 14.4) with __ulock_wait as an unsupported fallback; Windows = pagefile-backed section in the Local\ kernel-object namespace + named auto-reset Event for cross-process wake, because WaitOnAddress/WakeByAddress are process-local by documented contract.
- Runtime: build a small custom thread-per-core executor (arena task slots, RawWakerVTable pointing at slots, one io_uring/kqueue/IOCP driver per core, cross-thread wakes through a bounded MPSC queue plus a driver kick). None of the existing crates satisfies "no Arc, no work stealing, io_uring + kqueue + IOCP, ring integration" at once; compio is the closest runner-up and monoio the second.
- Fast path: parse fixed-layout message (tens of ns) -> pop a pre-sized slab slot (tens of ns) -> insert into a pre-sized single-writer hash table (about 100-400 ns) -> publish by one release-store of a pointer (tens of ns) -> write completion sequence (one cache-line transfer, about 50-150 ns) -> wake. The wake is 10-100x the rest, so the design goal is "never park the daemon core while a client is active" and "the client spins for the measured wake cost before parking".
- Process launch is 0.5-2 ms even in the best case (posix_spawn) and grows with parent size for fork; it must be done by the SDK process itself, never by the daemon; the optional Linux namespace launcher pays unshare + bind-mount costs that have no citable measurement and must be measured.
- SDK completion is an fd (eventfd on Linux, a pipe or socketpair on macOS, a loopback socket on Windows) so asyncio's add_reader and libuv's uv_poll can await it; on Windows asyncio's default ProactorEventLoop cannot add_reader at all and libuv can only poll sockets, so the Windows completion object must be a socket.

## 2. Findings by sub-question

Terms used below. Syscall: a user-to-kernel-and-back transition. Mitigations: kernel patches for Meltdown/Spectre (KPTI = separate kernel page tables, retpoline = indirect-branch thunks). Futex: a kernel wait queue keyed by a user-space word, so the uncontended path needs no syscall. Wake latency: the time from the waker's syscall to the sleeping thread executing again. UDS: Unix-domain socket. RTT: round-trip time. Cache-line transfer: the coherence protocol moving a 64-byte line between cores. NUMA: non-uniform memory access (different memory latency per socket/node). Minor page fault: a trap that maps an already-resident or zero page into the address space. Thread-per-core: one OS thread pinned per core, each owning its data, communicating only by message passing (Seastar's "shared-nothing").

### 2.1 Sub-question 1: the latency budget from measured numbers

Syscall entry/exit.
- Ren et al. measured 41 Linux versions (3.0 to 4.20, Ubuntu default config) on a 2.40 GHz Intel Xeon with LEBench and attribute most of a multi-year slowdown to 11 root causes; the Meltdown patch (KPTI) costs two page-table-pointer swaps per kernel round trip, a constant of about 400 cycles (about 170 ns at 2.4 GHz), plus two TLB flushes whose cost was 700-6000 cycles in their read tests; the Spectre patch (retpoline) costs about 30-35 cycles per indirect branch and hits select/poll/epoll hardest; a misconfigured "forced context tracking" added 200-300 ns to every kernel entry/exit in some releases. [A: Ren SOSP'19 slides] The paper's summary numbers are an average 22% KPTI slowdown across their microbenchmarks (63% on recv, 59% on read) and 66% average retpoline slowdown on select/poll/epoll. [D summary of A: Colyer 2019 on Ren SOSP'19]
- A user-kernel round trip for a trivial syscall (getuid) measured 78 ns with mitigations disabled versus 239 ns with them enabled on the same Xeon Gold 6256 (kernel 3.10, RHEL 7); 464 ns on a Xeon E5-2643 v2 with mitigations; 560 ns on a Core i5-4250U with kernel 5.12 and mitigations; clock_gettime via the vDSO is 13-24 ns because it never enters the kernel. [D: gms.tf 2021]
- KPTI overhead depends on syscall rate: 1% to over 800% across workloads; PCID support (Linux 4.14) cuts the TLB-walk share of cycles from 2.91% back to 0.22% in the author's 100 MB working-set test. [D: Gregg 2018]
- FlexSC (Soares and Stumm) established that the indirect cost of a syscall, cache and TLB pollution that lowers user-mode instructions-per-cycle after the call returns, can exceed the direct mode-switch cost; USENIX returned HTTP 403 to our fetcher for the PDF, so its exact figures are not reproduced here and should be pulled by hand before being quoted. [A: FlexSC OSDI'10, not retrieved]
- On the 2009 AMD Opteron 8380 used for Barrelfish, a trap costs about 800 cycles and an IPI-plus-context-switch wake ("C") about 6000 cycles, i.e. about 2.4 µs at 2.5 GHz. [A: Baumann SOSP'09]

Implication for slates: a single syscall is 0.1-0.6 µs on current x86 Linux with mitigations, which is affordable inside a 50 µs budget; what is not affordable is a chain of them plus a scheduler wake on each side. Apple silicon and Windows syscall costs have no citable measurement in this research and are MUST-MEASURE items (Section 5).

Context switch, futex/eventfd wake, and thread wake in practice.
- Shenango parks a runtime kthread with a blocking read on an eventfd and unparks it by writing to that eventfd; the IOKernel reallocates cores every 5 µs and a core reallocation completes in 5.9 µs using under 2 µs of IOKernel CPU time; waking a kthread and preempting one each add "only a few µs" to a packet RTT (their Figure 6). Hardware: Intel Xeon E5-2650 v4, Ubuntu 18.04, Linux 4.15.0. [A: Ousterhout NSDI'19]
- Caladan's scheduler core decides every 10 µs and converges in about 20 µs; it identifies "sending IPIs" as one of the most expensive operations both Linux and its KSCHED module perform, and amortizes them with multicast IPIs; each per-core shared-memory control region is a single 64-byte cache line because mwait monitors one line. Hardware: 2x12-core Xeon Broadwell, Linux 5.2.0/5.4.0 (modified). [A: Fried OSDI'20]
- Snap's interrupt-driven ("spreading") scheduler shows "remarkably worse latency" at low request rates than its spin-polling ("compacting") scheduler because an interrupt may target a core in a deep C-state; the compacting scheduler avoids the wake cost by spin-polling on one core and expanding only under load. Hardware: Intel Skylake servers, 100 Gbps NICs. [A: Marty SOSP'19]
- LMAX measured 32,757 ns mean latency per hop through a blocking ArrayBlockingQueue (a park/unpark per message) versus 52 ns through the Disruptor ring on an Intel Core i7-2720QM at 2.2 GHz (Java, 2011). This is the cleanest published "blocking wake versus polled ring" comparison. [C: LMAX Disruptor technical paper]
- On Linux 6.15/6.17 with a 3.7 GHz AMD server, waking an idle io_uring SQPOLL kernel thread "introduces a non-trivial latency of roughly 30 µs", and operations that fall back to io_worker threads add about 7.3 µs on average versus inline execution; an 8-byte network ping-pong with DEFER_TASKRUN plus NAPI busy-poll reaches about 8-9 µs one way. [D (arXiv preprint): io_uring for DBMSs 2025]
- The direct cost of a thread context switch and its indirect cache-perturbation cost were separated by Li, Ding and Shen; the PDF was not retrievable in this session (404/403), so no figure is quoted; their qualitative result, that the indirect cost can dominate the direct cost for large working sets, is what matters for a daemon that must keep its working set hot. [A: Li ExpCS'07, not retrieved]

Implication: every published system that reaches single-digit microseconds either never sleeps the hot core (Snap dedicated/compacting, Shenango IOKernel, Caladan scheduler core, Disruptor busy-spin) or accepts that the first wake after idleness costs 5-30 µs. A daemon that parks its provisioning core cannot promise 50 µs on the first request after idle unless the client spins for the response.

eventfd, pipes, Unix-domain sockets and TCP loopback.
- eventfd is an 8-byte counter file descriptor usable with poll/select/epoll (and io_uring) and is documented as the lower-overhead replacement for a pipe used purely for signalling. [B: eventfd(2)]
- A Red Hat performance-team IPC benchmark on RHEL 9.6 reports Unix-domain socket one-way latency of 2-10 µs (example p95 5.21 µs, p99 8.43 µs), TCP localhost 5-20 µs, and POSIX message queues 5-15 µs; hardware not specified. [D: rusty-comms]
- A macOS throughput benchmark (hardware unspecified) reports 5.36 million 64-byte messages/s through shared memory (about 0.19 µs per message), 304 K/s through a pipe (about 3.3 µs) and 157 K/s through a Unix-domain socket (about 6.4 µs); these are throughput reciprocals, not latency, and the CPU is not stated. [D: brylee10 unix-ipc-benchmarks]
- Microsoft's own 64-byte TCP-loopback echo test on a 6-core 3.2 GHz AMD desktop: mean RTT 27 µs (Server 2008 R2, IOCP), 17 µs (Server 2012, IOCP), 12 µs (Server 2012, IOCP + SIO_LOOPBACK_FAST_PATH), 9 µs (RIO polling) and 3 µs (RIO polling + fast path, jitter within +/-319 ns). [B: Microsoft 2012 loopback fast path]
- Barrelfish measured a one-way L4 IPC at about 424 cycles and its own URPC at 450 cycles latency on the 2009 Opteron (Table 2). [A: Baumann SOSP'09]

Implication: any socket or pipe round trip is 5-30 µs by itself on measured systems; used once at connect time it is fine, used per provisioning request it consumes most of the budget before any work is done.

io_uring submission and completion.
- The ring design places submission (SQ) and completion (CQ) queues in memory shared between application and kernel, coordinated with head/tail indices and explicit read/write barriers; registering files avoids an atomic file-reference get/put per I/O that "can be a noticeable slowdown for high IOPS workloads", and registering buffers avoids per-I/O mapping work; on the author's test box io_uring reached about 1.7 M 4 KiB IOPS per core with polling and about 1.2 M without, versus 608 K for aio. [C: Axboe, Efficient IO with io_uring]
- Flag semantics and kernel versions: IORING_SETUP_SQPOLL (kernel thread polls the SQ, sleeps after sq_thread_idle ms and must be woken with IORING_ENTER_SQ_WAKEUP; no privileges needed since 5.13), IORING_SETUP_SINGLE_ISSUER (6.0), IORING_SETUP_DEFER_TASKRUN (6.1, requires SINGLE_ISSUER, completions are processed only when the submitting thread calls io_uring_enter with GETEVENTS), IORING_SETUP_COOP_TASKRUN (5.19, avoids IPIs/forced kernel entries), IORING_SETUP_NO_MMAP and REGISTERED_FD_ONLY (6.5), IORING_SETUP_NO_SQARRAY (6.6), IORING_FEAT_SINGLE_MMAP (5.4). [B: io_uring_setup(2)]
- The 2025 DBMS study recommends DEFER_TASKRUN with SINGLE_ISSUER as the default execution mode for low jitter, notes batching 16 operations cuts CPU cycles per operation by 5-6x, and says SQPOLL only pays off when a dedicated polling core is justified (see the 30 µs SQPOLL wake above). [D (preprint): io_uring for DBMSs 2025]

Cross-core cache-line transfer and atomic operations (the cost of one ring slot handoff).
- David, Guerraoui and Trigonakis (Table 2/3; cycles, average of 10,000 repetitions, <3% std dev): on an 8-socket Xeon E7-8867L (Westmere-EX, 2.13 GHz) a load of a line modified by another core on the same die is 109 cycles (about 51 ns), one QPI hop 289, two hops 400; a store to a modified line 115 cycles same die; CAS on a modified line 120 cycles same die, 324 one hop, 430 two hops; local LLC 44 cycles; RAM 355 cycles; a store to a line shared by all 80 cores 445 cycles. On a 4-socket Opteron 6172 (2.1 GHz): same-die 81-83 cycles, one hop 172-175, two hops 252-254, RAM 136. Their conclusions: atomics cost about the same as a store plus a memory barrier; cross-socket communication is 2-7.5x more expensive than intra-socket; the LLC round trip (44 cycles) is the fastest possible core-to-core path on the Xeon. [A: David SOSP'13]
- Molka et al. on a dual Intel Xeon X5570 (Nehalem): L1 4 cycles, L2 10 cycles, L3 38 cycles (about 13 ns); a line held exclusive by another core on the same socket costs 22.2 ns (9.2 ns snoop penalty over the L3 hit), modified lines in another core's L1/L2 25.5-28.3 ns; a line in the other socket costs 63 ns (exclusive), 58 ns (shared) and over 100 ns (modified, forces write-back); local memory 65 ns, remote memory 106 ns. [A: Molka PACT'09]
- Schweizer, Besta and Hoefler (Table 2, nanoseconds): Haswell Core i7-4770 L1 1.17, L2 3.5, L3 10.3, memory 65, CAS overhead about 4.7; Ivy Bridge Xeon E5-2697 v2 L1 1.8, L2 3.7, L3 14.5, other-socket hop 66, memory 80; AMD Opteron 6272 L1 5.2, L2 8.8, L3 30, hop 62, memory 75; Xeon Phi 7120 hop 161, memory 340. Atomics are about 5-10 ns slower than plain reads for E/M lines, remote-cache and memory accesses are over 60 ns, cross-socket about 50 ns more, and CAS costs the same as FAA/SWP (contrary to folklore). [A: Schweizer PACT'15]
- ffwd's delegation server handles a request in about 40 cycles (55 M ops/s on a 2.2 GHz core) with zero atomics; the whole design is bounded by cache-line transfer latency, about 80 ns one way between cores on one socket and about 200 ns between sockets; their Table 1 gives local versus remote LLC latency of 63/135 ns (Broadwell E5-4660), 70/177 (Sandy Bridge E5-4620), 98/185 (Westmere-EX E7-4820), 92/163 (Opteron 6378). [A: Roghanchi SOSP'17]
- Modern parts (CAS ping-pong, tier D): Sapphire Rapids intra-socket average 59 ns, worst 81 ns, cross-socket average 138 ns; Graviton 3 average 48 ns; quad-socket Skylake 47 ns intra / 150 ns cross. [D: Chips and Cheese 2023] Apple M1 Pro 40 ns within a P-cluster, 53 ns across P-clusters, 145 ns between P and E clusters; Ryzen 9 5950X 17 ns within a CCX and 85 ns across CCXs; Core i9-12900K 35-50 ns; Xeon Platinum 8375C 51 ns; SMT siblings 4.3-10 ns (reported as RTT/2). [D: nviennot core-to-core-latency] Measurements for M1 Pro through M5 Pro exist but only as plots (no extracted values); P-cores show lower latency than E-cores within their clusters. [D: hydroo macos-core-to-core-latency] macOS does not export processor binding; affinity tags are scheduler hints only, so per-core-pair numbers on macOS are statistical, not pinned. [B: Apple thread affinity release note]

Implication: one ring-slot handoff (producer writes a line, consumer reads it) is one to two cache-line transfers: 50-150 ns on one socket or one Apple cluster, 150-400 ns across sockets or across the P/E boundary on Apple silicon. A whole request-response through two rings is under 1 µs when both sides are polling.

Minor page fault.
- Ren et al. include small- and big-page-fault tests; the "fault-around" feature caused a 54% slowdown of the big-pagefault test and transparent huge pages, when absent, make some tests up to 83% slower, but the slides give no absolute per-fault figure. [A: Ren SOSP'19 slides; D summary: Colyer 2019] MAP_POPULATE prefaults a mapping's page tables at mmap time, MAP_LOCKED additionally locks it (an explicit mlock is the stronger guarantee), and MAP_HUGETLB/MFD_HUGETLB pages cannot be swapped and are reserved at boot or via nr_hugepages. [B: mmap(2); B: hugetlbpage kernel doc] The absolute minor-fault cost is a MUST-MEASURE item; the design removes it from the hot path by prefaulting and locking every ring and pool at daemon start (Section 4).

Apple silicon and Windows specifics.
- No peer-reviewed or vendor measurement of Apple silicon syscall, __ulock/os_sync wake, or Mach-message latency was found; the only Apple numbers are tier-D core-to-core plots and the nviennot M1 Pro values above. Windows has the vendor loopback RTTs above (2012 hardware) and no published WaitOnAddress/Event wake latency. All are boot-time calibration targets (Section 5).

### 2.2 Sub-question 2: IPC designs that reach under 50 µs, wake strategy, wait-on-address primitives, shared memory, rendezvous and peer authentication per OS

Designs with evidence.
- Snap (Google, in production since 2016): applications talk to the userspace networking daemon through shared-memory command and completion queues; the shared regions are set up by "exchanging tmpfs-backed file descriptors over Unix domain sockets"; an application writes a command into the command queue and then either spin-polls the completion queue or asks for a thread notification when the completion is written; engines communicate over lock-free memory-mapped regions and occasionally via "an eventfd-like construct" for interrupt-style delivery; blocking synchronization is prohibited in engines. Engine scheduling has three modes: dedicating cores (pinned, spin-polling, optional userspace mwait), spreading (interrupt-driven, subject to C-state wake latency), compacting (spin-poll on one core, grow under load). This is exactly the shape of slates' SDK-to-daemon path. [A: Marty SOSP'19]
- Demikernel: a queue-oriented datapath API (PDPIX) with explicit zero-copy buffer ownership between application and libOS, a per-I/O budget under 1 µs, about 50 ns of I/O-processing overhead per I/O achieved by the Rust libOS, coroutines that compile to plain function calls, and a central per-libOS memory allocator with reference counting for use-after-free protection. [A: Zhang SOSP'21]
- Shenango and Caladan: a dedicated scheduler core polls shared memory (Shenango every 5 µs, Caladan every 10 µs), runtimes park on an eventfd and are unparked by a write, preemption uses signals, and IPIs are the dominant cost that both systems engineer around (multicast IPIs, mwait on a single cache line). [A: Ousterhout NSDI'19; A: Fried OSDI'20]
- Barrelfish URPC: a region of shared memory carries cache-line-sized messages between one writer core and one reader core; the sender writes the line sequentially and the receiver polls the last word so a partially written line is never seen; single-message latency 450 cycles; the receiver polls for P cycles before sleeping for an IPI that costs C cycles, and with no arrival-time information P = C bounds the overhead at 2C and the latency at C. [A: Baumann SOSP'09]
- ffwd: one server core owns the data structure; each client has a private request cache line pair and clients on one socket share a response line pair; the server polls, never executes an atomic, spends about 40 cycles per request, and throughput is bounded by interconnect latency (about 80 ns intra-socket, 200 ns cross-socket one way). Delegation beats locks by up to an order of magnitude when the critical section is short. [A: Roghanchi SOSP'17]
- LMAX Disruptor: a pre-allocated power-of-two ring indexed by monotonically increasing sequence numbers, one writer per resource ("single writer principle"), padding to avoid false sharing on the sequence counters, and pluggable wait strategies (busy-spin or condition variable); mean latency per hop 52 ns versus 32,757 ns for a blocking queue. [C: LMAX Disruptor technical paper] Vyukov's bounded MPMC queue applies the same per-slot sequence idea with one CAS per enqueue/dequeue position; the 1024cores site redirected our fetcher and was not retrieved, so it is cited for the design name only. [C: Vyukov bounded MPMC, not retrieved]
- Aeron: client and media driver communicate over ring buffers in memory-mapped shared memory (on Linux typically under /dev/shm, which is a tmpfs path, i.e. a filesystem entry even though it is RAM-backed); idling uses Agrona's BackoffIdleStrategy: spin 10 times, yield 5 times, then park with exponential backoff from 1 µs to 1 ms, with the caveat that Linux coalesces timer events in a 50 µs window unless /proc/PID/timerslack_ns is lowered. [C: Aeron design overview; C: Agrona BackoffIdleStrategy]
- io_uring itself is the same pattern between user space and kernel: shared SQ/CQ rings, head/tail indices with barriers, registered buffers/files to avoid per-operation reference and mapping work. [C: Axboe io_uring]

Seqlocks (a version counter incremented before and after a write; readers retry if the counter is odd or changed) are the right publish mechanism for small, rarely-written, often-read records such as a volume's mount table entry; Boehm's paper on making them memory-model-correct (readers must use atomic loads or fences to avoid data races) could not be retrieved (ACM 403), so it is cited for the recommendation only. [A: Boehm MSPC'12, not retrieved]

Wake strategy: spin-then-park with a measured threshold.
- The spin-block problem's deterministic optimum is to spin for exactly the cost of blocking and then block; this is 2-competitive against any adversary, and randomized strategies approach e/(e-1) ≈ 1.58 against an oblivious adversary; the paper's own words: "in contrast to ... the deterministic case, which is 2". [A: Karlin, Manasse, McGeoch, Owicki SODA'90 / Algorithmica 1994] Karlin, Li, Manasse and Owicki's SOSP'91 empirical study of adaptive spinning could not be retrieved this session. [A: Karlin SOSP'91, not retrieved]
- Barrelfish restates the same rule with measured constants: poll for P = C cycles where C is the measured IPI-wake cost (about 6000 cycles on their hardware). [A: Baumann SOSP'09]
- Practice: Snap keeps hot engines spinning and only interrupt-wakes idle ones; Shenango and Caladan dedicate a spinning core; Agrona backs off spin -> yield -> park. [A: Marty SOSP'19; A: Ousterhout NSDI'19; C: Agrona]

Wait-on-address primitives per OS.
- Linux futex(2): a 32-bit, 4-byte-aligned word; FUTEX_WAIT atomically compares the word to an expected value and sleeps only if equal; FUTEX_WAKE wakes up to N waiters; FUTEX_PRIVATE_FLAG lets the kernel skip the shared-mapping key lookup, whereas shared futexes work across processes through mmap'd shared memory even when the virtual addresses differ; FUTEX_WAIT_BITSET takes absolute timeouts against CLOCK_MONOTONIC or CLOCK_REALTIME; the uncontended path never enters the kernel. [B: futex(2)] futex_waitv waits on up to 128 futexes at once (32-bit futexes only). [B: futex2 kernel doc]
- macOS os_sync_wait_on_address: atomic compare-and-wait on a 4- or 8-byte value; OS_SYNC_WAIT_ON_ADDRESS_SHARED makes it work on an address in a shared-memory region across processes, and the waker must then use OS_SYNC_WAKE_BY_ADDRESS_SHARED with the same address; without the flag the kernel applies single-process optimizations; wake-any and wake-all variants; timeout and deadline variants return ETIMEDOUT; spurious wakeups surface as EINTR and must be retried; available on macOS 14.4, iOS 17.4, tvOS 17.4, watchOS 10.4. Apple did not publish the header's documentation on its website. [B: os_sync_wait_on_address.h header; C: rust-lang/rust PR 122408] The private __ulock_wait/__ulock_wake have existed since macOS 10.12 and back this API; the Rust project declined to ship a private-API fallback without Apple's permission. [C: rust-lang/rust PR 122408]
- Windows WaitOnAddress/WakeByAddressSingle/WakeByAddressAll (Windows 8+, Synchronization.lib): waits on 1/2/4/8-byte values, may wake spuriously (low memory, abandoned wake, checked builds), and, decisively for slates, "Only a thread within the same process can be woken." [B: WaitOnAddress; B: WakeByAddressSingle] Cross-process waking therefore needs a kernel object: a named auto-reset Event (CreateEventW with a Local\ or Global\ name, or shared via DuplicateHandle/inheritance; SetEvent releases one waiter) or an I/O completion port packet, but IOCPs "are not sharable between processes". [B: CreateEventW; B: I/O completion ports; B: DuplicateHandle]

Shared memory without a disk file, and its "never touches disk" caveats.
- Linux memfd_create (3.17): an anonymous tmpfs-backed file with no mount needed, shareable by passing the fd over a Unix socket (SCM_RIGHTS, at most 253 fds per message) or by fork inheritance; MFD_ALLOW_SEALING enables F_ADD_SEALS (F_SEAL_SHRINK/GROW/WRITE etc.), MFD_HUGETLB (4.14) backs it with hugetlb pages. [B: memfd_create(2); B: unix(7); B: fcntl(2)] tmpfs pages are swappable, so hermeticity requires mlock/mlock2 (RLIMIT_MEMLOCK or CAP_IPC_LOCK; locks are not inherited across fork and a page stays locked while any process locks it) or hugetlb pages, which "cannot be swapped out under memory pressure". [B: mlock(2); B: hugetlbpage kernel doc]
- macOS shm_open: names are limited to PSHMNAMLEN = 31 characters (ENAMETOOLONG beyond that), objects persist until shm_unlink and do not survive reboot, no visible filesystem entry is created, the descriptor is FD_CLOEXEC, and the object inherits the creator's effective uid/gid and mode. [B: Apple shm_open(2); C: XNU posix_shm.h] Internally XNU backs each object with anonymous Mach memory objects created by mach_make_memory_entry_64 with MAP_MEM_NAMED_CREATE, kept in a list per object; they are ordinary pageable anonymous memory managed by the VM system (compressor/swap), so mlock is required for hermeticity. [C: XNU posix_shm.c] A memory entry is a Mach port send right that can be handed to another task in a Mach message and mapped with mach_vm_map; mach_vm_remap maps a range of another task's address space. [C: XNU mach_vm.defs]
- Windows CreateFileMapping with hFile = INVALID_HANDLE_VALUE creates a section "backed by the system paging file instead of by a file in the file system"; SEC_COMMIT (default) commits the whole range, SEC_RESERVE reserves it for later VirtualAlloc commits; SEC_LARGE_PAGES requires SeLockMemoryPrivilege, SEC_COMMIT and a size that is a multiple of GetLargePageMinimum; names live in the kernel object namespace (Local\ per session, Global\ needs SeCreateGlobalPrivilege outside session 0) and are shared by name, inheritance or DuplicateHandle (PROCESS_DUP_HANDLE on the target). [B: CreateFileMapping; B: Kernel object namespaces; B: DuplicateHandle] "Backed by the paging file" means pages may be written to disk under pressure; VirtualLock guarantees locked pages "not [be] written to the pagefile while they are locked" but is capped by the minimum working set (raise it with SetProcessWorkingSetSize), and large pages are "always resident in physical memory". [B: VirtualLock; B: Large-page support] CreateFileMappingNuma places the physical pages on a chosen node. [B: CreateFileMappingNuma]

Which rendezvous primitives create filesystem entries (must-not-write-to-disk audit).
- Linux: pathname AF_UNIX sockets create a socket inode in the filesystem; abstract-namespace sockets (sun_path[0] == 0) are "independent of the filesystem", are removed automatically when the last reference closes, and have no permission semantics, so authentication must come from SO_PEERCRED. memfd_create, futexes, eventfd and io_uring rings create nothing on disk. [B: unix(7); B: memfd_create(2)]
- macOS: shm_open objects live in a kernel namespace with no filesystem entry; Unix-domain sockets require a filesystem path (the abstract namespace is Linux-only); launchd MachServices are registered in the bootstrap namespace with no filesystem entry at runtime, but the LaunchAgent plist that declares them is a file installed once; XPC anonymous listener endpoints can only be handed over an existing connection. [B: Apple shm_open(2); B: unix(7); B: launchd.plist(5); D: HackTricks/Apple forum notes on anonymous listeners]
- Windows: named pipes are objects of the named-pipe file system rooted at \\.\pipe\ and are not persisted on disk; named Events and sections are kernel-object-namespace names; AF_UNIX sockets (Windows 10 build 17063+) create an NTFS reparse-point file at the bound path and do not support fd passing, so they are excluded. [B: Pipe names; B: Named pipes; B: CreateEventW; B (vendor blog): AF_UNIX comes to Windows]

Peer authentication.
- Linux: SO_PEERCRED returns the peer's pid/uid/gid as of connect/listen/socketpair time on connected AF_UNIX stream sockets; SO_PASSCRED delivers SCM_CREDENTIALS per message. [B: unix(7)]
- macOS: getpeereid returns the peer's effective uid/gid and is documented as reliable ("no way for either side to influence the credentials returned"); SOL_LOCAL options LOCAL_PEERCRED (0x001), LOCAL_PEERPID (0x002), LOCAL_PEEREPID, LOCAL_PEERUUID, LOCAL_PEEREUUID and LOCAL_PEERTOKEN (0x006, "retrieve peer audit token") are defined in XNU's sys/un.h. [B: getpeereid(3); C: XNU sys/un.h] For an shm_open-based rendezvous the kernel's uid/gid/mode check on the object is the authentication. [B: Apple shm_open(2)] XPC connections additionally support code-signing requirements on the peer. [B: Apple XPC documentation]
- Windows: GetNamedPipeClientProcessId (Vista+) returns the client pid of a server-side pipe instance; ImpersonateNamedPipeClient adopts the client's token (a message must be read first; check TokenImpersonationLevel); sections and events carry DACLs through SECURITY_ATTRIBUTES. [B: GetNamedPipeClientProcessId; B: Impersonating a named pipe client; B: CreateFileMapping]

Proposed rendezvous per OS (justified in Section 4).
- Linux: daemon listens on an abstract-namespace AF_UNIX socket named from (uid, daemon instance nonce); on connect it checks SO_PEERCRED uid, sends the client's per-connection memfd (rings + futex words) via SCM_RIGHTS, and both sides then only touch shared memory plus shared futexes; no filesystem entry at any point. [B: unix(7); B: memfd_create(2); B: futex(2)]
- macOS: daemon creates a shm_open object named "/sl<uid-hash>" (within 31 characters) with mode 0600 holding a bootstrap block; the client opens it, claims a slot with an atomic CAS, and both sides use os_sync_wait_on_address(SHARED) on words inside that object; no sockets, no launchd plist required for the fast path (a LaunchAgent is optional for auto-start). [B: Apple shm_open(2); B: os_sync_wait_on_address.h]
- Windows: daemon creates a pagefile-backed section "Local\slates-<sid-hash>" and a named auto-reset Event per client slot, both with a DACL restricted to the user's SID; the client maps the section, claims a slot, and wakes the daemon with SetEvent while spinning on the ring first; a named pipe is used only if a fallback control channel is needed. [B: CreateFileMapping; B: CreateEventW; B: Kernel object namespaces]


### 2.3 The async runtime decision

Requirements restated: thread-per-core with no work stealing; no `Arc` on any per-request path; completion-shaped I/O on Linux (io_uring with an epoll fallback), macOS (kqueue), Windows (IOCP); integration with our shared-memory rings and the FUSE/NFS/WinFsp drivers; a deterministic simulation driver.

- tokio: work-stealing multi-thread scheduler; tasks and I/O resources are `Arc`-managed; the runtime is `Send`-centric; vorpal keeps it at the I/O edge only and hosts it on a dedicated thread bridged by a bounded channel [C: survey-vorpal.md §2.4]. Fails the first two requirements by design.
- monoio (ByteDance): thread-per-core; "Users do not need to worry about tasks being `Send` or `Sync`"; io_uring on Linux 5.6+, epoll on older Linux, kqueue on macOS; "Experimental windows support is on the way" [C: monoio README, fetched 2026-09-04]. Fails the Windows requirement today.
- compio: "A thread-per-core Rust runtime with IOCP/io_uring/polling"; created to fill the gap monoio leaves on non-Linux platforms; no MSRV or maturity statement on the README [C: compio README, fetched 2026-09-04]. Closest existing fit; its internal ownership model would need to be audited for `Arc` on the request path, and its drivers would still need our ring integration and FUSE-over-io_uring support.
- glommio: Linux-only io_uring, `Rc`-based; not cross-platform [C: glommio docs].
- embassy-executor: statically allocated tasks and wakers built on `RawWakerVTable` pointing at task storage, no allocation, no `Arc`; designed for embedded, but its task/waker model is the proof that an executor needs no `Arc` [C: embassy-executor src/raw].
- The std contract: `RawWakerVTable` holds four function pointers taking an opaque `data` pointer; "If the `RawWaker` will be used to construct a `Waker` then these functions must all be thread-safe"; `LocalWaker` needs no thread safety; nothing requires `Arc` (reference counting "is left to the vtable implementer and must be atomic only if constructing a `Waker`") [B: std::task::RawWakerVTable docs, fetched 2026-09-04].

Decision: a custom thread-per-core executor. Each shard has a task arena (fixed-capacity slots addressed by index + generation), an intrusive run queue, a hierarchical timing wheel [A: Varghese & Lauck SOSP'87], and one driver (io_uring / epoll / kqueue / IOCP) owned by that thread. Wakers are `RawWaker`s whose data pointer encodes (shard, slot, generation); `wake` from the owning shard pushes the slot onto the local run queue; `wake` from another shard pushes (slot, generation) onto the target shard's bounded MPSC ring and kicks the driver (eventfd / `EVFILT_USER` / `PostQueuedCompletionStatus`), which is why the vtable can be thread-safe without any reference count: a stale generation is a no-op. Estimated size: executor and timers ~2 kLOC; three drivers ~1.5 kLOC each; simulation driver ~1 kLOC; total 6-7 kLOC plus tests. Runner-ups: compio (adopt if its audit shows an `Arc`-free request path and an acceptable driver seam; re-check each release), monoio (when Windows lands).

### 2.4 The provisioning fast path, decomposed

Steps for "create volume" once the request word is visible to the owning shard (budget in parentheses is the cited cost class):
1. Read the fixed-layout request from the ring slot (one cache line transfer, 50-150 ns intra-socket [A: David13; A: Schweizer15]).
2. Validate the request (bounds and enum checks, tens of ns).
3. Pop a volume record from the pre-sized volume slab (tens of ns; no allocation).
4. Insert the name into the per-shard volume-by-name index (ART insert ~100-400 cycles at catalog sizes [A: Leis13]).
5. Allocate the root directory node and the inode slot from per-volume arenas carved at boot (tens of ns).
6. Charge the quota: two integer updates on the shard (bounded volumes) or a reservation against the host budget counter (dynamic volumes) (tens of ns; a cross-shard budget counter is a cache-padded atomic touched once per volume, not per operation).
7. Append the operation to the in-memory log and, when replicas exist, to the replication queue (tens of ns; the acknowledgement policy decides whether to wait, see `database-design.md` §2.4).
8. Publish the volume to the bridge: a release store of the new root-namespace array pointer (tens of ns); the bridge's next LOOKUP sees it.
9. Write the completion into the reply ring slot (one cache-line transfer) and wake the client.

Everything except step 9's wake is sub-microsecond; the wake is 5-30 µs after idleness on measured systems (Shenango/Caladan/Snap/io_uring numbers in §2.1). Hence: the client spins on the completion word for the measured wake cost before parking (Karlin's 2-competitive rule [A: Karlin90; A: Baumann09]); the daemon's shards spin on their rings while any client is active and park only after a measured idle window; the daemon publishes its measured wake latency in the rendezvous block so clients size their spin. Pre-allocated at start, sized from the machine profile: volume slab, per-volume arena pools, ring buffers, task arenas, index nodes; all pre-faulted and locked (`memory-and-system-awareness.md`), rings placed on the NUMA node of the shard's core.

### 2.5 Process launching

`fork` cost grows with the parent's page-table size; `vfork`/`posix_spawn` avoid copying; `CreateProcess` is the most expensive of the family; all are in the 0.5-2 ms class on measured systems (Barrelfish's trap/IPI costs bound the floor; SOCK measured process creation as the dominant serverless start cost) [A: Baumann09; A: Oakes18]. The daemon therefore never launches tools; the SDK process spawns them itself with the path returned by `attach`. The optional Linux launcher (`slates exec`) forks once, enters `CLONE_NEWUSER|CLONE_NEWNS`, makes `/` recursively private, bind-mounts the volume onto the chosen path, and `exec`s the tool; its cost is `unshare` + `mount(MS_BIND)` + `exec`, unmeasured in the literature and measured at boot on each kernel (`os-filesystem-bridge.md` §2.1).

### 2.6 Python and TypeScript integration for latency

- asyncio: `loop.add_reader(fd)` works on Unix selectors (epoll/kqueue); on Windows the default `ProactorEventLoop` "does not support" `add_reader`/`add_writer`, and `SelectorEventLoop` on Windows accepts socket handles only, limited to 512 sockets [B: Python asyncio platform support, fetched 2026-09-04]. Therefore the completion object the SDK exposes is a socket on Windows (a connected loopback socket pair whose readability is the signal) and an eventfd/pipe on Unix. The SDK's fast path is: write the request into the ring, spin for the measured wake window, then `await` fd readiness; the awaiting side needs no Rust runtime, and the same fd works with uvloop and trio/anyio because they all wait on fds.
- Node: Node-API "will be Application Binary Interface (ABI) stable across versions of Node.js" (Node-API 9 on v18.17+/20.3+, 10 on v22.14+/23.6+) [B: Node-API docs, fetched 2026-09-04]; `napi_get_uv_event_loop` returns the libuv loop so an addon can register a `uv_poll_t` on the completion fd (a socket on Windows, which libuv's poll handles require) and resolve a Promise on readiness; napi-rs's `AsyncTask` (libuv threadpool) is the fallback for calls that must block [C: vorpal survey §7.1; B: Node-API docs (from memory for uv_poll; verify against the libuv docs)].
- The Python and TypeScript SDK designs therefore share one completion mechanism: shared-memory ring + wake word + one fd that becomes readable when the reply lands; the fd is signalled by the daemon only if the client has parked (the client sets a "parked" bit before waiting, the daemon checks it after writing the reply), so the fd write is skipped on the spinning fast path.

## 4. Recommendation for slates

1. **IPC per OS**: shared-memory rings (one command ring and one completion ring per client, fixed-layout 64-byte slots, sequence numbers, cache-line padding) plus a wake word: Linux shared futex on a `memfd` region; macOS `os_sync_wait_on_address` with the SHARED flag on an `shm_open` object (fallback `__ulock_wait` is not shipped); Windows a pagefile-backed section (locked with `VirtualLock` after raising the working set) plus a named auto-reset Event per client because `WaitOnAddress` is process-local. Runner-ups: sockets/pipes per request (5-30 µs each), Mach messages (unmeasured, macOS-only), named pipes (fine for the control channel only).
2. **Rendezvous per OS with zero filesystem entries**: Linux abstract-namespace `AF_UNIX` + `SO_PEERCRED` + `SCM_RIGHTS` fd passing; macOS `shm_open` object named from the uid, mode 0600, slots claimed by CAS, `getpeereid`/`LOCAL_PEERTOKEN` on an optional control socket only if one is needed (a LaunchAgent plist is an install-time file, not a runtime write); Windows `Local\` section and events with a DACL on the user's SID, `GetNamedPipeClientProcessId` on the optional control pipe. Discovery order: `SLATES_ENDPOINT` environment variable, then the per-user well-known name.
3. **Wake strategy**: spin-then-park with the spin length equal to the measured park/unpark cost on this machine (Karlin/Barrelfish), re-measured periodically because DVFS changes it; the daemon publishes the number; shards stay hot while clients are active.
4. **Runtime**: the custom executor of §2.3; compio as the documented runner-up; tokio nowhere.
5. **Fast path**: the nine steps of §2.4 with every allocation pre-sized at boot from the machine profile and every ring and pool NUMA-placed and locked.
6. **SDK completion**: one fd per client (eventfd/pipe on Unix, a loopback socket on Windows) signalled only when the client has parked; identical for Python asyncio/uvloop/trio and for Node via libuv polling.

## 5. Risks, unknowns, and must-calibrate-at-boot

- Apple silicon syscall, `os_sync_wait_on_address` wake, and core-to-core costs have no peer-reviewed numbers; Windows Event wake latency likewise. The daemon measures at boot: wake latency (park a thread, wake it, measure), cross-core round trip through a ring, syscall cost (`clock_gettime` via vDSO versus a real syscall), and minor-fault cost; these feed the spin length, the idle-park window, and the pre-fault policy.
- `os_sync_wait_on_address` requires macOS 14.4; the minimum macOS version is therefore 14.4 unless a documented fallback (a Mach semaphore or a pipe) is accepted for older systems.
- Windows: `WaitOnAddress` is process-local by contract; the Event-based design costs a kernel object per client; measure its wake latency and its cost under thousands of clients.
- DEFER_TASKRUN/SINGLE_ISSUER io_uring modes require 6.1+; containers may block io_uring via seccomp; the epoll fallback must be first-class, not a stub.
- The 50 µs target is achievable only when the client spins; a client that parks immediately pays the OS wake and lands in the 10-60 µs band. The SDKs default to spinning for the published window.
