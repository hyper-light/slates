## 2. Findings by sub-question

### 2.1 EdenFS / Sapling / Mononoke (Meta)

Terms: *checkout* = one working copy of one commit; *mount* = the OS mount point that exposes a checkout; *tree* = a directory object listing (name, object ID) pairs; *blob* = a file-content object; *materialized* = an inode whose contents can no longer be re-derived from a source-control object ID; *overlay* = the local store of materialized inodes; *journal* = an in-memory log of modifying I/O for Watchman; *redirection* = a subdirectory that bypasses the virtual FS.

**What EdenFS is.** "A virtual filesystem designed for efficiently serving large source control repositories"; it "lazily fetches file data, so that it only needs to fetch file information for portions of the repository that are actually used." It optimizes three operations: `status`, commit switching (checkout), and file-change notification via Watchman; it also returns content hashes without reading contents so build tools can key caches on them. Linux uses FUSE, macOS NFSv3, Windows ProjFS, but "EdenFS still tracks its state using the same inode structure that is used on Linux and macOS" on all platforms. [C: eden/fs/docs/Overview.md]

**One daemon, many mounts.** "A single EdenFS daemon can manage multiple checkouts for the user." Each checkout gets its own mount point (Linux/macOS) or ProjFS virtualization root (Windows). Each `EdenMount` holds a `FuseChannel`, the inode set, "an `Overlay` object that tracks locally modified files and directories, and a `Journal` that records all recent modifying file I/O operations." Object fetching is a chain: in-memory cache, then a `BackingStore` (Sapling or Git). Mounting is done by a separate root-privileged helper process over a Unix socket. Per-checkout state lives under `~/.eden/clients/<checkout>/` (config, snapshot ID, overlay). [C: eden/fs/docs/Process_State.md]

**Data model (Merkle-like trees).** Commits point at a root tree; a tree entry "has the name of the child entry as well as the object ID, which refers either to another tree object for a subdirectory or to a blob object for a regular file." Trees served by Mononoke additionally carry file size and content hash per entry (Git's model lacks this). "EdenFS expects to be able to look up objects by ID, where an object ID is an opaque 20-byte key"; content addressing is used by both Git and Sapling but EdenFS "doesn't require this property." Mutable `TreeInode`/`FileInode` objects parallel the immutable `Tree`/`Blob` objects. [C: eden/fs/docs/Data_Model.md]

**Lazy inode loading.** "When a `TreeInode` object is loaded we know the names of all children inodes, but we do not actually create inode objects in memory for the children until they are accessed." A fresh checkout is entirely non-materialized. [C: eden/fs/docs/Inodes.md]

**Materialization and its upward propagation.** "An inode is not materialized if we have a source control object ID that can be used to fetch the inode contents." When a file is modified, "EdenFS then removes the source control object ID from the inode information, and instead stores the file contents in the overlay." Crucially: "Whenever a file or directory inode is materialized its parent inode must also be materialized," because a directory's object ID fully identifies its entries; materialization propagates to the root until an already-materialized ancestor is hit. Materialization is orthogonal to loaded/unloaded (all four combinations exist). [C: eden/fs/docs/Inodes.md] The overlay "records metadata about the list of files in the root, the list of files in 'foo', the list of files in 'foo/bar' and finally materializes 'foo/bar/baz'" for a write to foo/bar/baz. [C: eden/fs/inodes/Overlay.h]

**Where things live (the overlay is on disk — a difference from slates).** The overlay is "an on-disk map from inode number to its timestamps plus the file's or tree's contents." In memory, `InodeMap` keeps `loadedInodes_` (full state) and `unloadedInodes_` (for inodes the kernel still references: FUSE refcount, object ID if not materialized, mode bits, parent inode number, name). Durability target is process-crash safety only: "If the process dies, none of the user's data should be lost," explicitly not power loss or disk failure. [C: eden/fs/docs/InodeStorage.md] Overlay inode catalogs are pluggable (`Sqlite` default on Windows, `Legacy` elsewhere, filesystem-backed and ephemeral/in-memory variants exist); the next-inode-number counter "Persists on disk on clean exit" and inode-range reservations are "fsync-ed... in all cases"; directory writes can be deferred through a WAL ("buffered overlay"). [C: eden/fs/inodes/Overlay.h; eden/fs/docs/Config.md `[overlay] buffered`, `inode-catalog-type`]

**Inode numbers: allocated on demand, must be stable.** EdenFS "assigns inode numbers on demand when an inode is first accessed" from "a monotonically increasing 64-bit ID"; assignments are recorded in the overlay so "simply listing a directory does cause it to be written to the overlay." [C: eden/fs/docs/Inodes.md] Stability is a hard requirement learned from build systems: "Eden should never hand out duplicate inode numbers," and if a checkout "forgets that directory's inode numbers... the mtimes allocated to the source files could appear to advance," breaking incremental builds. [C: eden/fs/docs/InodeStorage.md] Hard links are unsupported because each inode has a single parent pointer. [C: eden/fs/docs/Inodes.md]

**Inode lifetime and unloading under memory pressure.** Inodes use an intrusive refcount (`InodePtr`) plus a separate FUSE refcount; "Inode objects may be unloaded even when the FUSE reference count is non-zero" (they move to `unloadedInodes_`). Unloading happens on shutdown, on unlink when both counts are zero, and by a background GC; unloading under memory pressure is described as possible but not implemented ("we could decide to immediately unload unreferenced inodes if we are low on memory"). [C: eden/fs/docs/InodeLifetime.md] The GC (`EdenServer::garbageCollectInodes`) takes a GC lease, invalidates entries not used within `gcCutoff` (default 6 hours), skips materialized inodes, and then "unloads any inode whose filesystem reference count is zero." Per-OS: FUSE invalidation prompts `FUSE_FORGET`; NFSv3 "does not notify EdenFS when file handles are closed" so refcounts are dropped manually via invalidation callbacks; PrjFS checks on-disk access times via `_wstat64()`. [C: eden/fs/docs/InodeGarbageCollection.md]

**Locking and rename (the hard case is centralized).** Lock order from leaf to root: `location_` (never nest), `InodeMap data_`, `InodeMetadataTable`, `OverlayFileAccess`, `FileInode`, `TreeInode contents_`, then "EdenMount's Rename Lock: a very high level lock... acquired before any other individual inode-specific locks." Rule: "If you are not holding the mountpoint rename lock, you can only acquire a TreeInode `contents_` lock if the other `contents_` locks you are holding are for this TreeInode's immediate parents." [C: eden/fs/docs/InodeLocks.md] "There is a mountpoint-wide rename lock that is held during any rename or unlink operation" but not during create; directory-over-empty-directory rename may hold "up to 3 TreeInode locks concurrently." Rename of an unloaded child waits for the load and re-checks rather than holding the rename lock across the load. [C: eden/fs/docs/Rename.md] Lesson: EdenFS accepts one mount-wide rename serialization point; creates/reads stay per-directory.

**Checkout is O(changed), not O(tree).** Checkout compares old and new `Tree` objects per directory; unchanged subtrees share object IDs and are skipped. Simple actions (new entries) run "while holding the TreeInode's contents lock"; others become deferred `CheckoutAction`s "executed after releasing the lock." "For the old blob we only download the sha1 as this is all we will need." Actions report whether "the directory's inode's readdir cache must be flushed." [C: eden/fs/inodes/CheckoutAction.h] The public statement of the resulting property: "operations like `checkout` [are] much faster, in exchange for a small performance hit when first accessing new files," and the stated scalability goal is that "all source control operations scale with the number of files in use by a developer, and not with the size of the repository itself." [C: facebook/sapling README.md]

**Journal (change feed for Watchman).** The Journal "contains metadata only; it is not a full snapshot"; it records created/removed/changed/renamed/replaced paths, root (commit) updates, and unclean paths after checkout, each delta with a sequence number and timestamp. Default memory limit `kDefaultJournalMemoryLimit = 1000000000` bytes; when exceeded it "removes the oldest deltas until the memory usage of the journal is below the journal's memory limit." Subscribers "are called on the thread that called addDelta" and must only schedule work; deltas may be coalesced between observations. [C: eden/fs/journal/Journal.h] Watchman consumes this instead of crawling, which is how `hg status` stays O(changes). [C: Overview.md]

**Caching layers and their measured costs.** Kernel VFS cache in front of FUSE: "The latency of a cached operation is somewhere below a microsecond," whereas an uncached FUSE request costs "10+ microseconds" (author's measurement, conditions unstated — must-measure). EdenFS returns infinite cache expiry and explicitly invalidates. In-process: blob cache (LRU, default 40 MiB, minimum 16 entries, eviction deferred until a file's full range has been read via a CoverageSet), blob-metadata cache (blob ID -> 64-bit size + 20-byte SHA-1, "approximately one million entries consuming under 100 MB"), then a RocksDB local store, then the Sapling cache and the server. [C: eden/fs/docs/Caching.md]

**Threads.** FUSE: `fuse:NumDispatcherThreads` (default 16) per mount doing blocking reads of /dev/fuse ("if you have 3 mounts, there will be 3*fuse:NumDispatcherThreads threads"); shared `FsChannelThreadPool` (default = ncores, unbounded queue "due to deadlocks caused by FsChannelThreads being blocked trying to add to a full queue"); `EdenCPUThreadPool` 12 threads; NFS: one server per mount with an EventBase reader and work on the pool; ProjFS notifications on a single-threaded sequenced executor; `SaplingBackingStore` 32 threads with configurable batch sizes for blobs/trees/aux data. "In general, we try to avoid blocking on other threads. The only places we ought to block are talking to the filesystem and contending on locks." [C: eden/fs/docs/Threading.md] Lesson for slates: EdenFS is a lock-based, thread-pool design; its documented deadlocks and unbounded queues are exactly what a thread-per-core, shared-nothing design avoids, but its "never block except on the kernel" rule stands.

**Per-OS invalidation strategies.** Linux/FUSE: kernel caches with infinite TTL; EdenFS calls invalidation and gets `FUSE_FORGET`. macOS/NFSv3: no callbacks exist, so "EdenFS chmod's the parent directories of any files that changed during checkout with the same permissions that they currently have" to make the client drop its cache; "there are reports of stale content being seen after checkout." Windows/ProjFS: invalidate with `PrjDeleteFile` and `PrjMarkDirectoryAsPlaceholder`; if handles are open "invalidation fails while checkout succeeds," leaving disk and inodes desynchronized. [C: eden/fs/docs/macOS.md; Windows.md]

**macOS via NFS: what Meta learned (directly relevant to slates on macOS).** NFSv3 was chosen because "Apple deprecated third party kernel extensions"; the costs: no xattrs; no client pid in requests; readdir "includes basically only the names of the entries... the types of the entries are missing," forcing a lookup+getattr per entry and motivating a Thrift readdir endpoint for Buck2; "NFS never tells us when a file has been forgotten," so inode counts grow and a background GC is needed; on a daemon crash "IO in NFS mounts will hang" (FUSE returns ENOTCONN); the macOS NFS client "does not support close-to-open guarantees as the spec says it should"; case: "macOS will use the first casing used to access a file as the source of truth"; deleting an open file yields `.nfs-xxxx` temp files. Architecture: "n+1 servers" for n mounts (one nfsd3 each plus a shared mountd), each an RPC server on folly AsyncSocket; the mount syscall carries all options because NFS has no post-mount INIT negotiation. Rollout impact: "when we rolled out NFS perf impacts across the board were pretty much a wash." NFSv4 was rejected for spec size (323 vs 126 pages), serialized OPENs, and lease complexity; SMB and FileProvider were rejected (FileProvider "fsevents frequently drops events"). [C: eden/fs/docs/macOS.md]

**Windows via ProjFS.** "PrjFS refers to files with paths rather than inode numbers." Three on-disk states: unhydrated placeholder, hydrated placeholder, full (locally modified/created) file. "PrjFS does not remember directory contents. Every time a directory is listed PrjFS will re-request the listing from EdenFS." Writes happen first, notifications arrive after and "ProjectedFS doesn't provide any guarantee about the ordering of notifications," so EdenFS reconciles by inspecting disk. Locally modified content is not duplicated into the overlay; "materialized" on Windows means "disk... is the source of truth." Files already read "will still be readable after EdenFS is stopped," so fsck runs at every startup. [C: eden/fs/docs/Windows.md; WindowsFsck.md] ProjFS is designed for "high-speed backing data stores"; it offers no progress or online/offline reporting. [B: Microsoft ProjFS docs]

**Redirections: attaching real storage at chosen paths.** Redirections "allow specific subdirectories to bypass EdenFS, and be stored directly on local disk," because writes through a user-space FS cost "user application -> kernel -> EdenFS -> kernel -> disk," which hurts when build tools write "many thousands of files, containing many gigabytes of data." Linux uses bind mounts (symlinks are the fallback, with `..` semantics caveats); `.eden-redirections` in the repo root is applied on every checkout; the directories "must be new subdirectories that only contain generated files"; writes there bypass the journal, so Watchman does not see them (deliberate). [C: eden/fs/docs/Redirections.md] Lesson: the inverse is what slates needs — mounting a slates volume at a chosen path inside another tree — and the bind-mount/symlink/APFS-volume menu is the OS toolkit for it.

**Graceful restart (takeover).** A new daemon takes over FUSE/NFS mounts (not ProjFS) by receiving the mount fds and a serialized inode map (inode number, parent, name, refcounts, object hash, mode, last-used time); for "3+ million inodes" the transfer is chunked at 512 MB. [C: eden/fs/docs/Takeover.md] This is the strongest in-repo evidence of typical loaded-inode counts per mount at Meta.

**Globbing and prefetch APIs.** Beyond the FS interface, a Thrift interface offers checkout, glob and hash queries; `globFiles` evaluates gitignore-style patterns and returns matches without the caller crawling the mount. [C: eden/fs/docs/Globbing.md; Overview.md] (Evaluation over unloaded `Tree` objects and prefetch flags are in eden/fs/service/eden.thrift; see 2.5.)

**Paths.** Components are capped at 255 bytes; OS path limits 4096 (Linux), 1024 (macOS), 260/32767 (Windows); "Mononoke additionally restricts paths to 980 characters maximum." [C: eden/fs/docs/Paths.md]

**Mononoke.** "Mononoke is the server built for the Sapling Source Control System," "primarily written in Rust," with "mysql, sqlite, file and S3 backends," and "meant to scale up to accepting thousands of commits every hour across millions of files." [C: eden/mononoke/README.md] The source tree has `blobstore` (content-addressed blob layer with packblob compression), `manifest`, `derived_data`, `mononoke_types`, and `servers`; the client fetches trees and files lazily through the Sapling remote API rather than cloning. [C: eden/mononoke directory listing] Public statement: "as you use the repository we download just the commits, trees, and files you actually need." [D: Meta engineering post 2022-11-15]

**Scale numbers stated for Sapling/EdenFS (all as stated, none independently measurable here).**
- "Sapling scales to repositories with 10's of millions of files, commits, and branches." [B: sapling-scm.com introduction]
- "tens of millions of files, tens of millions of commits, and tens of millions of branches," "tens of thousands of internal developers," and, for the Linux kernel repo, "three-quarters of the 5.5 GB... is the history." [D: Meta engineering post 2022-11-15]
- 2014 baseline for the main repo: "hundreds of thousands of files," "thousands of commits a week," "tens of thousands of files changing every day"; Watchman-backed status "more than 5x faster than Git's status"; remotefilelog made clones/pulls "10x faster... from minutes to seconds" and cut server network load ">10x." [D: Meta engineering post 2014-01-07]
- Takeover chunking exists for "3+ million inodes" per mount; journal cap 1 GB; blob cache 40 MiB; blob-metadata cache ~1M entries < 100 MB; GC cutoff 6 h; 16 FUSE dispatcher threads per mount; 32 backing-store threads. [C: Takeover.md; Journal.h; Caching.md; InodeGarbageCollection.md; Threading.md]
- Kernel-cached FS op < 1 µs vs uncached FUSE op 10+ µs (Meta's own statement; conditions unstated). [C: Caching.md]

**What transfers to slates from 2.1.** (a) The tree/blob object model with per-entry size+hash is the right unit of sharing and of O(changed) diff/checkout; (b) the "materialize upward to root" rule is the copy-on-write path-copying rule in disguise; (c) inode-number stability is a correctness requirement for build tools, not a nicety; (d) one mount-wide rename lock is the pragmatic answer to cross-directory rename when directories are locked independently — slates should reproduce the *semantics* with a per-volume serialization point but without a blocking mutex; (e) macOS NFS needs an explicit invalidation strategy and its own inode GC because the client never says "forget"; (f) the journal-as-change-feed with a bounded memory budget is what makes `status`/Watchman-style consumers O(changes).

### 2.2 Google Piper / CitC (Clients in the Cloud)

Terms: *Piper* = Google's monorepo version-control service; *CitC* = the cloud-backed FUSE workspace layer; *workspace* = a developer's overlay of edits on top of the repository at some revision.

**Scale numbers (all as of 2015-2016, stated by the authors).** "The Google codebase includes approximately one billion files and has a history of approximately 35 million commits spanning Google's entire 18-year existence. The repository contains 86TB of data, including approximately two billion lines of code in nine million unique source files." "Each day the repository serves billions of file read requests, with approximately 800,000 queries per second during peak traffic and an average of approximately 500,000 queries per second each workday." "Google's codebase is shared by more than 25,000 Google software developers"; "On a typical workday, they commit 16,000 changes to the codebase, and another 24,000 changes are committed by automated systems." [A: Potvin & Levenberg, CACM 2016] Note the ratio: one billion *files* but nine million *unique source files* — the rest is release-branch copies, deleted-at-head files, configuration, docs and data; slates should expect "files per tree" and "unique content objects" to differ by two orders of magnitude in this kind of corpus. [A: same]

**Replication and latency hiding.** "Piper is distributed over 10 Google data centers around the world, relying on the Paxos algorithm to guarantee consistency across replicas." "Caching and asynchronous operations hide much of the network latency from developers"; the toolchain "requires developers to be online." [A: same]

**CitC = workspaces as cheap overlays over shared base content.** "Most developers access Piper through a system called Clients in the Cloud, or CitC, which consists of a cloud-based storage backend and a Linux-only FUSE file system." "Developers see their workspaces as directories in the file system, including their changes overlaid on top of the full Piper repository." "CitC supports code browsing and normal Unix tools with no need to clone or sync state locally." "Developers can browse and edit files anywhere across the Piper repository, and only modified files are stored in their workspace. This structure means CitC workspaces typically consume only a small amount of storage (an average workspace has fewer than 10 files) while presenting a seamless view of the entire Piper codebase to the developer." [A: same]

**Snapshots on every write; workspaces visible from anywhere and to other tools.** "All writes to files are stored as snapshots in CitC, making it possible to recover previous stages of work as needed. Snapshots may be explicitly named, restored, or tagged for review." "CitC workspaces are available on any machine that can connect to the cloud-based storage system, making it easy to switch machines and pick up work without interruption. It also makes it possible for developers to view each other's work in CitC workspaces." "Working state is thus available to other tools, including the cloud-based build system, the automated test infrastructure, and the code browsing, editing, and review tools." "Over 80% of Piper users today use CitC." [A: same]

**Lessons for slates (volumes as cheap overlays over shared base content).**
1. The per-workspace state that must be private is tiny (median well under ten files) while the visible tree is a billion entries; therefore per-volume metadata must be O(changes), and the base tree must be shared structurally, never copied. This is the same conclusion EdenFS reaches with materialization (2.1). [A: Potvin & Levenberg 2016; C: eden/fs/docs/Inodes.md]
2. "Snapshot on every save" is a product feature, so snapshot creation must be O(1)-ish (persistent tree root swap), not a copy.
3. A workspace must be attachable from any machine and readable by other services (build, test, review) — i.e., remote attach and multi-reader access are baseline, and a *single owner* per workspace is the implied write model (a workspace belongs to a developer; others view it). [A: same]
4. The base store is read-dominated at 5e5–8e5 QPS and served from a strongly consistent, geo-replicated service with heavy caching — for slates, the base content tier should be immutable, content-addressed and cache-friendly, while mutable per-volume state is small and single-owner. [A: same]

### 2.4 Client cache coherence and leases for volumes attached from several machines

Terms: *lease* = a time-bounded promise from a server that it will not let the covered data change without first asking the leaseholder; *callback* = a server-to-client notification that cached data is now invalid; *delegation* = NFSv4's recallable lease that lets one client handle opens/closes (and writes) locally; *close-to-open* = a cached copy is validated at open and flushed at close, so readers who open after a writer closes see the new data; *capability (Ceph)* = a per-inode, per-client permission bitmask that also encodes cache/buffer rights.

**Leases (Gray & Cheriton, SOSP 1989).** Definition: "the server also returns a lease guaranteeing that the data will not be written by any client during the lease term unless the server first obtains the approval of this leaseholder... When a client writes a datum, the server must defer the request until each leaseholder has granted approval or the term of its lease has expired." [A: Gray & Cheriton 1989] Failure handling is by time: after a client failure the server "must delay writes to a file for which the failed client holds a lease" until the lease expires; short leases bound that delay and "minimize the false write-sharing"; long leases cut renewal traffic. Measured on a V-system compilation trace: "at S = 1, a term of 10 seconds reduces the consistency traffic to 10% of that for a zero term," and "most of the benefit of a non-zero lease term is gained by a term of just a few seconds"; the authors expect "lease terms on the order of seconds and message times... in the range of milliseconds." [A: same] Historical anchors given in the paper: Sprite, RFS and the AFS prototype used a zero-term lease at the granularity of file opens (validate on every open), while AFS's revised version "went from using a lease term of zero in the prototype to effectively a lease term of infinity" (callbacks). [A: same]

**AFS (Howard et al., TOCS 1988).** Whole-file caching with server-maintained *callbacks*: "Before modifying a file or directory, a server has to notify every workstation that has a callback on that file"; callbacks replaced per-open validation and "dramatically reduce[d] the number of cache validation requests." Semantics: "Writes to an open file by a process on a workstation are visible to all other processes on the workstation immediately but are invisible elsewhere in the network. Once a file is closed, the changes made to it are visible to new opens anywhere on the network. Already open instances of the file do not reflect these changes." "No implicit locking is performed." Scale: the prototype ran at "CPU utilization of about 40 percent" averaged over 8 hours with 75% over 5-minute windows; the redesign targeted "at least 50 clients per server" and the out-of-kernel implementation "is capable of supporting many hundreds or thousands of clients per server." [A: Howard et al. 1988]

**Coda (Kistler & Satyanarayanan, TOCS 1992).** Optimistic replica control with callback-based coherence inherited from AFS, disconnected operation via *hoarding*, and reintegration with write/write conflict detection ("The only class of conflicts we are concerned with are write/write conflicts"). Observed sharing: "In our use of optimistic server replication in Coda for nearly a year, we have seen virtually no conflicts due to multiple users updating an object in different network partitions," and the AFS-trace study over 400 users quantified how rarely a different user is the next writer of a file (table in the paper; see section 3). [A: Kistler & Satyanarayanan 1992] Hoard profiles are user-supplied lists plus recorded references ("Venus can record all file references"), walked every 10 minutes — an early form of access-derived prefetch. [A: same]

**NFSv4 (RFC 7530; RFC 8881).** Baseline without delegation is close-to-open: "cached data present on a client must be revalidated after doing an OPEN... the client fetches the change attribute from the server, compares it with the cached change attribute, and, if different, declares the cached data (as well as the cached attributes) as invalid." [B: RFC 7530 §10.3.1] Delegations: "Recallable delegation of server responsibilities for a file to a client improves performance by avoiding repeated requests to the server in the absence of inter-client conflict. With the use of a 'callback' RPC from server to client, a server recalls delegated responsibilities when another client engages in the sharing of a delegated file." Two kinds: OPEN_DELEGATE_READ (many may coexist; holder "is assured that no other client may modify the contents or attributes") and OPEN_DELEGATE_WRITE ("Only one... may exist for a given file at a given time"; holder "may modify the file data since no other client will be accessing the file's data"). The server "must recall the delegation before deciding whether the OPEN from the other client may be granted," and a typical grant condition is that "the probability of future conflicting open requests should be low, based on the recent history of the file." Callbacks are tested with CB_NULL and "correct protocol operation does not depend on them." [B: RFC 7530 §10.2, §10.4] All client state hangs off one lease: "in the worst case, one RPC is required every lease period." [B: RFC 7530 §9.5] NFSv4.1 adds optional *directory delegations* ("cache directory contents (in a read-only fashion) while being notified of changes") explicitly motivated by "numerous queries for files that do not exist... compilation in software development environments." [B: RFC 8881 §10.9] In practice CB_NOTIFY is "rarely implemented by clients" [C: Buildbarn ADR 0009], and Apple's client "does not support close-to-open guarantees as the spec says it should." [C: eden/fs/docs/macOS.md]

**Ceph capabilities (Weil et al., OSDI 2006; CephFS docs).** Capabilities "include four bits controlling the client's ability to read, cache reads, write, and buffer writes." When a file is opened by multiple clients "with either multiple writers or a mix of readers and writers, the MDS will revoke any previously issued read caching and write buffering capabilities, forcing client I/O for that file to be synchronous." For metadata, "no metadata locks or leases are issued to clients" (MDS applies updates synchronously; readdir+stat is optimized instead). [A: Weil et al. 2006] Today's docs: caps are "quite granular, and it's possible that multiple clients can hold different capabilities on the same inodes"; with concurrent writers "the lock state will be transferred to LOCK_MIX" and "the clients will do sync read/write"; LazyIO "relaxes POSIX semantics." [B: docs.ceph.com/cephfs/capabilities]

**Decision for slates — the consistency model for volumes attached from several machines.** Choose *single-writer volume ownership with a recallable owner lease, plus snapshot readers*, layered with *optional per-subtree write delegations* for explicit multi-agent sharing, and *never* silent last-writer-wins:
- Default: exactly one *owner* (one node, one agent) holds a short, implicitly renewed lease on a volume (seconds, per Gray & Cheriton's analysis; the exact term is a measured input: renewal RTT vs. failover delay). All mutations go through the owner; other machines attach *snapshots* (immutable content-addressed roots) which need no coherence at all. This matches CitC (a workspace has one developer; others view it) and Coda/AFS evidence that write sharing is rare. [A: Potvin & Levenberg 2016; A: Kistler & Satyanarayanan 1992; A: Gray & Cheriton 1989]
- Shared-write volumes (explicitly requested): the owner grants NFSv4-style recallable delegations per subtree (directory-granularity, because agents partition work by path); a conflicting open recalls the delegation, and while more than one writer touches the same file the system does what Ceph does — revoke caching/buffering and serialize at the home node (correct, slower), rather than what NFS-without-delegation does (close-to-open races) or what a naive replicated store does (last-writer-wins). [B: RFC 7530 §10.4; A: Weil et al. 2006]
- Optimistic parallelism is offered as *clone + merge* at the API (Coda-style reintegration with write/write conflict surfaces as data), never as concurrent mutation of one root. [A: Kistler & Satyanarayanan 1992]
- Runner-ups: (i) per-file leases everywhere (IndexFS/NFSv4 file delegations) — rejected as the default because it multiplies lease state by files (millions per volume) and the common agent workload is exclusive anyway; (ii) last-writer-wins with vector clocks (Dynamo) — rejected because filesystem semantics (rename, directory invariants) do not merge automatically and build tools cannot tolerate silent divergence; (iii) fully synchronous home-node I/O for everything (Ceph's conflict path as the default) — correct but throws away the kernel page cache; only used under actual conflict.


### 2.3 Distributed metadata services and the recurring design rules

- Ceph's metadata server partitions the namespace dynamically by subtree, migrating hot subtrees between servers and replicating hot directories for reads; the OSDI'06 paper reports near-linear metadata throughput scaling with the number of MDS nodes and identifies rename across subtrees as the operation needing a two-server protocol [A: Weil et al. SC'04; A: Weil et al. OSDI'06]. GFS kept all metadata in one master's memory (64 bytes per 64 MB chunk, prefix-compressed namespace) and HDFS's NameNode inherited the single-namespace-server limit [A: Ghemawat et al. SOSP'03]. HopsFS moved HDFS metadata into an in-memory NewSQL database (NDB) with row-level locking and reported 16x the throughput of HDFS with 37x more metadata capacity [A: Niazi et al. FAST'17]. IndexFS scaled metadata by embedding directory entries and attributes in LSM tables with client-side caching of path prefixes and leases [A: Ren et al. SC'14]. LocoFS decoupled directory and file metadata into separate stores to cut the cost of dependent operations [A: Li et al. SC'17]. InfiniFS decouples directory metadata into access-related and content-related parts, hashes file metadata by parent id, and resolves paths speculatively so lookups need one round trip on the common path; it targets hundreds of billions of files [A: Lv et al. FAST'22]. Tectonic (Meta's exabyte store) keeps metadata in a sharded key-value store (ZippyDB) partitioned by hash of the parent for the name layer, with file and block layers separately partitioned, and serves multi-tenant clusters from one namespace [A: Pan et al. FAST'21]. Colossus (Google) likewise stores file metadata in Bigtable-backed "curators" [D: Google Cloud blog on Colossus].
- Recurring rules extracted: (1) keep hot metadata in memory and make the on-path structures cache-friendly; (2) partition the namespace so that the common operations (lookup, create in a directory, stat) touch one partition; (3) separate directory entries from inode attributes so directory scans do not drag attributes and vice versa; (4) let clients cache path prefixes under leases so path resolution is O(1) round trips; (5) treat cross-partition rename as the special case with its own protocol; (6) avoid any global lock or global counter.
- slates' mapping: a volume is the partition (every operation names its volume), so rules 2 and 6 hold by construction; rule 3 is the inode slab separate from directory nodes (`cow-data-structures.md` §2.1); rule 4 is the kernel dcache plus explicit invalidation; rule 5 is "rename never crosses volumes" (a cross-volume move is a copy-on-write clone of the subtree plus an unlink, sequenced through the log).

### 2.5 Lazy materialization and sub-millisecond remote attach

- Buildbarn's bb_clientd presents a single FUSE (Linux) or NFSv4 (macOS) mount whose `cas/` subtree lazily loads content-addressed objects from the remote CAS by digest; a build action's inputs "attach" as a directory tree whose blobs are fetched on first read; it uses lease times of 60-120 s and validity of 300 s for cached attributes [C: bb-clientd README and config]. The Bazel Remote Execution API models trees as `Directory` messages referring to blobs by SHA-256 digest and size, so a tree is attached by fetching directories only [C: REAPI protocol].
- Slacker (FAST'16) measured that pulling image data accounts for 76% of container start time while only 6.4% of that data is read, and built a lazy block-level loader with snapshot/clone primitives so containers start in seconds instead of minutes [A: Harter et al. FAST'16]. DADI (ATC'20) applies block-level lazy loading with a peer-to-peer fetch tree and reports container start speedups of an order of magnitude at Alibaba scale [A: Li et al. ATC'20]. Nydus and eStargz do the same at the file/chunk level for OCI images [C: containerd stargz-snapshotter; C: dragonflyoss/nydus]. gVisor's rootfs overlay backs the upper layer with memory (`--overlay2=root:memory`) so container writes never reach the host disk, with a documented memory-accounting trade-off [C: gVisor docs].
- Conclusion for slates: a remote attach is a manifest reference (the snapshot's root identity plus the chunk index for the tree), which is metadata-only and O(paths touched) to serve; content chunks are fetched on first read from any replica holding them, verified by identity, and cached in the local arena; the attach itself completes in the same sub-50 µs path as a local clone once the manifest is resident. Prefetch policy is derived from data: the daemon records per-volume first-read sequences (which paths were read within the first N seconds after attach) and prefetches the measured hot set on the next attach of the same base (EdenFS's template eager-sets and sampled glob profiles, Coda's hoard profiles) [C: survey-hecate.md §2.7; A: Kistler & Satyanarayanan TOCS'92].

### 2.6 Replicating content across nodes in RAM

- Unit of replication: the content-addressed chunk (immutable, self-verifying), so replication needs no ordering; only manifests (small) need the ordered log. Anti-entropy between replicas compares Merkle roots of manifests and walks down only where they differ (Dynamo's Merkle-tree synchronization) [A: DeCandia et al. SOSP'07]; Sapling's tree manifests give the same O(changed) diff for free [C: Sapling manifest-tree].
- Replication factor versus erasure coding in memory: RAMCloud argued that 3x DRAM replication triples cost and energy and therefore kept redundancy on disk [A: Ousterhout SOSP'11]; Cocytus (FAST'16) applied erasure coding to the *data* of an in-memory key-value store while replicating only the small *metadata*, reporting memory savings of roughly a third to a half against three-way replication at the cost of a reconstruction path on failure [A: Zhang et al. FAST'16 — numbers from memory, flagged for re-verification]. For slates the content chunks are large and immutable, so erasure coding of chunks across k+m nodes is the documented option for the "many nodes, memory-bound" regime; f+1 replication is the default because it keeps reads local and recovery a copy.
- Placement across failure domains follows the failure-domain tree; datacenter RTTs are in the 100s of microseconds within a region and tens of milliseconds across regions, and tail latency must be engineered with hedged and tied requests [A: Dean & Barroso CACM'13].

## 4. Recommendation for slates

1. **Base-content sharing**: immutable, content-addressed chunks and Merkle manifests as the shared base; a volume's private state is its delta (CitC: <10 files on average), so per-volume metadata is O(changes) and never a copy.
2. **Metadata partitioning**: by volume (the natural partition); within a volume, directory nodes separate from the inode slab; no cross-volume rename.
3. **Consistency and leases**: single-writer volume ownership with a short renewable lease carrying an epoch, snapshot readers everywhere, optional recallable per-subtree delegations for explicitly shared volumes, conflicts surfaced as data (clone + merge), never last-writer-wins.
4. **Lazy attach and prefetch**: attach = manifest reference; content on first read; prefetch sets learned from recorded first-read sequences per base snapshot.
5. **Replication**: f+1 in-RAM copies of chunks and manifests across declared failure domains, chosen by rendezvous hashing over the failure-domain tree; Merkle anti-entropy; erasure coding as the documented memory-bound option.
6. **Scale targets**: the table in §2.7, with every "measured" row an input the daemon reads at runtime.

## 5. Risks, unknowns, must-measure

- The Cocytus memory-saving figures and the Colossus description are from memory or secondary sources; re-verify before citing in the design.
- EdenFS's per-operation latency claim has no stated conditions; measure ours.
- Lease terms, delegation recall latency, and prefetch hit rates are workload-dependent; the design records them per volume and derives the lease from measured renewal RTT and failover budget.
