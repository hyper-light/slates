## 1. Questions answered

1. Namespace: what structure should each directory use (hash table, adaptive radix tree, B-tree, sorted array) as a function of its size; what a full path costs; how to build the inode/handle table; how to do hard links, atomic rename with cycle prevention, and case/normalization-insensitive names; what the scale evidence (Google Piper/CitC, EdenFS, ScaleFS) says.
2. Snapshot/clone: which mechanism gives O(1) clone with the lowest per-snapshot memory, the least write amplification, cheap deletion, wait-free readers on immutable versions, and no shared-ownership (`Arc`) problem in a thread-per-core design: CoW B-tree with lazy reference counting (Rodeh/Btrfs), birth-time/deadlist (ZFS/WAFL), persistent functional structures (HAMT/CHAMP/RRB), Merkle manifests with a materialized overlay (git/Sapling/EdenFS), or operation logs (ScaleFS).
3. Content: fixed pages vs content-defined chunks vs extents vs rope/piece table; page-size alignment (4 KiB / 16 KiB / 64 KiB); what real tools (git, cargo, npm, editors) actually write; zero-copy paths; sparse files; how to pick the page/chunk size from measured data.
4. Concurrency: shared-nothing (one core owns a volume, requests cross cores through rings) versus RCU/epoch-style (atomically published immutable snapshots, wait-free readers on any core, single writer); the cited costs of a cross-core message versus an epoch-protected read; what the Scalable Commutativity Rule, ScaleFS, RadixVM, the Linux dcache, ffwd and Barrelfish say; which memory-reclamation scheme (EBR, hazard pointers, DEBRA, IBR, Hyaline) fits.
5. Dedup/content addressing: BLAKE3 costs and tree-hash properties; FastCDC/LBFS/Data Domain chunking; whole-file vs block dedup yield (Meyer & Bolosky); when hashing pays for itself; how content addressing feeds clone, archive and replication.
6. Accounting: how ZFS and Btrfs charge shared blocks; how to give a bounded volume exact O(1) ENOSPC; who pays for shared chunks under clones/snapshots; what dynamic volumes need.
7. Metadata: which POSIX/Windows attributes to store; what git/cargo/npm/editors/watchers actually depend on (executable bit, mtime stability, inode-number stability); inode numbers across snapshots and restarts (EdenFS, ScaleFS).

## 2. Findings by sub-question

### 2.1 Namespace representation

Terms: *namespace* = the mapping from paths to file objects. *Directory* = a map from a name (byte string) to a child. *Inode* = the record that holds a file's metadata and points at its content. *Handle table* = a table that maps small integers (inode numbers, file handles) to inode records. *Slab* = a pre-allocated array of fixed-size slots. *Generational index* = a slot index paired with a counter that is bumped each time the slot is reused, so a stale handle can be detected.

**Directories are almost all tiny, with a long tail.**
- In Microsoft's five-year study of ~70,000 Windows desktop file systems, the median directory holds 2 files across all years; 46-49% of directories have two or fewer entries; 90% of directories have 20 or fewer entries and two or fewer subdirectories; 65-67% have no subdirectories; the arithmetic mean directory size fell from 12.5 to 10.2 entries [A: Agrawal07 §3 and §4].
- Measured here on developer trees that slates will actually host [M]: `node_modules` of a TypeScript monorepo (65,048 files, 10,027 dirs): entries/dir p50 = 2, p90 = 13, p99 = 77, max = 1,520. Cargo registry sources (28,853 files, 6,168 dirs): p50 = 2, p90 = 11, p99 = 37, max = 1,706. A Cargo `target/` directory (191,690 files, 19,616 dirs, 134 GiB): p50 = 4, p90 = 4, p99 = 91, max = 61,067 (the flat `deps/` directory). Linux kernel source tree (98,135 files, 6,224 dirs): p50 = 6, p90 = 34, p99 = 181, max = 3,365. Name lengths: p50 = 11-27 bytes, p99 = 35-81 bytes, max 107 bytes; the POSIX/EdenFS per-component limit is 255 bytes [C: EdenFS Paths.md].
- Conclusion: the common case (p90 <= 34 entries) fits in one or two cache lines of name hashes; only the tail (build output directories, `deps/`, big flat vendored trees) needs a real index. Any per-directory structure must therefore be *adaptive*: a compact representation up to a cut-over, an indexed one beyond it. The cut-over is a runtime-measured constant (see §5), not a magic number.

**Which index for the large case: hash table vs adaptive radix tree (ART) vs HOT vs B-tree.**
- ART (Leis, Kemper, Neumann) uses four node sizes (Node4, Node16, Node48, Node256) with lazy expansion and path compression; it bounds worst-case space at 52 bytes/key for any key length and measured as low as 8.1 bytes/key; single-threaded lookups on a Core i7-3930K (3.2 GHz, 12 MB LLC) are comparable to a chained hash table for dense keys and lower for sparse keys; with 16M keys lookups are memory-bound and ART, FAST and the hash table incur similar cache misses (ART half as many for dense keys); sparse keys cost ~0.85 mispredicted branches per lookup at node-type dispatch; Node16 lookups use SSE compares and Node48 two array lookups [A: Leis13 §III, §IV-G Table, §V-A Fig. 10 and Table III].
- Masstree (trie of B+-trees on 8-byte key slices) reaches "more than six million simple queries per second" on a 16-core machine with logging and network, and 6-10 M ops/s on YCSB A-C; reads are lock-free via per-node version numbers with retry; writes lock only the affected node [A: Mao12 §1, §4.4].
- HOT (Height Optimized Trie) varies the number of bits per node to keep fanout high for string keys; across four 50M-key datasets its footprint stays at 11.4-14.4 bytes/key; on long string keys ART's space grows by 51% and Masstree's by 230% relative to integers, HOT's by 26%; HOT needs less space than the raw keys themselves for emails (43%) and URLs (74%) [A: Binna18 §6.3, Fig. 9]. HOT is also the trie shown to synchronize with a simple optimistic protocol [A: Binna18 §5; A: Leis16 for ART's Optimistic Lock Coupling and ROWEX].
- Swiss tables (abseil `flat_hash_map`, Rust `hashbrown`/`std::HashMap`): one control byte per slot holding a 7-bit second hash (H2) plus empty/deleted state; a group of control bytes is scanned with SIMD; probing continues over deleted slots and stops at empty ones [C: Abseil design note]. hashbrown 0.17.1 (the code behind Rust's `std::HashMap` on Rust 1.98) reserves 12.5% of slots empty (max load factor 7/8), uses triangular probing, tags EMPTY = 0xFF and DELETED = 0x80, and has NEON, SSE2 and generic group implementations whose width is the SIMD register size [C: hashbrown raw.rs `bucket_mask_to_capacity`, control/tag.rs, control/group/*.rs]. hashbrown's README claims ~2x the speed of the previous std map and 1 byte overhead per entry [C: hashbrown README; no independent benchmark fetched, treat the 2x as tier D].
- Concurrent hash tables: the "folklore" lock-free linear-probing table with word-sized keys/values is the fastest known; Maier, Sanders and Dementiev show growing/shrinking can be added at comparable cost and that the result is "an order of magnitude faster than the best more general tables"; finds proceed without any write [A: Maier19 abstract, §4]. Optimistic cuckoo hashing (Li et al.) reaches ~40 M req/s on 4 cores with 120 M keys and lock-free reads [A: Li14 Fig. 1]. Michael's lock-free hash table and Shalev-Shavit split-ordered lists are the classical lock-free designs [A: Michael02; A: Shalev06] (no numbers used from them here).
- What deployed file systems do: the Linux dcache is one global hash table keyed by (parent dentry pointer, name hash); the table is sized at boot by `alloc_large_system_hash("Dentry cache", ..., 13, ...)` (2^13 minimum buckets, scaled by memory) and lookups run under RCU with a per-dentry `d_seq` sequence count plus a global `rename_lock` seqlock that makes a lookup retry if a rename raced with it [C: Linux 7.2 fs/dcache.c; B: path-lookup.rst §"rename_lock", §"RCU and seqlocks"]. ScaleFS keeps each in-memory directory ("mdir") as a concurrent hash table from name to mnode number, with file pages in a radix array; creates of different names in the same directory touch different per-core logs and different hash buckets, so they are conflict-free [A: Bhat17 §5, Fig. 1]. EdenFS keeps directory contents in a `TreeInode` guarded by a `contents_` lock [C: EdenFS InodeLocks.md].
- Ordered vs unordered: git tree objects and Sapling tree-manifest entries are stored as name-sorted lists so that a directory's content hash is canonical [C: git object format; C: Sapling manifest-tree lib.rs: "sorted lists of (name, child_hash, type)"]. POSIX `readdir` does not promise an order, but any snapshot/dedup design that wants a Merkle hash per directory needs a canonical order, and range/prefix iteration is what glob and "list this subtree" need. A pure hash table gives O(1) lookup but no order; a sorted array or B-tree gives order and O(log n) lookup; a trie (ART/HOT) gives both order and near-hash lookup at 8-15 bytes/key [A: Leis13; A: Binna18].

**Full-path resolution cost.**
- Resolution is one directory lookup per component; the Linux VFS caches every successful component in the dcache, and RCU-walk then resolves cached components with no locks or atomics, retrying only when a `d_seq`/`rename_lock` check fails [B: path-lookup.rst]. For a FUSE/NFS/WinFsp bridge this means the daemon mostly sees LOOKUP for the *last* component after the cache is warm, and full paths only on cold caches or when entry timeouts expire (bridge-side details are in the sibling note `os-filesystem-bridge.md`).
- Path depth is small: the median directory depth in the 2004 Microsoft dataset was 6 (mean 6.9) [A: Agrawal07 §4.3]; the measured trees above have maximum depth 5-12 [M]. So per-component O(1) expected lookup makes full-path resolution O(depth) with depth ~6-12, and the design lever is per-component constant, not asymptotics.

**Inode/handle tables.**
- EdenFS assigns inode numbers "on demand when an inode is first accessed" from "a monotonically increasing 64-bit ID", and stores the assigned numbers in the overlay so they survive restarts; its `InodeMap` maps inode number to object and keeps enough information about unloaded inodes to recreate them if the kernel looks the number up again [C: EdenFS Inodes.md; C: InodeLifetime.md].
- ScaleFS never reuses inode numbers: "inode numbers are generated by a monotonically increasing per-core counter, concatenated with the core number that allocated the inode", which is legal because POSIX only forbids two simultaneously existing files sharing a number; this makes allocation scalable and lets inode garbage collection be deferred [A: Clements13 §7 / A: Bhat17 §5.1]. The same paper's rule of "embrace specification non-determinism": `creat` may assign any unused inode number, whereas the "lowest available FD" rule kills scalability [A: Clements13 §4].
- The generational-index pattern is what FUSE itself expects: each entry reply carries an (ino, generation) pair, and the pair must be unique over the file system's lifetime if it is exported over NFS [C: libfuse fuse_lowlevel.h `fuse_entry_param.generation`].
- Implication for slates: a per-volume slab of inode records addressed by (slot index, generation); inode *numbers* handed to the kernel are (core/volume prefix, monotonically increasing counter) and never reused within a volume's lifetime; slots are reused but only after the generation is bumped, so a stale FUSE handle can never alias a new file.

**Hard links.**
- POSIX: `st_ino` + `st_dev` uniquely identify a file, `st_nlink` counts links, and `rename` of two names for the same file succeeds and does nothing [B: POSIX sys/stat.h; B: POSIX rename]. EdenFS does not support hard links because it requires each inode to have exactly one parent (needed for its parent-pointer/path bookkeeping) [C: EdenFS Inodes.md]. The Scalable Commutativity paper's `statbench` shows `fstat` scalability collapses when `st_nlink` is a shared counter, and recovers with Refcache (per-core counters that are only reconciled when the value may have reached zero) [A: Clements13 §7.2 Fig; A: Clements13b §3.1].
- Implication: hard links to regular files are cheap if the *directory entry* (not the inode) carries the name and the inode carries only `nlink`; the only cost is that "path of inode" is no longer unique, which matters for change journals and watchers (record the entry path in the journal, not the inode). Directory hard links are forbidden by POSIX except `.`/`..`, which keeps the tree a tree and keeps rename-cycle checks simple.

**Rename atomicity and directory-cycle prevention.**
- POSIX requires that when `new` exists, "a link named new shall remain visible to other threads throughout the renaming operation and refer either to the file referred to by new or old before the operation began"; `old` "shall not name an ancestor directory of new" (EINVAL); renaming a directory over a non-empty directory fails with EEXIST/ENOTEMPTY; file-over-directory is EISDIR [B: POSIX rename].
- EdenFS takes a mount-wide rename lock "for the duration of a rename or unlink operation", acquired before any inode-specific lock; renaming a directory over an empty directory additionally holds the destination's `contents_` lock "to ensure that it is empty, and to prevent new entries from being created inside this directory", so a rename can hold up to three `TreeInode` locks (source dir, destination parent, destination child); creates do not take the rename lock [C: EdenFS InodeLocks.md; C: Rename.md]. Linux similarly serializes cross-directory renames per superblock (`s_vfs_rename_mutex` in `lock_rename`) and checks ancestry under it [C: Linux fs/namei.c].
- The commutativity analysis shows two renames commute when both sources exist and all four names differ, or when one's source does not exist and is not the other's destination, etc. [A: Clements13 §5.1 Fig. 4]: renames rarely conflict, so serializing *cross-directory* renames per volume is a correctness convenience whose cost only matters if rename rate is high (see §5: measure rename rate under cargo/npm/git workloads).
- Cycle check: walk from the destination's parent to the root comparing inode ids against the source directory; O(depth) with depth ~6-12 [M; A: Agrawal07]. In a persistent-tree design (see §2.2) the walk is over parent pointers that the writer owns exclusively, so no extra locking is needed.

**Case sensitivity and Unicode normalization.**
- APFS: "case-insensitive by default"; in both variants it is *normalization-insensitive* using a hash of the normalized form of the name while preserving the bytes as written; it accepts only valid UTF-8 names; it implements normalization and case folding per Unicode 9.0 (HFS+ used Unicode 3.2 and stored the decomposed form) [B: Apple APFS Guide FAQ].
- Windows: "Do not assume case sensitivity"; NTFS preserves case but names are compared case-insensitively by default; "NTFS supports POSIX semantics for case sensitivity but this is not the default"; reserved names (CON, PRN, AUX, NUL, COM1-9, LPT1-9, also with extensions), reserved characters `< > : " / \ | ? *`, no trailing space or period; `MAX_PATH` = 260 unless the `\\?\` prefix (or the long-path opt-in) is used [B: Microsoft "Naming Files, Paths, and Namespaces"]. Since Windows 10 build 17107 a directory can be flagged case-sensitive (`fsutil file setCaseSensitiveInfo <dir> enable`); the flag is inherited by new subdirectories and applies to NTFS only; changing it requires an empty directory [B: Microsoft WSL "Case Sensitivity"].
- git: `core.ignoreCase` is "an internal variable which enables various workarounds ... on filesystems that are not case sensitive, like APFS, HFS+, FAT, NTFS" and is probed and set by `git clone`/`git init`; `core.precomposeUnicode` (macOS only) "reverts the unicode decomposition of filenames done by Mac OS" so that the index holds precomposed names; `core.protectHFS`/`core.protectNTFS` refuse paths equivalent to `.git` under HFS+ folding or NTFS 8.3 short names [C: git-config(1), git 2.50.1]. EdenFS's path documentation defines component/relative/absolute path types and length limits but says nothing about case folding [C: EdenFS Paths.md]; its Windows document notes ProjFS placeholder states but not case handling [C: EdenFS Windows.md].
- Implication: names must be stored as the exact bytes the client wrote (UTF-8 validated where the host requires it), and each volume carries a *name-equivalence policy* fixed at creation: byte-exact (Linux default), Unicode case-fold + normalization-insensitive (macOS default), or case-fold only (Windows default). Insensitive lookup is made O(1) by indexing on the hash of the folded/normalized key and comparing folded forms on collision, which is exactly APFS's technique [B: Apple APFS FAQ]. Equality under a policy must be stable for the life of a volume (git probes it once); a mismatch between policy and the host bridge is how `.git` path attacks and duplicate-entry confusion arise [C: git-config core.protectHFS/NTFS].

**Scale evidence.**
- Google's Piper/CitC: the repository is described as one billion files, 35 million commits, tens of thousands of developers [A: Potvin16 abstract]; secondary notes on the paper report 2 billion lines of code, 86 TB, ~800k queries/s, and that CitC workspaces "are directories in the file system", show the full repository with local changes overlaid, and store "all writes to files ... as snapshots" that can be named and restored [D: florian reading notes on Potvin16; the CACM page itself returned 403 in this session, so the 86 TB / 800k QPS figures are flagged as not re-verified against the primary].
- EdenFS targets repositories "spanning many millions of files", lazily fetching only what is used [C: EdenFS Overview.md]; it runs 16 FUSE dispatcher threads per mount by default, plus an unbounded FsChannel pool sized to the core count [C: EdenFS Threading.md].
- ScaleFS is conflict-free for 99.2% of the commutative test cases Commuter generates (Linux ext4: 65%) and scales on an 80-core machine [A: Bhat17 §1, §8]; sv6 (its predecessor) is conflict-free for 13,528 of 13,664 tests, Linux for 9,389 [A: Clements13 §1].

**Decision inputs for §4.** A directory in slates should be a *sorted* small array up to a measured cut-over (start value 16-32 entries, the size of one SIMD group / two cache lines of 8-byte name hashes, matching ART's Node16 and Swiss-table groups [A: Leis13; C: hashbrown]) and beyond that a sorted structure with a hash side-index, so that (a) lookup stays O(1) expected via the hash, (b) iteration is canonical and Merkle-hashable, (c) the immutable snapshot copy of a directory is a flat, contiguous, cache-friendly array (HOT/ART-like footprints of ~12-16 bytes/key are the target, not std `HashMap`'s inline key+value+control byte at 7/8 load).

### 2.2 Snapshot and clone mechanism

Terms: *snapshot* = an immutable, readable version of a volume. *Clone* = a writable volume forked from a snapshot. *Copy-on-write (CoW)* = never modify a shared node in place; write a modified copy and re-point the parent. *Shadowing* = Rodeh's name for strict CoW where every modification re-points ancestors up to the root. *Path copying* = the persistent-data-structure name for the same thing. *Reference count (refcount)* = a per-node count of how many parents/versions point at it. *Birth time / birth epoch* = the version number (ZFS: transaction group, "txg") at which a block or node was created. *Deadlist* = ZFS's per-snapshot list of blocks freed from the live dataset that an older snapshot still references. *HAMT* = hash array mapped trie, a persistent hash map with 32-way bitmap-indexed nodes. *Merkle tree* = a tree in which each node's identifier is a hash of its children's identifiers. *Materialized* (EdenFS) = an inode whose content is no longer identical to a known immutable object and so lives in the mutable overlay.

**(a) CoW B-tree with lazy reference counting (Rodeh 2008; basis of Btrfs).**
- Cloning a tree: "(1) Copy the root-node of Tp into a new root. (2) Increment the free-space counters for each of the children of the root by one." Refcounts live in the free-space map, not in nodes; a node with refcount 1 is modified in place (normal shadowing), while a shared node (refcount > 1) is relocated: the old location's count is decremented, the new copy gets count 1, and "the ref-count of N's children is incremented by 1" - this is what makes the counting lazy: nodes deep in a shared subtree keep refcount 1 until the path above them is split [A: Rodeh08 §5.1-5.3, Fig. 11].
- Costs versus WAFL: "A single byte per block is sufficient for supporting 256 clones" against WAFL's 32 bytes; "Only the children of the root of a b-tree are involved in snapshot creation" against WAFL's full pass over the free-space map on create and delete; single-file clones are possible; deletion "traverses only the nodes that belong only to p and decrements ref-counters"; the price is "additional costs when updates occur" (refcount maintenance on the write path) [A: Rodeh08 §2.2, §5.6].
- Node size in the paper: 4 KiB pages holding between b and 2b+1 entries with pro-active split/merge on the way down so that a single top-down pass suffices (no b-link chaining, no leaf chaining, which strict shadowing forbids) [A: Rodeh08 §4]. Write amplification is inherent: "Modifying a leaf requires shadowing up to the root" [A: Rodeh08 Fig. 1].

**(b) Birth-time snapshots without per-block refcounts (WAFL, ZFS/OpenZFS).**
- WAFL creates a snapshot by duplicating the root inode: "a brand new Snapshot consumes no disk space except for the Snapshot inode itself"; sharing is tracked by a 32-bit block-map entry per 4 KiB block with one bit per snapshot, which is why it keeps "up to 20 Snapshots on-line at once" and why creating a snapshot copies the active bit into a snapshot bit across the map [A: Hitz94 §3.4, §4.1, Fig. 5].
- ZFS keeps a birth transaction group in every block pointer and needs no per-block counts. In OpenZFS `dsl_dataset_block_kill`: if `BP_GET_BIRTH(bp) > ds_prev_snap_txg` the block is freed immediately (`dsl_free`) and `ds_unique_bytes -= used`; otherwise it is inserted into the dataset's deadlist (`dsl_deadlist_insert`) because an earlier snapshot still references it; in both branches `ds_referenced_bytes -= used`. `dsl_dataset_block_born` adds `used` to both `ds_referenced_bytes` and `ds_unique_bytes` (a new block is unique until a snapshot is taken) [C: OpenZFS module/zfs/dsl_dataset.c]. Deadlists "can only be modified from the syncing thread" (single writer), and readers use read locks [C: OpenZFS dsl_deadlist.c header]. OpenZFS partitions each deadlist into sub-lists keyed by birth txg so that destroying a snapshot moves whole sub-lists to the neighbouring snapshot instead of walking blocks; this detail is from the same source file's structure and should be re-verified when the accounting module is written (see §5).
- Consequences: snapshot creation is O(1) (record the current root and txg; open an empty deadlist), freeing is O(1) per block with a single comparison, and the only walk is at snapshot destruction, proportional to that snapshot's deadlist. The scheme relies on snapshots of one dataset forming a *chain*; clones fork the chain from an origin snapshot and get their own deadlist, and OpenZFS adds "livelists" for clones with entries "grouped by birth txg so we can be sure the ALLOC/FREE pair for a given blkptr will be in the same entry" [C: dsl_deadlist.c "Livelist Overview"]. The 2003 ZFS paper describes transactional copy-on-write of all blocks and pooled storage but only announces snapshots as forthcoming, so the mechanism's tier-A description is Hitz94 plus the OpenZFS source [A: Bonwick03 §8-9].

**(c) Persistent functional structures (HAMT, CHAMP, RRB, persistent B-trees).**
- Bagwell's HAMT indexes 32-way nodes by 5-bit hash slices with a bitmap and a population count, giving "single access searches, close to single access inserts and greater than 80 percent disk block load factors", i.e. O(log32 n) ~ effectively constant depth [C: Bagwell01 abstract; a widely deployed technical report, basis of Clojure/Scala maps]. Immutability comes from path copying: an update copies the O(log32 n) nodes on the path (each <= 32 slots), never the whole map.
- CHAMP (Steindorfer & Vinju) reorders HAMT node layout (payload before sub-nodes, two bitmaps) and memoizes hashes; against Clojure it cuts map footprint by 64% and set footprint by a median of 52%, against Scala by 15%/31%; iteration is 1.3-6.7x faster and equality checking 3-25.4x faster [A: Steindorfer15 §1].
- RRB vectors give an ordered persistent sequence with effectively-constant-time indexing/update and logarithmic concatenation and split [A: Stucki15; abstract only - the ACM page returned 403 in this session, so no number from it is used].
- A persistent B-tree (fanout f, ordered) has the same path-copying cost profile as a HAMT but keeps sorted order; that is what Rodeh's structure is when the refcounting is removed. All of these are "O(1) snapshot" (retain the root) and "wait-free reader" (readers never see mutation) by construction, and none needs per-node counts as long as *something* else (epochs, refcounts on versions, or a tracing collector) decides when a node is unreachable.

**(d) Merkle-tree manifests with a materialized overlay (git, Sapling, EdenFS).**
- git and Sapling represent a directory as an immutable object listing sorted (name, id, type) entries; identical directories hash identically "regardless of path", so a commit is a root hash and unchanged subtrees are shared by identity [C: Sapling manifest-tree lib.rs; C: git tree objects]. Sapling's in-memory `TreeManifest` has three link states - `Leaf` (file), `Durable` (immutable tree loaded by hash), `Ephemeral` (mutable, modified in this session) - and `persist()` "walks the entire tree, converting ephemeral nodes to durable ones by computing content hashes and writing to storage", skipping subtrees whose hash matches the parent's [C: manifest-tree lib.rs]. This is copy-on-first-write with hashing deferred to commit time.
- EdenFS layers a mutable inode state over an immutable commit: an inode is materialized when EdenFS "does not know a source control object ID" for it; materialization cascades upward ("all parent directories up to the root must also materialize since the directory contents no longer match the source control tree"); "even if the file is later modified to have its original contents again EdenFS may keep the file materialized"; tree entries may also carry file size and content hash so `stat` does not need the blob [C: EdenFS Inodes.md; Glossary.md; Data_Model.md]. EdenFS does not require object ids to be content hashes, only that they be 20-byte lookup keys [C: Data_Model.md].
- Costs: snapshot = flush (hash every ephemeral directory on modified paths: O(modified directories x their sizes) hashing work, plus O(1) to record the root); clone = O(1) (new overlay over the same root); write = O(depth) materialization the first time, then in place; deletion = drop the overlay; GC of the object store is by reachability from roots (git uses tracing `gc`/`prune`). Merkle ids give free deduplication of identical subtrees and a content-addressed unit for archive/replication (§2.5).

**(e) Operation logs (ScaleFS/oplog).**
- ScaleFS keeps an in-memory file system built from concurrent structures and, separately, per-core operation logs (link, unlink, rename, ...) with "timestamped linearization points" from synchronized CPU timestamp counters; `fsync` sorts and merges the per-core logs, absorbs cancelling operations (e.g. create then unlink) and tracks dependencies, then applies them to the on-disk representation; per-core appends need no coordination, so commutative operations stay conflict-free [A: Bhat17 §1, §5]. An op-log is therefore a *commit/replication* mechanism layered on a read structure, not a substitute for one: reading a snapshot from a raw log means replaying it.

**Write amplification of path copying, quantified from measured tree shapes [M; A: Agrawal07].**
- Copying a whole directory node per write costs the sum of the sizes of the directories on the path. With a 61,067-entry `deps/` directory (Cargo target) at ~16 bytes per entry, every file write under it would copy ~1 MB of directory entries, roughly 1,000x a 1 KiB write. Even the p99 directory (37-181 entries) costs 0.6-3 KiB per write, comparable to the median file itself (1-7 KiB, §2.3).
- Splitting directories into persistent B-tree/HAMT nodes of at most f entries bounds the copy to depth x ceil(log_f(dir size)) x f entries: with f = 32 and the measured worst path (depth <= 12, one 61k-entry directory, others tiny) that is ~12 x 1 x 32 + 4 x 32 entries ~ 0.5k entries ~ 8 KiB per first write, and ~200 entries ~ 3 KiB for a typical path [arithmetic on M].
- Birth epochs remove the *per-write* copy entirely: a node born in the current epoch (i.e. after the latest snapshot) is mutated in place (ZFS's `birth > prev_snap_txg` test, Rodeh's `refcount == 1` test); only the first write to each node after a snapshot pays the path copy [C: OpenZFS dsl_dataset.c; A: Rodeh08 §5.3]. For Cargo builds that write ~190k files between snapshots, this is the difference between O(files x path) and O(files + distinct directories touched) copying.

**Deletion/GC cost by scheme.**
- Refcount (Rodeh): exact and immediate for arbitrary clone DAGs; cost O(nodes exclusively owned by the deleted version + shared boundary); 1 byte/node for 256 sharers [A: Rodeh08 §5.6]; every shadow of a shared node writes counts for all its children, which on a shared-memory multi-core design needs per-core delta caching (RadixVM's Refcache flushes per-core deltas every epoch, 10 ms in its implementation, and detects true zero only after a full epoch of stability) [A: Clements13b §3.1].
- Birth epoch + deadlists (ZFS): no per-node counts; free is one comparison; destroy walks only that snapshot's deadlist; clones need an origin snapshot that stays alive (hidden if the user destroys it) while clones exist, which is a refcount on *snapshot objects* (one integer each), not on nodes [C: OpenZFS dsl_dataset.c; B: zfsprops(7) "origin", "clones"].
- Tracing (git gc): exact, no write-path cost, but O(live objects) per collection and unbounded pause; nothing in the file-system literature surveyed uses it in the hot path.

**Wait-free readers on immutable versions, and ownership without `Arc`.**
- In every scheme above, a reader of a snapshot touches only nodes born at or before that snapshot's epoch, which no writer will modify; the reader needs (1) the snapshot root and (2) a guarantee that the nodes will not be *freed* during the read. (2) is a property of the snapshot object (pinning) or of the reclamation scheme (§2.4), never of individual nodes. Rodeh's design already states the principle: counters "are physically located in the free-space maps", not in the nodes [A: Rodeh08 §5]. Linux dcache readers likewise hold no per-dentry reference during RCU-walk; they sample sequence counts and retry [B: path-lookup.rst].
- Therefore nodes can live in a per-volume arena addressed by 32-bit indices, owned by exactly one core; sharing between versions is a fact recorded in side tables (birth epoch per node, one refcount per snapshot), and `Arc` is unnecessary. The remaining question - can a reader on another core read a snapshot while the owner writes new versions - is the concurrency choice of §2.4.

**Comparison.**

| Criterion | (a) CoW B-tree + lazy refcount | (b) Birth epoch + deadlist | (c) Persistent HAMT/B-tree (pure) | (d) Merkle + overlay | (e) Op-log |
|---|---|---|---|---|---|
| Clone cost | O(root fanout) [A: Rodeh08] | O(1) [C: OpenZFS] | O(1) | O(1) after flush; flush = hash modified dirs [C: Sapling] | O(1) to mark, O(log) to read |
| Per-snapshot memory | root copy + counters on root's children | snapshot record + empty deadlist | root pointer | root hash + retained durable nodes | log position |
| Write amplification | first write after clone copies path and bumps child counts; in place when count == 1 | first write after snapshot copies path; in place when born in epoch | every write copies path (O(depth x f)) | first write materializes path (O(depth)); in place after | append only; read side pays |
| Deletion / GC | exact, immediate, O(exclusive nodes) | O(deadlist); clones pin origin | needs external reclamation (epochs/tracing) | tracing by reachability (git gc) | replay/compaction |
| Wait-free readers on snapshots | yes | yes | yes | yes | no (replay) |
| Fits thread-per-core, no Arc | yes if counts are owner-core plain integers | yes; single "syncing thread" already the ZFS model | yes | yes | yes |
| Arbitrary clone DAGs | native ("clones as first class citizens") | via origin snapshots (chain + forks) | native | native | awkward |
| Dedup of identical subtrees | no | no | no | yes (by hash) | no |

**Decision (details in §4).** Use (b) as the core mechanism - a per-volume arena of persistent ordered nodes with a birth epoch per node, snapshots as O(1) records with deadlists, clones as forks with origin pinning - because it has the lowest write-path cost (a comparison instead of refcount writes), the smallest per-node overhead (an epoch number that is needed anyway for accounting), O(1) snapshot/clone (the 50 µs provisioning budget), and 30 years of deployment in WAFL/ZFS. Add (d)'s Merkle hashing *lazily* at commit/archive/replicate time (Sapling's `persist()`), so identical subtrees dedup and the archive unit is content-addressed, and use (e) for shipping changes between machines. Runner-up: (a) lazy refcounts - exact GC for DAGs and single-file clones, but it puts writes on the write path and per-node counters that are contended unless per-core-cached [A: Clements13b]. Rejected as the primary structure: (c) pure path-copying (amplifies every write) and (e) alone (reads must replay).


### 2.3 File content representation

Terms: *extent* = a contiguous byte range of a file backed by one chunk (or a hole). *Chunk* = an immutable unit of content bytes. *Content-defined chunking (CDC)* = cutting a stream where a rolling hash of a small window hits a pattern, so boundaries survive insertions. *Rope / piece table* = editor structures that represent a file as a sequence of references into immutable buffers.

- What tools actually write [M; C]: git writes whole objects and whole files (checkout writes each file once, then renames temp files into place); rustc/cargo create many small files and append to a few large ones (`deps/*.rlib`, incremental caches); editors write a temp file then rename; npm creates tens of thousands of files under 4 KiB with the median well under one page; large binaries (toolchains, `target/` artifacts) are written sequentially once. Microsoft's five-year study puts the median file at a few KiB with the byte mass in large files ("most bytes are in files > 1 MiB") [A: Agrawal07 §3]; Meyer & Bolosky report the same skew ("storage being consumed by files of increasing size") [A: Meyer11 §3].
- Consequence: two regimes. Small files (the count) are one chunk each and dominate metadata cost; large files (the bytes) are sequences of chunks and dominate memory and copy cost. sylk stored one chunk per write with no re-chunking, which destroyed dedup between versions and made small edits of big files cost the whole file [C: survey-sylk-vfs.md §1.1, §8.2].
- Representation chosen (details §4): a file's body is an extent list keyed by logical offset (a small sorted array for the common case, a persistent B-tree beyond a measured cut-over), each extent pointing at a chunk handle plus (offset, length) within it, with a `Zero` extent kind for holes; chunks are page-multiple buffers in the per-volume arena, sized as a multiple of the *measured* base page (4 KiB x86, 16 KiB Apple Silicon, 4/16/64 KiB Linux arm64 by kernel build) so a chunk is always DMA/splice/mmap friendly [B: hugetlbpage.rst; B: Apple vm_page_size guidance]. Writes go to an owned, mutable "open extent" of the file until close/snapshot ("seal"), at which point the dirty range is re-chunked (fixed page-multiple chunks by default; content-defined chunks only for files above a measured size threshold where insert-shifting matters, per `compression-archive-dedup.md` §2.4), hashed lazily, and deduplicated. This is EdenFS's materialized-inode model with hashing deferred to seal time [C: EdenFS Inodes.md; C: Sapling manifest-tree `persist()`].
- Zero-copy paths: FUSE `splice` moves reply pages without a copy only for reads above two pages and writes above one page [A: Vangoor et al. TOS 2019 §2.6]; with page-aligned chunks a read reply is one or more whole pages, so the daemon replies with references into the arena and never memcpy's; with FUSE-over-io_uring registered buffers the same pages are the ring's buffers [B: fuse-io-uring.rst]. mmap by a client is served from the kernel page cache filled by those replies; the daemon never maps its arena into client processes (hecate's DAX leak argument: a shared slab page could expose another volume's bytes) [C: survey-hecate.md §8.4 item 5].
- Choosing the chunk size from data, not a constant: the daemon measures (a) the base page size, (b) memcpy and hash throughput per size (boot calibration), and (c) the per-volume file-size histogram as files are sealed; the small-file chunk is one page-multiple that holds the p50-p90 file whole; the large-file chunk is the size where per-chunk fixed cost (a manifest entry, a hash, an extent) falls below a measured fraction of the copy cost, which on the cited hardware is in the 64 KiB-1 MiB band (sylk chose 64 KiB by fiat; FastCDC's 8 KiB expected size targets dedup, not copy cost) [A: Xia16; C: survey-sylk-vfs.md §7.4]. The value is recorded per volume and per machine profile; it is not a compile-time number.

### 2.4 Concurrency and lock-freedom

- The Scalable Commutativity Rule: whenever interface operations commute, there exists a conflict-free (scalable) implementation; sv6 is conflict-free for 13,528 of 13,664 generated cases versus 9,389 for Linux [A: Clements13]. The rule's practical advice for a file system: allocate inode numbers and file descriptors without a "lowest available" constraint, keep per-directory state separate, and avoid shared counters (Refcache) [A: Clements13 §4, §7].
- ScaleFS: per-core operation logs merged at `fsync`, conflict-free for 99.2% of commutative cases on an 80-core machine [A: Bhat17]. RadixVM: per-core reference counting with epoch-based reconciliation (10 ms epochs) so `mmap`/`munmap` of disjoint regions scale [A: Clements13b]. Linux dcache: RCU-walk path lookup with per-dentry `d_seq` and a global `rename_lock` seqlock; readers take no locks and no atomics; a concurrent rename forces a retry [B: path-lookup.rst; C: fs/dcache.c].
- Message passing versus shared memory: ffwd's delegation to a single server core costs ~40 cycles per request and beats locks by up to 10x for short critical sections, bounded by one cache-line transfer each way (~80 ns intra-socket) [A: Roghanchi17]; Barrelfish's URPC delivers a cache-line-sized message in ~450 cycles [A: Baumann09]; the cross-core cache-line transfer costs 50-150 ns on one socket or one Apple cluster and 150-400 ns across sockets or across the P/E boundary [A: David13; A: Molka09; A: Schweizer15; D: nviennot core-to-core]. An epoch-protected read on the reader's own core costs one plain store per event-loop iteration (QSBR) and zero fences on the read path [A: Hart06 §3.1] (see `database-design.md` §2.3).
- Two candidate architectures: (i) shared-nothing, one shard owns each volume, every operation (including reads from bridge threads) is routed to the owner over a ring: ~0.5-1 µs per request when both sides poll, no reclamation, deterministic; (ii) published-snapshot reads, the owner writes new versions and publishes the root with a release store, any core reads the immutable snapshot under QSBR: sub-100 ns reads, but the read path must never touch a node born after its epoch and every mutation must be path-copied (not in-place), which conflicts with the in-place-when-born-this-epoch rule of §2.2.
- Decision (§4): a hybrid. Mutations and *metadata* reads of a volume go to the owning shard (design (i)); the bridge queue for a volume is pinned to the same shard when the bridge allows it (FUSE-over-io_uring per-core queues; `FUSE_DEV_IOC_CLONE` channels; WinFsp dispatch threads handed to shards by handle), so most requests never cross a core. *Content* reads of sealed chunks (immutable by construction) are served from any core without a message, because a sealed chunk never changes and its lifetime is pinned by the snapshot the reader holds (design (ii) restricted to immutable data). Wait-free readers on immutable data plus a single writer per volume is the ZFS "syncing thread" model and the Linux dcache model at once [C: OpenZFS dsl_deadlist.c; B: path-lookup.rst].

### 2.5 Deduplication and content addressing

- BLAKE3: 256-bit output, a binary tree over 1 KiB chunks, so hashing parallelizes across SIMD lanes and cores and any subtree can be verified independently (Bao) [C: BLAKE3 spec/paper]. Throughput tables in the paper (Cascade Lake-SP with AVX-512, cycles per byte; a 48-core machine in GiB/s; an ARM1176 in cycles per byte) show it ahead of SHA-256 and SHA-1 on every platform measured [C: BLAKE3 paper §5, tables at lines 395-536 of the local extract]; per-platform absolute throughput is a must-measure (5.8 GB/s with AVX-512 on an i3-1005G1 versus 380 MB/s with NEON on a Raspberry Pi 4 in OpenZFS's benchmarks [D: openzfs PR 12918]).
- Content-defined chunking: LBFS cut at Rabin fingerprints over 48-byte windows with 2 KiB minimum, 8 KiB expected, 64 KiB maximum [A: Muthitacharoen01 §3.1]; FastCDC is ~10x faster than Rabin-based CDC and ~3x faster than Gear/AE by using a gear hash, cheaper cut-point judgment, skipping the minimum, and *normalized chunking* that narrows the size distribution around the 8 KiB target [A: Xia16 §1, §3]; Data Domain's Summary Vector (Bloom filter), Stream-Informed Segment Layout and Locality Preserved Caching remove 99% of index disk accesses [A: Zhu08] (their locality lesson transfers to an in-memory index as cache-line locality).
- Whole-file versus block dedup: on 857 desktop file systems, whole-file dedup "achieves about three quarters" of the space savings of aggressive block-level dedup for live file systems and 87% for backups [A: Meyer11 abstract, §4]. For slates the live corpus is source trees and build outputs; whole-file content addressing plus page-multiple chunks for large files captures the bulk; CDC is reserved for the large-file class where a measured dedup gain justifies its CPU cost.
- When hashing pays: hashing costs measured cycles per byte; a saved chunk saves its bytes for the lifetime of the sharing; the daemon hashes at seal time (never per write), skips hashing for chunks of volumes whose measured dedup hit rate is below the cost of hashing them (tracked per volume as an EWMA), and always hashes at archive/replicate time because content identity is the transfer unit [A: Zhu08; A: Meyer11]. Clone and snapshot need no hashing at all (they share by reference); dedup across volumes is a background pass on sealed chunks.

### 2.6 Exact space accounting for bounded volumes

- ZFS tracks `referenced` (bytes reachable from the dataset) and `used`/`unique` (bytes freed only when this dataset or snapshot goes away); `dsl_dataset_block_born` adds to both, `dsl_dataset_block_kill` subtracts `referenced` always and `unique` only when the block was born after the previous snapshot, otherwise the block moves to the deadlist [C: OpenZFS dsl_dataset.c]. Btrfs qgroups track `rfer` (referenced) and `excl` (exclusive) per subvolume and charge shared extents to every qgroup that references them for `rfer` and to none for `excl` until the last sharer [C: Btrfs qgroups design].
- O(1) ENOSPC for a bounded volume: charge the volume for every chunk it *references* (ZFS `referenced` semantics) at the moment the reference is created (write, clone, restore), and release the charge when the reference is dropped; a shared chunk is charged to each referencing volume in full (no fractional accounting), which is exact, O(1) per write, and conservative (a clone costs its full referenced size on paper while sharing memory physically). The physical host budget is charged once per chunk (owner core's arena counters). Two counters per volume, both plain integers on the owning shard: `referenced_bytes` (drives ENOSPC against the quota) and `unique_bytes` (what destroying the volume would free); both are exact by construction because every reference change passes through the owner.
- Dynamic volumes: grow the reservation in slab increments taken from the host budget when `referenced_bytes` approaches the current reservation; the increment and the headroom derive from the measured allocation burst rate of that volume (bytes per second over the recent window) and the measured free memory and pressure signals (`memory-and-system-awareness.md` §2.4), so growth is neither a fixed percentage nor a fixed size.

### 2.7 Metadata for POSIX and Windows semantics

- Store per inode: kind, mode bits (with the executable bit, which git tracks), uid/gid (as reported to the kernel; a volume-wide identity map), size, `nlink`, `atime`/`mtime`/`ctime`/`btime` with nanosecond fields (Linux and macOS report ns; Windows 100 ns ticks), the inode number (monotonic, never reused within a volume, generation-guarded) and, when sealed, the content identity. Extended attributes are optional per volume (NFSv3 cannot carry them [C: EdenFS macOS.md]; WinFsp offers streams/EAs behind flags); Windows attributes (hidden, readonly, archive) map to mode bits and a small flags word.
- What tools depend on: git needs the executable bit, stable inode numbers only for its index racy-git heuristics (mtime + size + inode), and `core.precomposeUnicode`/`core.ignoreCase` probing [C: git-config(1)]; cargo/rustc key incremental caches on mtime and size, so mtimes must not move when content is unchanged (EdenFS learned this the hard way: forgotten inode numbers advanced mtimes and broke incremental builds) [C: EdenFS InodeStorage.md]; editors and watchers rely on inode stability to track renamed files; Watchman/inotify need a change feed with ordering (the journal) [C: EdenFS Journal.h].
- Inode stability across snapshots and restarts: inode numbers are properties of the volume, allocated at first exposure and kept in the manifest, so a re-attached snapshot presents the same numbers it presented before (the FUSE `generation` field distinguishes reuse after destroy) [C: EdenFS Inodes.md; C: libfuse fuse_entry_param]. A clone gets fresh numbers in its own space (different `st_dev` per volume), so two clones of one snapshot never alias.

## 4. Recommendation for slates

1. **Namespace**: per directory, a sorted small array of (name hash, name, child handle) up to a measured cut-over (start: one SIMD group of hashes), then a persistent ordered node structure (B-tree-shaped, fanout chosen so a node fills a small number of cache lines) with a hash side index; names stored as exact bytes with a per-volume equivalence policy (byte-exact, Unicode fold+normalize, case-fold) fixed at creation and applied through a folded-key hash, as APFS does. Inodes in a per-volume slab addressed by (slot, generation); inode numbers monotonic and never reused within a volume. Hard links to files supported (nlink on the inode, path in the journal); directory hard links refused. Cross-directory renames serialized per volume (one owner, so serialization is free); the cycle check walks parent pointers the owner exclusively holds. Runner-ups: hash-only directories (no canonical order for Merkle hashing and readdir), HOT/ART for every directory (excellent for the tail, wasteful for the p90 case), a global dcache-style table (needs RCU machinery the owner model makes unnecessary).
2. **Snapshot mechanism**: birth-epoch copy-on-write over persistent ordered nodes (ZFS/WAFL), snapshots as O(1) records with deadlists, clones as forks pinning their origin, in-place mutation of nodes born in the current epoch, Merkle content identities computed lazily at seal/archive/replicate time (Sapling `persist()`), an operation log per volume for change feeds and shipping. Runner-ups: lazy refcounted CoW B-tree (exact DAG GC but refcount writes on the write path), pure path copying (amplifies every write), operation log alone (reads replay).
3. **Content**: page-multiple chunks in per-volume arenas; extent lists keyed by offset; open mutable extents until seal; re-chunk, hash and dedup at seal; CDC only for the measured large-file class; holes as `Zero` extents; replies by reference (splice/io_uring buffers), never mapping the arena into client processes.
4. **Concurrency**: one owning shard per volume for all mutations and metadata; bridge queues pinned to the owner where the OS allows; sealed-chunk reads served from any core without messages; no locks, no `Arc`, no reclamation machinery inside a volume; QSBR only for the few cross-shard read-mostly tables.
5. **Dedup**: whole-object first (content identity of sealed chunks), page-multiple chunks for large files, CDC for the measured class; hashing never on the write path; per-volume hashing enabled when the measured hit rate pays for the measured hash cost; BLAKE3 fixed as the identity for format stability.
6. **Accounting**: `referenced_bytes` and `unique_bytes` per volume as plain integers on the owner; bounded volumes reserve their quota at creation and refuse with ENOSPC when `referenced_bytes + request > quota`; shared chunks charged in full to each referencer; dynamic volumes grow in measured increments against measured free memory and pressure.

## 5. Risks, unknowns, must-measure-at-runtime

- The directory cut-over between the sorted array and the indexed structure; the persistent node fanout; the small-file and large-file chunk sizes; the CDC size threshold; the per-volume hashing hit-rate threshold: all measured (page size, cache line, memcpy/hash throughput, file-size histogram, dedup hit rate) and recorded per machine profile and per volume.
- Rename rate under real workloads (cargo, npm, git) decides whether per-volume rename serialization is ever visible; measure in the workload suite.
- Unicode folding tables (Unicode version) must be pinned per volume policy version so equality never changes for a live volume.
- The Piper/CitC secondary numbers (86 TB, 800k QPS) were not re-verified against the CACM page this session; the primary citation is retained and the numbers flagged.
- The OpenZFS deadlist sub-list-by-birth-txg detail should be re-read from source before the accounting module is implemented.
