Terms of art (one line each):
- Page: the unit of virtual-to-physical mapping the MMU uses; the smallest granule the OS can back, protect, or swap.
- Huge page / superpage / large page: a single mapping covering many base pages (2 MiB, 1 GiB on x86-64; 2 MiB/32 MiB/512 MiB etc. on arm64 depending on base page size); fewer TLB entries per byte.
- THP: Linux Transparent Huge Pages; the kernel opportunistically backs anonymous memory with huge pages without application changes.
- Minor (soft) page fault: a fault resolved without disk I/O (e.g. zero-fill of a fresh anonymous page). Major fault: needs I/O.
- Pre-faulting / pre-touching: forcing pages to be materialized before first real use so the fault cost is paid up front.
- Wired / locked / pinned memory: pages the OS promises not to page out (mlock on POSIX, VirtualLock on Windows, "wired" in XNU).
- Commit vs reserve (Windows): reserve claims address space only; commit charges the system commit limit (RAM + pagefile) and makes the pages usable.
- Overcommit (Linux): the kernel hands out virtual memory beyond physical capacity; the OOM killer resolves the shortfall later.
- PSI: Linux Pressure Stall Information; per-resource fraction of wall time that tasks stalled waiting for that resource.
- Jetsam / memorystatus: XNU's memory-pressure process killer and its pressure-level machinery.
- NUMA: Non-Uniform Memory Access; memory attached to another socket/die costs more to reach.
- First-touch: the NUMA placement policy under which a page is placed on the node of the CPU that first writes it.
- DVFS: dynamic voltage and frequency scaling; the CPU clock changes with load, power, and temperature.
- Little's law: L = lambda * W; mean number in system equals mean arrival rate times mean time in system.
- Slab / magazine / arena: object-cache allocator (Bonwick), per-CPU stack of pre-constructed objects (Bonwick & Adams), and a region of memory an allocator carves privately.

## 2. Findings by sub-question

### 2.1 Page sizes, allocation granularity, and huge pages per platform

**Runtime queries (never hard-code).** Apple's porting guide states: "Virtual memory page sizes are different. Fetch the value from the `vm_page_size` global variable" and, generally, "Instead of hardcoding values related to the underlying system, fetch those values dynamically from system global variables whenever possible ... When a global variable isn't available, use the `sysctl` or `sysctlbyname` functions" [B: Apple, Addressing architectural differences in your macOS code]. POSIX exposes the same through `sysconf(_SC_PAGESIZE)`/`getpagesize()`; on Linux the ELF auxiliary vector `AT_PAGESZ` carries it too. Windows exposes `SYSTEM_INFO.dwPageSize` ("The page size and the granularity of page protection and commitment. This is the page size used by the VirtualAlloc function") and, separately, `dwAllocationGranularity` ("The granularity for the starting address at which virtual memory can be allocated"), plus `lpMinimumApplicationAddress`/`lpMaximumApplicationAddress` for the usable user address range [B: Microsoft Learn, SYSTEM_INFO]. `VirtualAlloc` rounds a reserved base address "down to the nearest multiple of the allocation granularity" and a commit address "down to the next page boundary" [B: Microsoft Learn, VirtualAlloc].

**x86_64.** Base page 4 KiB; the hugetlb documentation states "x86 CPUs normally support 4K and 2M (1G if architecturally supported) page sizes" [B: kernel.org hugetlbpage.rst]. Linux exposes the THP size at `/sys/kernel/mm/transparent_hugepage/hpage_pmd_size` and the hugetlb pool sizes under `/sys/kernel/mm/hugepages/hugepages-<size>kB/` [B: kernel.org transhuge.rst, hugetlbpage.rst]. Windows x64 large page size is returned by `GetLargePageMinimum` (2 MiB on x64 in practice; the API is the only correct source) [B: Microsoft Learn, Large-Page Support].

**Apple Silicon (aarch64-apple-darwin).** Base page 16 KiB. [measured here] `hw.pagesize=16384`, `vm.pagesize=16384`, `getconf PAGESIZE=16384`, `pagesize=16384`, `vm_stat` reports "page size of 16384 bytes" (Darwin 25.4.0, arm64). Apple's guidance to read `vm_page_size` rather than assume 4 KiB is above [B: Apple]. Rosetta-translated x86_64 processes are a distinct case; the daemon ships native arm64 binaries and should treat any process reporting a 4 KiB page under Rosetta as an unsupported configuration (see Section 5 for the unverified detail of how XNU emulates 4 KiB pages for translated processes).

**Linux arm64.** The kernel supports exactly three base page sizes, selected at build time: `CONFIG_ARM64_4K_PAGES`, `CONFIG_ARM64_16K_PAGES` ("AArch32 emulation requires applications compiled with 16K (or a multiple of 16K) aligned segments"), and `CONFIG_ARM64_64K_PAGES` ("allowing only two levels of page tables and faster TLB look-up"); virtual address width is likewise a build choice (39-bit only with 4K, 42-bit only with 64K, 48-bit, or 52-bit) [B: arch/arm64/Kconfig]. Which distributions use which: RHEL 9 and RHEL 10 ship a 4 KiB kernel by default and offer `kernel-64k` as an alternative from RHEL 9.2 / 10.0 [B: Red Hat, "The 64k page size kernel", RHEL 9 docs; Red Hat solution 7000060]; RHEL 8 on aarch64 shipped 64 KiB pages and could not be switched to 4 KiB [B: Red Hat solution 7020544]; Oracle UEK 7 changed its Arm default to 4 KiB [B: Oracle UEK 7 release notes]; the Red Hat bugzilla "Change page size to 4k for aarch64" documents the RHEL 9 switch [B: bugzilla.redhat.com 1978730]. Asahi Linux compiles its kernel with 16 KiB pages because the Apple M1 IOMMUs (DARTs) only support 16 KiB-aligned pages; 4 KiB kernels need "very hacky patches" [D: Asahi Linux alpha release notes, 2022]. Consequence for slates: on Linux arm64 the page size is a property of the running kernel, not the CPU; it must be read at startup and every size-class, arena, and mmap length must be derived from it.

**Windows.** `dwPageSize` is 4 KiB on x86, x64 and ARM64 client systems in practice, but the daemon must read it [B: SYSTEM_INFO]; `dwAllocationGranularity` is 64 KiB on all current Windows SKUs in practice and is the granule at which reserved regions begin, so a reservation of N pages can waste up to 64 KiB minus one page of address space per region [B: SYSTEM_INFO; VirtualAlloc]. Large pages: obtain `SeLockMemoryPrivilege` via `AdjustTokenPrivileges`, call `GetLargePageMinimum`, then `VirtualAlloc` with `MEM_LARGE_PAGES` where "The size and alignment must be a multiple of the large-page minimum" and "you must also specify MEM_RESERVE and MEM_COMMIT" [B: Large-Page Support; VirtualAlloc]. Properties stated by Microsoft: "The memory is always read/write and nonpageable (always resident in physical memory)"; "The memory is part of the process private bytes but not part of the working set"; "Large-page allocations are not subject to job limits"; "Large-page memory must be reserved and committed as a single operation ... large pages cannot be used to commit a previously reserved range of memory"; and the practical warning "Large-page memory regions may be difficult to obtain after the system has been running for a long time because the physical space for each large page must be contiguous ... applications should avoid making repeated large-page allocations and instead allocate all large pages one time, at startup" [B: Large-Page Support].

**i686 (32-bit address space).** Windows: "User-mode virtual address space for each 32-bit process: 2 GB, up to 3 GB with IMAGE_FILE_LARGE_ADDRESS_AWARE and 4GT" on 32-bit Windows, and "2 GB with IMAGE_FILE_LARGE_ADDRESS_AWARE cleared (default), 4 GB with IMAGE_FILE_LARGE_ADDRESS_AWARE set" for a 32-bit process on 64-bit Windows; 64-bit processes get 128 TB on Windows 8.1/Server 2012 R2 and later [B: Microsoft Learn, Memory Limits for Windows Releases]. `MEMORYSTATUSEX.ullTotalVirtual` reports the actual user-mode address space of the calling process ("approximately 2 GB for most 32-bit processes on an x86 processor and approximately 3 GB for 32-bit processes that are large address aware running on a system with 4-gigabyte tuning enabled") and `ullAvailVirtual` the unreserved, uncommitted remainder [B: MEMORYSTATUSEX]. Linux i386 defaults to a 3G/1G user/kernel split (`VMSPLIT_3G`, `PAGE_OFFSET 0xC0000000`), with 2G/2G and 1G/3G as build options [B: arch/x86/Kconfig]. Consequence: volume size caps on i686 must be computed from measured address space (`ullAvailVirtual` on Windows; a probing reservation on Linux), never assumed; and because Windows large pages need contiguous physical memory and AWE needs a privilege, a 32-bit daemon should plan on 4 KiB pages and reserve-then-commit in allocation-granularity units (Section 2.7).

**Transparent Huge Pages on Linux.** Controls live under `/sys/kernel/mm/transparent_hugepage/`: `enabled` (`always`/`madvise`/`never`), per-size `hugepages-<size>kB/enabled` (adds `inherit`), `defrag` (`always`/`defer`/`defer+madvise`/`madvise` (default)/`never`), `use_zero_page`, `shrink_underused`, and `khugepaged/{pages_to_scan,scan_sleep_millisecs,alloc_sleep_millisecs,max_ptes_none,max_ptes_swap,max_ptes_shared,pages_collapsed,full_scans}` [B: transhuge.rst]. `madvise(MADV_HUGEPAGE)` (Linux 2.6.38) marks a range for THP; `MADV_NOHUGEPAGE` forbids it; `MADV_COLLAPSE` (Linux 6.1) performs "a best-effort synchronous collapse of the native pages mapped by the memory range into Transparent Huge Pages" and "ignores these settings" (the sysfs policy), so "Setting 'never' in all sysfs THP controls does not disable Transparent Huge Pages globally" [B: madvise(2); transhuge.rst]. `prctl(PR_SET_THP_DISABLE)` disables THP for a process; `PR_THP_DISABLE_EXCEPT_ADVISED` disables it "except when the usage of THPs is advised" [B: transhuge.rst]. Accounting: `AnonHugePages` in `/proc/meminfo`, per-mapping in `/proc/PID/smaps` [B: transhuge.rst]. The documented bloat hazard: "an application may mmap a large region but only touch 1 byte of it, in that case a 2M page might be allocated instead of a 4k page for no good" [B: transhuge.rst]. THP pages are swappable (the split/swapout counters `thp_swpout` and `thp_swpout_fallback` exist) [B: transhuge.rst], so THP does not by itself help a RAM-only guarantee.

**hugetlbfs / MFD_HUGETLB.** "Huge pages cannot be swapped out under memory pressure" [B: hugetlbpage.rst]. The persistent pool is sized by `/proc/sys/vm/nr_hugepages` (needs root), surplus pages by `nr_overcommit_hugepages`; `mmap(MAP_HUGETLB)` and `memfd_create(MFD_HUGETLB)` work without a hugetlbfs mount; `/proc/meminfo` reports `HugePages_Total/Free/Rsvd/Surp` [B: hugetlbpage.rst]. This is the only Linux memory type that is unswappable without `mlock`, but it depends on an administrator pre-reserving the pool, and it fails (ENOMEM/SIGBUS on fault when reservation is exhausted) rather than degrading, so slates can use it only opportunistically.

**macOS superpages.** XNU's `mach/vm_statistics.h` defines `VM_FLAGS_SUPERPAGE_MASK` ("3 bits that specify whether large pages should be used instead of base pages (!=0), as well as the requested page size"), `VM_FLAGS_SUPERPAGE_SIZE_ANY`, and `SUPERPAGE_SIZE_2MB`/`VM_FLAGS_SUPERPAGE_SIZE_2MB` guarded by `#if defined(__x86_64__) || !defined(KERNEL)`; the 2 MiB constant exists in the kernel only for x86_64 [C: apple-oss-distributions/xnu, osfmk/mach/vm_statistics.h]. There is no public API for transparent large pages on Apple Silicon; slates must treat macOS arm64 as 16 KiB-page-only for planning (see Section 5).

**Evidence on huge-page benefits and harms.**
- Gaud et al. (ATC'14), two AMD Opteron NUMA machines (A: 2x12 cores, 64 GB, 4 nodes; B: 4x16 cores, 512 GB, 8 nodes), Linux 3.9 THP: "THP increases performance (by up to 109%) for several benchmarks ... but also significantly decreases performance by as much as 43% in some cases"; large pages "affect between 25% and 30% of applications in our benchmark set and cause degradations between 5% and 43%"; causes are the hot-page effect (hot data coalesced onto few pages that cannot be balanced across nodes) and page-level false sharing; with 2 MiB pages CG's memory-controller imbalance rises from ~0% to 20% (A) and 59% (B) and UA's local-access ratio falls from ~88% to ~66%; for SSCA the share of L2 misses due to page walks fell from 15% to 2% for a 17% gain; with 1 GiB pages SSCA degraded 34% and streamcluster by 4x; an overloaded memory controller can cost "as many as 1000 cycles, compared to about 200 cycles on a not overloaded controller" [A: Gaud et al., USENIX ATC 2014].
- HawkEye (ASPLOS'19), Intel Haswell-EP E5-2690 v3, 96 GB, Linux 4.3, 100 GB allocate-and-touch microbenchmark (Table 1): Linux-4KB 26.2 M faults, average fault 3.5 us, 92.6 s of fault time; Linux-2MB with synchronous zeroing 51.5 K faults, average fault 465 us, 23.9 s total; without zeroing the average fault is 2.65 us (4 KiB) and 13 us (2 MiB). "clearing a base page takes about 25% of total page fault time which increases to 97% for huge pages". Redis 45 GB insert/delete/insert: Linux THP bloat 28 GB (20 GB useful), Ingens 20 GB (28 GB useful). MMU overhead measured with `DTLB_LOAD_MISSES_WALK_DURATION`+`DTLB_STORE_MISSES_WALK_DURATION` over `CPU_CLK_UNHALTED` ranged up to 39% of cycles (cg.D, 4 KiB) versus 0.02% with 2 MiB. Only 15 of 79 applications across SPEC CPU2006, PARSEC, SPLASH-2, Biobench, NPB, CloudSuite showed >3% gain from huge pages. Redis throughput was "7% lower ... than Linux-2MB" without THP while using 16.2 GB instead of 33.2 GB [A: Panwar, Bansal, Gopinath, ASPLOS 2019].
- Ingens (OSDI'16): identifies the three THP failure modes that HawkEye and later work build on: synchronous huge-page allocation and zeroing inflates fault latency, aggressive promotion causes memory bloat (utilization-threshold promotion, e.g. 90%, is its remedy), and huge-page promotion is unfair across processes; Ingens promotes asynchronously and treats "memory contiguity as a resource" [A: Kwon et al., OSDI 2016, cited via Panwar et al. 2019 Section 1-2; the USENIX PDF returned HTTP 403 during this research, so Ingens' own numbers are not reproduced here].
- TEMERAIRE (OSDI'21): making TCMalloc's page heap hugepage-aware "improved requests-per-second (RPS) by 7.7% and reduced RAM usage 2.4%" across 8 applications, and a 1% fleet experiment showed "6% fewer TLB miss stalls, and 26% reduction in memory wasted due to fragmentation" [A: Hunter et al., OSDI 2021, abstract via research.google]. Design: a `HugePageFiller` that packs small allocations into 2 MiB hugepages by "longest free range" ("If a hugepage has a free range of length 8, we never allocate from it for a smaller request"), `HugeRegion`s of 1 GiB backed on demand for mid-size allocations, a `HugeCache` of backed single hugepages, and release of whole hugepages rather than partial `MADV_DONTNEED` that would break them [C: tcmalloc docs, temeraire.html].
- Ren et al. (SOSP'19), Xeon E5-2630 v3, Ubuntu kernels 3.0-4.20: disabling THP (the upstream default from 4.8 onward) made the `huge-read` test up to 83% slower, and THP "also diminishes the slowdowns caused by other root causes" such as KPTI because it reduces page-fault and TLB-miss counts [A: Ren et al., SOSP 2019 Section 4.2.3].

**What this means for slates.** (1) Huge pages are a measured, per-region decision, not a global switch: the benefit is real only where the daemon's own PMU/timer measurements show page-walk stalls or fault-time domination; the harm (bloat, 465 us synchronous faults, NUMA imbalance) is documented at the same tier. (2) The daemon should request THP only via `MADV_HUGEPAGE` on regions it will fully populate (arena backing for bounded volumes, hash tables), keep `enabled=madvise`-style behaviour regardless of the system setting by using `PR_THP_DISABLE_EXCEPT_ADVISED` where available, and prefer `MADV_COLLAPSE` after pre-faulting (Section 2.2) so zeroing never lands on the request path. (3) On NUMA machines, follow Gaud et al.: keep huge pages within node-local arenas (first-touch by the owning core) and never share a huge page across cores' data. (4) Windows large pages are taken once at startup or not at all; macOS arm64 has none.

### 2.2 Page-fault costs and pre-faulting

- HawkEye's measurements on Haswell-EP: a 4 KiB fault averages 3.5 µs including zeroing (2.65 µs without), a 2 MiB fault 465 µs with synchronous zeroing (13 µs without); zeroing is ~25% of base-page fault time and ~97% of huge-page fault time [A: Panwar et al. ASPLOS'19 Table 1]. Ren et al. show fault-around and THP settings move fault-heavy tests by 54-83% [A: Ren et al. SOSP'19]. These are the reasons no fault may sit on the provisioning path.
- Primitives: Linux `MAP_POPULATE` (prefault at mmap), `MADV_WILLNEED`, `MADV_POPULATE_READ`/`MADV_POPULATE_WRITE` (5.14+, populate without touching), `mlock2(MLOCK_ONFAULT)` ("Lock pages that are currently resident and mark the entire range so that the remaining nonresident pages are locked when they are populated by a page fault") [B: mlock(2), madvise(2), mmap(2)]; Windows `PrefetchVirtualMemory` and `VirtualLock` (locked pages "are guaranteed not to be written to the pagefile while they are locked") [B: Microsoft Learn VirtualLock, fetched 2026-09-04]; macOS `madvise(MADV_WILLNEED)` and `mlock` [B: macOS madvise(2), mlock(2)].
- Measuring fault cost at boot: map a region of the arena size class, touch one byte per page with `CLOCK_MONOTONIC` around a batch of N pages, repeat with `MAP_POPULATE`/`MADV_POPULATE_WRITE`, and record per-page cost for base and (where available) huge pages; the pre-fault policy is "pre-fault and lock everything pre-sized at boot; pre-fault dynamic growth increments off the request path on the owning shard's idle time" and the measured per-page cost bounds how large an increment can be prepared per idle window.

### 2.3 RAM-only guarantees per OS, and honest degradation

- Linux: unprivileged locking is bounded by the `RLIMIT_MEMLOCK` soft limit; "Since Linux 2.6.9, no limits are placed on the amount of memory that a privileged process can lock", i.e. `CAP_IPC_LOCK` removes the bound; locks are not inherited across `fork` and are dropped at `execve` [B: mlock(2), fetched 2026-09-04]. The kernel's default limit was 64 KiB for many years and was raised to 8 MiB in Linux 5.17 (commit "mm: raise the default RLIMIT_MEMLOCK to 8 MiB", 2021) [C: kernel commit; from memory, verify]; distributions with systemd typically raise the service and user default (systemd's `DefaultLimitMEMLOCK`; the documentation page returned 403 this session, so the exact default is flagged) [B: systemd-system.conf(5), not retrieved]. `memfd_create(MFD_HUGETLB)` pages "cannot be swapped out" but need an administrator-reserved pool [B: hugetlbpage.rst]. cgroup v2 `memory.swap.max=0` forbids swap for the cgroup's tasks [B: cgroup-v2.rst]. Policy: at boot, probe the lock capacity by locking increasing sizes until `ENOMEM`/`EPERM`, record the number, lock metadata and rings first, then chunk arenas in priority order; report per volume whether its bytes are locked; never pretend.
- macOS: `mlock` is bounded by the wired-memory limits `vm.user_wire_limit` and `vm.global_user_wire_limit`; on the author's 128 GiB machine both report 116,823,110,451 bytes (about 108.8 GiB) with `vm.global_no_user_wire_amount` at 20,615,843,021 (about 19.2 GiB reserved from user wiring) and `ulimit -l` unlimited [M: sysctl on Darwin 25.4.0 arm64, 2026-09-04]. Unwired memory is subject to the compressor and to swap ("vm.swapusage: total = 12288.00M used = 11253.75M" on the same machine at that moment); "no disk" on macOS therefore means wired pages, and the daemon must wire what it promises to keep in RAM and report the rest as "may be compressed or swapped by the OS".
- Windows: `VirtualLock`'s limit is the process minimum working set minus a small overhead; "Each version of Windows has a limit on the maximum number of pages a process can lock. This limit is intentionally small"; raise it with `SetProcessWorkingSetSize` first [B: Microsoft Learn VirtualLock, fetched 2026-09-04]; large pages (`MEM_LARGE_PAGES`, `SeLockMemoryPrivilege`) are "nonpageable (always resident in physical memory)" and must be taken at startup [B: Large-Page Support]; AWE (`AllocateUserPhysicalPages`) is never paged but needs the same privilege. Policy: raise the working set to the measured budget, lock, and record the locked fraction.
- Degradation statement, per volume and per host: `locked_bytes`, `unlocked_bytes`, and the reason (limit reached, privilege missing); the SDK and MCP surfaces show it; a bounded volume may be created with a `require_locked` flag that fails creation instead of accepting unlocked memory.

### 2.4 Memory pressure and accounting signals per OS

- Linux PSI: `/proc/pressure/memory` and cgroup `memory.pressure` expose `some` ("the share of time in which at least some tasks are stalled") and `full` ("all non-idle tasks are stalled") as `avg10 avg60 avg300 total`; triggers are registered by writing `<some|full> <stall µs> <window µs>` and polled; windows are 500 ms to 10 s; unprivileged monitors must use windows that are multiples of 2 s [B: kernel PSI doc, fetched 2026-09-04]. Facebook's oomd acts on PSI [C: facebookincubator/oomd]. `/proc/meminfo` `MemAvailable` is the kernel's estimate of memory available for new work without swapping (Rik van Riel's 2014 commit) [B: proc(5); C: kernel commit 34e431b0]. cgroup v2 `memory.high`/`memory.max`/`memory.events` give the container's own limits and throttling events [B: cgroup-v2.rst].
- macOS: `host_statistics64` (`vm_statistics64`: free, active, inactive, wired, compressor pages), `dispatch_source` of type `DISPATCH_SOURCE_TYPE_MEMORYPRESSURE` with flags `NORMAL` (0x01), `WARN` (0x02), `CRITICAL` (0x04) ("Elevated memory pressure is a system-wide condition that applications registered for this source should react to by changing their future memory use behavior") [C: libdispatch dispatch/source.h, fetched 2026-09-04]; `kern.memorystatus_level` (85 on the author's machine at measurement) and jetsam limits [M; C: XNU memorystatus].
- Windows: `GlobalMemoryStatusEx` (`ullAvailPhys`, `ullTotalVirtual`, `ullAvailVirtual`), `CreateMemoryResourceNotification(LowMemoryResourceNotification | HighMemoryResourceNotification)` waitable objects, job-object memory limits, `GetProcessMemoryInfo` working-set queries [B: Microsoft Learn].
- Growth policy for dynamic volumes (no fixed percentage): the owning shard tracks each volume's allocation rate (bytes per second, EWMA with a time constant derived from the sample rate) and the host's free memory and pressure trend (PSI `some` avg10 slope on Linux, pressure level on macOS, low-memory notification on Windows); a volume may grow by an increment sized so that, at its current rate, the increment lasts longer than the measured time to prepare (pre-fault and lock) the next one, and only while projected free memory after the grant stays above a reserve equal to the measured peak allocation burst across all volumes over the recent window; when the projection fails the volume gets ENOSPC and a pressure event, never a silent swap. Bounded volumes commit (pre-fault and lock) their full quota at creation so their ENOSPC is a pure counter comparison.

### 2.5 CPU topology, caches, pinning, NUMA

- Cache-line size: glibc `sysconf(_SC_LEVEL1_DCACHE_LINESIZE)` (musl returns 0), `/sys/devices/system/cpu/cpu0/cache/index*/coherency_line_size` on Linux, `sysctl hw.cachelinesize` on macOS (128 on Apple M-series: measured 128 on this machine [M]), `GetLogicalProcessorInformationEx` on Windows [B: vendor docs]. crossbeam's `CachePadded` pads to 128 bytes on aarch64 and x86_64 because adjacent-line prefetchers pull pairs of 64-byte lines, and to 64/32 on others [C: crossbeam-utils CachePadded docs; C: survey-vorpal.md §4.4].
- Cores and classes: Linux `/sys/devices/system/cpu` (topology, `cpu_capacity`), macOS `hw.nperflevels`/`hw.perflevelN.*` (this machine: two levels, "Super" 6 cores with 16 MiB L2 and "Performance" 12 cores with 8 MiB L2; 18 physical = 18 logical) [M], Windows `GetLogicalProcessorInformationEx` and `GetSystemCpuSetInformation` (efficiency class) [B]. Shards are placed on performance-class cores by default and the count derives from the physical core count of that class.
- Pinning: Linux `sched_setaffinity`; Windows `SetThreadAffinityMask`/`SetThreadIdealProcessor`; macOS `thread_policy_set(THREAD_AFFINITY_POLICY)` is a hint only and is not honoured on Apple silicon, where QoS classes steer threads to P or E clusters [B: Apple thread affinity note; C: survey-hecate/ipc notes]. The design therefore pins where pinning exists and uses QoS (`QOS_CLASS_USER_INTERACTIVE` for shards) on macOS, and the calibration measures core-to-core latency per pair to detect the P/E boundary rather than assuming it.
- NUMA: Linux `/sys/devices/system/node`, `mbind`/`set_mempolicy`, first-touch placement; Windows `GetNumaHighestNodeNumber`, `VirtualAllocExNuma`; macOS none. Rings and arenas are first-touched by their owning shard so they land on the shard's node.

### 2.6 Runtime calibration methodology

- Model: lmbench's microbenchmarks (syscall, context switch, memory bandwidth, latency) [A: McVoy & Staelin USENIX'96]. Statistics: Kalibera & Jones show that a small number of repetitions at the right level (VM/process/iteration) gives rigorous confidence intervals in reasonable time [A: Kalibera & Jones ISMM'13]; Mytkowicz et al. show measurement bias from environment size and link order can exceed the effects being measured, so calibrations randomize layout-sensitive conditions and report medians with bootstrapped intervals [A: Mytkowicz et al. ASPLOS'09].
- What the daemon measures at start (the machine profile) and what each feeds: base page size and huge-page availability (chunk sizes, arena layout); cache-line size (padding); core counts by class and per-pair core-to-core latency (shard count and placement, ring placement); memory total/free/lock capacity (arena sizes, bounded-volume admission); minor-fault cost per page class (pre-fault policy); syscall cost and wake latency (spin windows, idle park thresholds); memcpy bandwidth per size (chunk size and copy budgets); BLAKE3 throughput (hash-on-seal policy); LZ4/zstd throughput per level (compression cost model); loopback bridge RTT per operation (attribute timeouts on macOS); mount/unshare cost (launcher form cost). Budget: each measurement is a few thousand iterations; the whole profile completes in well under a second on the author's machine class (must-measure per platform) and is cached in the anchor segment with the machine identity so restarts skip it.
- Deriving parameters: queue and ring capacities from Little's law with measured arrival and service rates plus the latency budget [B: Harchol-Balter 2013]; spin thresholds from measured wake cost (Karlin's rule); batch sizes from measured fixed per-operation costs; thread counts from performance-class core counts.
- Re-calibration: laptops throttle and DVFS changes clocks; the daemon re-measures wake latency and memcpy bandwidth on a slow cadence and whenever the OS reports a power-state change (Linux `cpufreq` notifications, macOS thermal-state notifications, Windows power events), and versions the profile so derived constants can be correlated with behaviour.

### 2.7 Allocator design

- Bonwick's slab allocator (object caches with constructed objects) and the magazine layer (per-CPU stacks of objects so the common path takes no lock) are the model for the per-shard pools [A: Bonwick USENIX'94; A: Bonwick & Adams USENIX'01]. Hoard bounds fragmentation and avoids false sharing with per-processor heaps [A: Berger et al. ASPLOS'00]; jemalloc's per-thread arenas and decay policies and TCMalloc's TEMERAIRE hugepage-aware page heap are the deployed refinements [A: Evans BSDCan'06; A: Hunter et al. OSDI'21]; mimalloc's free-list sharding and snmalloc's message-passing frees (a freed object is returned to its owning allocator by a queue) are the designs that fit shared-nothing shards exactly [A: Leijen et al. APLAS'19; A: Liétar et al. ISMM'19]. Buddy allocation gives O(log) variable-size extents inside a reserved region [B: Knuth TAOCP vol.1 §2.5]; segmented arrays grow without realloc in O(1) amortized with O(√n) extra space [A: Brodnik et al. WADS'99].
- slates' design: each shard owns (a) size-class slabs with per-shard free lists (no atomics; a cross-shard free is a message to the owner, snmalloc-style), (b) a buddy allocator over a large reserved, pre-faulted, locked region for chunk extents, and (c) segmented arrays for growable tables. The Rust global allocator matters only for the cold control plane; vorpal's jemalloc setup is reused for the binary with decay left on (a long-lived daemon) [C: survey-vorpal.md §3.1]. On 32-bit Windows the reserve-then-commit region is bounded by `ullAvailVirtual` and the volume quota ceiling derives from it.

## 4. Recommendation for slates

The **machine profile** (built at boot, cached in the anchor segment, re-measured on power-state change): page size and huge-page availability; cache-line size; core count by class and core-to-core latency matrix; total/free memory and lock capacity; fault cost per page class; syscall cost; wake latency; memcpy bandwidth by size; BLAKE3, LZ4 and zstd throughput by level; bridge loopback RTT by operation; launcher mount cost; address-space size (i686). Every derived constant records its inputs. **RAM-only policy**: lock what is promised (mlock/wired/VirtualLock after raising the working set), lock metadata and rings first, report locked and unlocked bytes per volume, offer `require_locked`, never spill. **Allocator**: per-shard slabs with message-passing frees, a buddy allocator over locked reserved regions for chunks, segmented arrays for growth; huge pages requested per region after pre-faulting (`MADV_COLLAPSE` where available) and only when measured page-walk cost justifies them; jemalloc for the cold control plane. **Growth policy**: measured allocation rate versus measured free memory and pressure trend with a reserve derived from observed bursts; bounded volumes commit at creation. Runner-ups: THP `always` (bloat and NUMA harms), a global allocator alone (contention and no ownership), fixed growth percentages (wrong by 10x across machines).

## 5. Risks and unknowns

- The exact Linux default `RLIMIT_MEMLOCK` and systemd's default were not re-verified this session; the design does not depend on them (capacity is probed).
- Apple silicon lacks public superpages; if measured TLB pressure matters, the only lever is contiguity within 16 KiB pages.
- Windows large pages can be unobtainable after uptime; the daemon takes them at start or not at all and never retries in the request path.
- Calibration time on slow machines (Raspberry-class ARM) may be seconds; the profile cache and a "quick profile" (fewer iterations, wider intervals) mitigate.
