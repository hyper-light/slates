# The OS Filesystem Bridge: presenting an in-memory userspace filesystem as a normal path on Linux, macOS, and Windows

Date: 2026-09-03. Author: research agent for the `slates` project. Status: complete draft (written incrementally; sections appear in the order they were finished).

Evidence tiers used throughout, shown as a bracketed tag after each claim:
[A] peer-reviewed paper (USENIX FAST/ATC/OSDI/SOSP etc.) or PhD thesis;
[B] standard (RFC, POSIX), textbook, or official kernel/OS/vendor documentation or man page;
[C] widely deployed implementation source or design document (Linux kernel source, libfuse, EdenFS/Sapling, Buildbarn, WinFsp, macFUSE, rclone, Rust crates);
[D] blog post, mailing-list benchmark, or vendor claim without a paper behind it (gap-filler only, flagged).

Terms of art are defined in one line at first use. "Hermetic" here means: our software never writes to a disk-backed filesystem (no temp files, caches, sockets, symlinks, or mount-point directories created by us where avoidable).

## 1. Questions answered

1. Linux: FUSE's per-operation cost is dominated by kernel/user transitions and wake-ups (tens of microseconds per request that reaches the daemon; sub-microsecond when the kernel cache answers), not by copying; the papers give the numbers and the knobs that matter (writeback cache, splice thresholds, `max_background`, attr/entry timeouts, readdirplus, `FUSE_DEV_IOC_CLONE`, and since Linux 6.14 FUSE-over-io_uring). Unprivileged mounts exist via setuid `fusermount3` and, since 4.18, directly inside user namespaces. A private mount namespace plus a bind mount can present a volume at an existing path with zero disk writes; a non-existent path cannot be created without a directory inode somewhere, and the only RAM-only place to create one is a tmpfs (e.g. `$XDG_RUNTIME_DIR`). Symlinks are disk inodes and also break "invisible filesystem" semantics, so they are rejected. mount(2)/unshare latency has no published microbenchmark; the closest peer-reviewed data (SOCK, ATC'18) shows mount-namespace churn in the sub-millisecond-to-tens-of-milliseconds range and degrading with the number of existing mounts, so it must be measured on the target kernels.
2. macOS: the kernel-extension route (macFUSE) still requires "Reduced Security" plus explicit third-party-kext approval in Recovery on Apple Silicon in 2026, is closed source, and has been abandoned by Meta for automation; FSKit (macOS 15.4+) is a signed app-extension framework currently limited to "unary" one-resource/one-volume, block-device-oriented file systems with no evidence of a Rust path or of latency data; the NFSv3 loopback server (EdenFS's production choice) needs no kext, no root when the mount point is user-owned and no reserved port is used, and is the only route that meets the hermeticity and adoption constraints, at the price of weak cache coherence and hang-on-death semantics. bb_clientd uses NFSv4.0 for fewer round trips; Meta chose v3 for a 2.5x smaller specification.
3. Windows: WinFsp is the only viable bridge (kernel FSD + user DLL, x86/x64/ARM64, GPLv3 with a FLOSS-only linking exception or a commercial license); drive-letter mounts are object-manager symlinks in kernel memory (no disk write), directory mounts are NTFS reparse points (a disk write) and network mounts cannot be directory mounts; ProjFS and the Cloud Files API hydrate and persist file content on the NTFS volume by design (EdenFS's own documentation lists the consequences), so they violate hermeticity; the built-in NFS client is v2/v3-only with a 32 KB transfer ceiling; SMB loopback needs Windows 11 24H2+ for a non-445 port and admin rights to map it.
4. Cross-cutting: one kernel mount per (host, user), established once, with volumes as top-level directories, is the model used by bb_clientd (single `~/bb_clientd` mount) and Google's CitC (`/google/src/cloud/<user>/<workspace>`); EdenFS instead mounts once per checkout. Under the single-root model a volume is a metadata operation inside the daemon, so provisioning does not touch mount(2) at all and the sub-50 µs budget is spent entirely in our own code. Per-OS "attach at a chosen path" rules are given in Section 4.
5. Coherence: FUSE offers explicit invalidation (inval_inode/inval_entry/delete/expire, and since protocol 7.44 `INC_EPOCH`), NFSv3 offers none (attribute-cache timers plus weak-cache-consistency data only; EdenFS forces revalidation with a no-op `chmod`), NFSv4 adds delegations/callbacks for open files only, and WinFsp offers `FspFileSystemNotify` plus per-class cache timeouts. Multi-agent coherence therefore has to be enforced by making the daemon the single authority per volume and driving each OS's invalidation path from it; shared-writable mmap is coherent only within one host.
6. Libraries: `fuser`, `fuse-backend-rs`, `fuse3`, `polyfuse`, `winfsp-rs`, and `nfsserve`/`nfs3_server` all use `Arc` and either OS threads or tokio; only `fuse-backend-rs` has an (experimental, evolving) FUSE-over-io_uring transport. The FUSE wire protocol is 68 opcodes and 9 notification codes in one header; NFSv3+MOUNT+portmap is 21+6+1 procedures over ONC RPC record marking; WinFsp needs roughly 25 callbacks. Writing our own /dev/fuse driver, NFSv3 server, and thin WinFsp binding is justified and sized in Section 2.6.
7. Failure: FUSE returns `ENOTCONN` to open files when the daemon dies and the mount stays in the table until lazily unmounted; NFS hard mounts hang (soft mounts return `EIO`/`ETIMEDOUT` after `retrans`); WinFsp deletes the volume devices when the process dies. FUSE mounts survive daemon restarts if the `/dev/fuse` fd is handed to the new process (XFUSE monitor service, EdenFS takeover over `SCM_RIGHTS`, libfuse `/dev/fd/N`, `fuser::Session::from_fd`); NFS survives because the client reconnects and retries as long as file handles stay valid; WinFsp has no documented handoff.

## 2. Findings by sub-question

### 2.1 Linux FUSE

**Architecture.** FUSE (Filesystem in Userspace) is a kernel driver plus a user-space daemon; the daemon reads requests from and writes replies to `/dev/fuse` [A: Vangoor et al., FAST'17, §2]. The kernel keeps five request queues: interrupts, forgets, pending (synchronous requests such as metadata), processing (requests handed to the daemon and awaiting a reply), and background (asynchronous reads/writes, init and release); at most `max_background` asynchronous requests (default 12) may sit in the pending queue, and when the number of background requests reaches the congestion threshold (75% of `max_background`, i.e. 9 by default) the kernel tells the VFS the device is congested [A: Vangoor et al., FAST'17, §2; A: Vangoor et al., ACM TOS 2019, §2]. The kernel source confirms the defaults: `FUSE_DEFAULT_CONGESTION_THRESHOLD (FUSE_DEFAULT_MAX_BACKGROUND * 3 / 4)` and a `fuse_max_pages_limit` of 256 pages per request [C: linux fs/fuse/inode.c, mainline 2026-09]. Every request read from `/dev/fuse` costs a memory copy between kernel and user space unless splice is used; libfuse splices only WRITE requests larger than one page and READ replies larger than two pages, so 4 KB I/O is always copied [A: Vangoor et al., ACM TOS 2019, §2.6]. The writeback cache allows the kernel to batch dirty pages into larger WRITE requests instead of synchronous 4 KB writes [A: Vangoor et al., FAST'17, §2]. `READDIRPLUS` returns entries together with attributes and pre-fills the kernel inode cache, "similar to NFSv3's readdirplus" [A: Vangoor et al., FAST'17, §2]. The current wire protocol is version 7.46, with 68 opcodes and 9 notification codes (`POLL`, `INVAL_INODE`, `INVAL_ENTRY`, `STORE`, `RETRIEVE`, `DELETE`, `RESEND`, `INC_EPOCH`, `PRUNE`) declared in one header [C: linux include/uapi/linux/fuse.h, mainline 2026-09]. A daemon can clone the device fd with `FUSE_DEV_IOC_CLONE` to get independent per-thread channels [C: linux fs/fuse/dev.c].

**Measured overhead (Vangoor et al.).** Setup: Dell PowerEdge R710, 4-core Xeon E5530 2.40 GHz, RAM capped at 4 GB, CentOS 7 with kernel 4.1.13, libfuse commit 386b1b, Seagate Savvio 15K.2 HDD and Intel X25-M SSD, a pass-through stackable file system (StackFS) over Ext4, 45 Filebench workloads, in two configurations (StackfsBase: single-threaded, no splice, no writeback cache; StackfsOpt: multithreaded, writeback cache, 128 KB max write, splice) [A: Vangoor et al., FAST'17, §4; A: ACM TOS 2019, §5]. Results: relative throughput ranged from -83.1% (files-cr-1th, single-threaded file creation, SSD) to +6.2% (web-server, Opt); "in the worst cases [FUSE] can be 3x slower"; relative CPU utilization rose by 0.13% to 31.2%; latencies rose "from none to 4x" [A: FAST'17 abstract and Observation 1, 9; A: ACM TOS 2019 abstract]. Metadata-intensive and file-create workloads are the worst; in the best-performing configuration only two file-create workloads out of 45 remained in the >50% degradation class [A: FAST'17, Observation 4 and 8]. Optimizations are not monotone: StackfsOpt was 35% worse than StackfsBase for files-rd-1th on SSD because the writeback cache and splice paths add work for small reads [A: FAST'17, Observation 3]. Raising `max_background` from 12 to 100 improved HDD sequential-read scaling because the kernel had been throttling to 12 in-flight daemons/threads [A: FAST'17, §5.2.1]. The 128 KB default readahead makes sequential reads insensitive to application I/O size [A: FAST'17, §5.2.1]. EdenFS's own operational note agrees on the shape: a kernel-cached operation costs "somewhere below a microsecond" while "any FUSE request that actually makes it into our FUSE daemon will take 10+ microseconds" [C: EdenFS docs/Caching.md, 2018].

**Where the microseconds go (RFUSE).** Setup: Dell PowerEdge R750xs, 2x Xeon Silver 4316 (80 logical cores), 256 GB DDR4, Ubuntu 20.04, kernel 5.15.0, libfuse 3.10.5 [A: Cho et al., FAST'24, §4.1]. For an empty `CREATE` on a null file system, VFS path walk (which itself issues `LOOKUP`s to the daemon) took 72% of the total; the user-space part took 18.1 µs purely from the context switch; waking the application thread that waits for the reply cost 39 µs [A: Cho et al., FAST'24, §2.2 and Fig. 2]. RFUSE replaces `/dev/fuse` read/write with per-core ring channels in shared memory and hybrid polling (50 µs default busy period) and gets 53% lower CREATE latency, a 6.46x faster user-space segment, and 2.27x FUSE's random-read throughput; FUSE's single pending queue stops scaling beyond 16 threads [A: Cho et al., FAST'24, §2.1, §4.2, §4.3]. XFUSE (Alibaba; Linux 4.19.91, dual Xeon Platinum 8163 2.5 GHz, 24 of 48 cores used) reaches "latency in the 4 microseconds range and throughput exceeding 8 GB/s" for a PMEM-like configuration where stock FUSE shows 10 µs and under 2 GB/s; the net cost of an event wait was about 5 µs in their setup and cross-CPU busy waiting gave the lowest latency ("just under 4 us"); for SSD-like storage busy waiting only wastes CPU, so they use an adaptive busy-event wait (10 µs window) [A: Huai et al., ATC'21, §3.1.1, §4.1]. ExtFUSE pushes metadata caching and permission checks into eBPF handlers in the kernel; on an i5-3550/16 GB/Samsung 850 EVO/Ubuntu 16.04 box it removed 75%, 99% and 100% of `lookup`, `getattr` and `getxattr` requests during a kernel build and cut kernel-untar time from 11.02 s (FUSE Opt) to 10.32 s (MDOpt) and 8.67 s (AllOpt) against 5.27 s native Ext4, and `make tinyconfig; make -j4` from 39.74 s (FUSE Opt) to 37.68 s (MDOpt) and 33.64 s (AllOpt) against 30.91 s native; it also found that the VFS issues a `getxattr` before every write on xattr-capable file systems, which alone cost 23% of 4 KB write throughput [A: Bijlani & Ramachandran, ATC'19, §6]. The lesson for slates is that the per-request floor of classic `/dev/fuse` is set by two scheduler wake-ups (roughly 5-40 µs on the cited hardware), so the kernel cache must answer the hot path and the transport should be ring-based where the kernel allows it.

**FUSE-over-io_uring (Linux 6.14+).** Merged in 6.14 from Bernd Schubert (DDN) [C: LWN, "fuse: fuse-over-io-uring" patch series; C: kernel Documentation/filesystems/fuse/fuse-io-uring.rst]. Every CPU core has its own queue; the daemon registers entries with `IORING_OP_URING_CMD` sub-command `FUSE_IO_URING_CMD_REGISTER` and afterwards completes-and-refetches with `FUSE_IO_URING_CMD_COMMIT_AND_FETCH` (one syscall per round instead of read+write); the kernel starts enqueueing only once every queue has at least one registered entry; notifications (daemon-initiated) and interrupts still travel over `/dev/fuse`; newer trees add buffer pools (`FUSE_IO_URING_CMD_ADD_BUFPOOL`) and a zero-copy mode that requires `CAP_SYS_ADMIN` [B: kernel fuse-io-uring.rst, mainline docs fetched 2026-09-03; C: uapi fuse.h]. The author's numbers (32-core HT Xeon E5-2650, patched passthrough-hp, RFC v1): 128 KB paged reads 1117 -> 1921 MB/s (1 job) and 6373 -> 11320 MB/s (16 jobs); 1 MB direct-I/O reads 2023 -> 3998 MB/s (1 job) and 8520 -> 27864 MB/s (16 jobs); file creation 3944 -> 10121 ops/s single-threaded, 16628 -> 44426 ops/s with 4 threads, with gains flattening at >= 8 cores [D: cover letter benchmark, LWN 988186, 2024]. Requests are meant to stay on the submitting core ("same core for sync requests, core+1 for large async"), which is exactly the thread-per-core shape slates wants [C: LWN 988186]. Mixed I/O sizes per queue and `O_DIRECT` were open issues at merge time [C: LWN 988186; C: LWN 1085618 "Buffer sizes for FUSE io_uring", 2026].

**FUSE passthrough (Linux 6.9+) and why it barely matters for RAM data.** The daemon opens a backing file, registers it with `FUSE_DEV_IOC_BACKING_OPEN` (getting a `backing_id`), and replies to `OPEN` with `FOPEN_PASSTHROUGH`; thereafter `read`/`write`/`splice`/`mmap` on the FUSE file are executed by the kernel directly on the backing file with no daemon round trip; it requires `CONFIG_FUSE_PASSTHROUGH`, the `FUSE_PASSTHROUGH` init flag with `max_stack_depth`, and `CAP_SYS_ADMIN` in the daemon [B: kernel fuse-passthrough.rst]. The backing object must be a kernel `struct file` on another file system; for slates the only RAM-only candidates are `memfd_create` or tmpfs files, which would move volume data into kernel page-cache pages that the daemon no longer owns, are swappable unless locked, and require a privileged daemon. It is therefore an optional accelerator for large-file read/mmap workloads, not the primary data path. RFUSE makes the same observation: passthrough "bypasses the FUSE daemon, thereby sacrificing FUSE's ability to support custom userspace filesystem functions" [A: Cho et al., FAST'24, §2.2].

**Knobs that matter.** Kernel mount options are `fd=`, `rootmode=`, `user_id=`, `group_id=`, `default_permissions` (kernel enforces mode bits), `allow_other` (root-only unless `/etc/fuse.conf` has `user_allow_other`), `max_read=`, `blksize=` [B: kernel Documentation/filesystems/fuse/fuse.rst]. The daemon negotiates capabilities in `FUSE_INIT`; libfuse exposes them as `FUSE_CAP_ASYNC_READ`, `POSIX_LOCKS`, `ATOMIC_O_TRUNC`, `EXPORT_SUPPORT`, `DONT_MASK`, `SPLICE_WRITE/MOVE/READ`, `FLOCK_LOCKS`, `IOCTL_DIR`, `AUTO_INVAL_DATA`, `READDIRPLUS`, `READDIRPLUS_AUTO`, `ASYNC_DIO`, `WRITEBACK_CACHE`, `NO_OPEN_SUPPORT`, `PARALLEL_DIROPS`, `POSIX_ACL`, `HANDLE_KILLPRIV(_V2)`, `CACHE_SYMLINKS`, `NO_OPENDIR_SUPPORT`, `EXPLICIT_INVAL_DATA`, `EXPIRE_ONLY`, `SETXATTR_EXT`, `DIRECT_IO_ALLOW_MMAP`, `PASSTHROUGH`, `NO_EXPORT_SUPPORT`, `OVER_IO_URING`, `ALLOW_IDMAP`, `SECURITY_CTX` [C: libfuse include/fuse_common.h]. Per-entry cache lifetimes are the `attr_timeout` and `entry_timeout` fields of `fuse_entry_param` (and `attr_timeout` on `getattr` replies) [C: libfuse fuse_lowlevel.h]. `direct_io` on `open` bypasses the page cache (then mmap needs `DIRECT_IO_ALLOW_MMAP`), `keep_cache` retains cached pages across opens [C: libfuse fuse_common.h]. Coherence-related notifications are covered in Section 2.5.

**Unprivileged mounts.** mount(2) is privileged, so libfuse ships `fusermount3`, installed setuid root, which always adds `nosuid,nodev` for non-root mounts and only permits `allow_other` when `user_allow_other` is set [B: kernel fuse.rst; C: libfuse util/fusermount.c; C: fusermount3(1)]. Since Linux 4.18 FUSE can be mounted by the root user of a user namespace: `fuse_fs_type` carries `FS_USERNS_MOUNT` [C: linux fs/fuse/inode.c, `.fs_flags = FS_HAS_SUBTYPE | FS_USERNS_MOUNT | FS_ALLOW_IDMAP`; C: torvalds commit 4ad769f "fuse: Allow fully unprivileged mounts"; C: LWN 755593, "Unprivileged filesystem mounts, 2018 edition"]. The kernel requires that the `/dev/fuse` fd was opened by a task in the same user namespace as the mount (`if (file->f_cred->user_ns != fsc->user_ns)` fails the mount) [C: linux fs/fuse/inode.c]; this dictates who opens the device (Section 4). Unprivileged processes can create user namespaces since 3.8 and obtain a full capability set inside them; `CLONE_NEWUSER|CLONE_NEWNS` in one call creates the user namespace first so the caller may then own a mount namespace; tmpfs, ramfs, overlayfs, proc, sysfs and similar can be mounted from a non-initial user namespace, block-device file systems cannot [B: user_namespaces(7)]. A new mount namespace starts as a copy of the parent's mount list; changes do not propagate back unless mounts are shared, and mounts inherited into a less privileged namespace are downgraded from shared to slave [B: mount_namespaces(7)]. The new mount API (5.2+: `fsopen`/`fsconfig`/`fsmount`/`move_mount`/`open_tree`, `OPEN_TREE_CLONE` for detached bind copies, `MOVE_MOUNT_BENEATH` since 6.5) attaches mounts by fd and needs `CAP_SYS_ADMIN` in the owning user namespace [B: move_mount(2)]; EdenFS uses exactly this sequence for both FUSE and NFS mounts and unmounts via `umount2("/proc/self/fd/N", MNT_DETACH|UMOUNT_NOFOLLOW)` to avoid path races [C: sapling eden/fs/privhelper/PrivHelperServer.cpp]. Caveat for laptops: Ubuntu 23.10+ restricts unprivileged user namespaces for unconfined programs through AppArmor (`kernel.apparmor_restrict_unprivileged_userns=1`); an AppArmor profile with the `userns` permission or the sysctl lifts it [B/C: Ubuntu security blog, 2023]. libfuse also lets a parent do the mount and pass the open `/dev/fuse` fd by naming the mount point `/dev/fd/N`, "so the FUSE filesystem process can run fully unprivileged" [C: libfuse ChangeLog.rst, release 3.3.0, 2018-11-06].

**Latency of mount(2), fusermount, and unshare + bind mount.** No peer-reviewed or vendor measurement of FUSE mount latency was found. The nearest published data is SOCK (Oakes et al., ATC'18; 8-core CloudLab m510, kernel 4.13.0-37): unsharing into new mount namespaces sustains about 1500 namespaces/s (creation plus deletion) while the count stays small, the rate "approaches zero" as existing host mounts grow toward ~1000 (their Fig. 2), mount- and IPC-namespace cleanup incurs tens of milliseconds of RCU-grace-period latency, bind mounts scale far better than union (AUFS) mounts, and `chroot` costs under 1 µs [A: Oakes et al., ATC'18, §2.1-2.2]. Those numbers say two things: per-volume kernel mounts and per-volume namespaces are in the 0.1-10 ms class and get worse with mount-table size, so they cannot be on the sub-50 µs provisioning path; and the cost is kernel-version- and mount-count-dependent, so it must be measured at runtime. Measurement method: with `CLOCK_MONOTONIC` around each syscall, on each target kernel (6.x/7.x), record (a) `open("/dev/fuse")`+`mount(2)` with `fd=`, (b) `fork`+`exec fusermount3` round trip including its unix-socket fd handshake, (c) `unshare(CLONE_NEWUSER|CLONE_NEWNS)`+`mount(NULL,"/",MS_REC|MS_PRIVATE)`+`mount(src,dst,MS_BIND)`, and (d) `fsmount`+`move_mount`; sweep the number of pre-existing mounts (10, 100, 1000) and report p50/p99 and the exit-time cleanup cost, because SOCK shows cleanup, not creation, dominates.

**Presenting a volume at an arbitrary existing path without disk writes.** Yes: in a private mount namespace, `mount(MS_BIND)` of `<root>/<volume>` onto an existing directory modifies only the in-kernel mount table of that namespace; nothing is written to the directory's file system, and other namespaces do not see it [B: mount_namespaces(7); B: mount(2) semantics of MS_BIND]. If the chosen path does not exist, some file system must gain a directory inode; on a disk-backed parent that is a metadata write, which the hermeticity rule forbids. Two RAM-only escapes exist on Linux: create the directory inside `$XDG_RUNTIME_DIR` (a per-user tmpfs, see 2.4) and bind from there, or overlay the parent with an overlayfs whose upper layer is a tmpfs inside the private namespace (both mountable from a user namespace [B: user_namespaces(7)]) and `mkdir` in the overlay; the overlay option is rejected for general use because every later write under that parent by the confined process would be captured in the RAM upper layer and lost. Symlinks are not acceptable: they are inodes on the backing disk, and they break "invisible filesystem" because `realpath`/`getcwd` and tools like git resolve them to the real mount path [inference from B: symlink(7) semantics; C: fusermount.c "umount(2) will follow symlinks" comment].

### 2.2 macOS

**macFUSE (kernel extension).** The macFUSE kernel extension is closed source; only `libfuse.dylib` and `macFUSE.framework` are open, and the last fully open release was osxfuse 3.8.3 (macOS 10.5-10.14) [C: macfuse/macfuse README]. On Apple Silicon with macOS 13 or later the user must shut down, boot into Recovery, open Startup Security Utility, select "Reduced Security", enable "Allow user management of kernel extensions from identified developers", reboot, then allow the extension in System Settings and reboot again; the wiki stresses this does not disable Gatekeeper or System Integrity Protection [C: macFUSE wiki "Getting Started", fetched 2026-09-03]. EdenFS's documentation states the requirement more harshly ("As of Ventura, third party kernel extensions require turning off SIP") and records the operational consequence: "As of 11.4 third party kernel extensions were no longer usable in automation (i.e. Sandcastle/CI)... because using kernel extensions requires clicking some buttons", so Meta "force migrated everyone to NFS on Ventura" and "macFUSE is no longer used by any EdenFS users" [C: sapling eden/fs/docs/macOS.md]. The two sources disagree on whether SIP itself must be disabled; both agree a Recovery-mode reboot and a per-machine security downgrade are unavoidable. Buildbarn adds that macFUSE "does tend to cause system lockups under high load" and that fixing it is hard because "macFUSE is no longer Open Source Software" [C: buildbarn bb-adrs 0009]. macFUSE 5.0.0 (2025-05-05) added an experimental FSKit backend selected at mount time with `-o backend=fskit` on macOS 15.4+, the kernel backend remaining the default [C: macFUSE 5.0.0 announcement]; 5.3.3 (2026-07-04) supports macOS 12 or later and improves daemonization for FSKit-backend file systems using libfuse [C: macFUSE 5.3.3 announcement]; the project site says supported file systems "can now run entirely in user space on macOS 26" with "no more rebooting into recovery mode", while the wiki still calls the kernel backend the one with "superior performance and full feature support" [C: macfuse.github.io; C: macFUSE wiki]. Adoption verdict: a kext path costs each user a Recovery reboot and a standing security downgrade, cannot be automated in CI, and depends on closed-source kernel code; it is not viable for a tool that agents provision on demand.

**FSKit.** FSKit (macOS 15.4+) lets developers "implement a file system that runs in user space", delivered as app extensions (Mac App Store compatible) that FSKit connects to Disk Arbitration, NetFS and `mount(8)`; its concepts are volume, resource (block device or URL-identified network resource), and container [B: Apple FSKit framework documentation]. "The current version of FSKit supports only `FSUnaryFileSystem`" (one `FSResource` presented as one `FSVolume`); `FSFileSystem` (multiple resources/volumes) is not yet supported [B: Apple FSKit docs; B: FSUnaryFileSystem docs]. Resource classes are `FSBlockDeviceResource`, `FSPathURLResource` ("a path in the system file space") and `FSGenericURLResource` [B: FSResource docs]. Modules need the `com.apple.developer.fskit.fsmodule` entitlement (macOS 15.4+) [B: Apple entitlement docs] and implement `FSUnaryFileSystemOperations` (`probeResource`, `loadResource`, `unloadResource`) [B: Apple docs]. A user must enable the extension under System Settings > General > Login Items & Extensions > File System Extensions, then mount with `mount -F -t <Type> <resource> <mountpoint>` (the `-F` flag means "an FSModule delivered using FSKit"); the sample uses a raw disk image attached with `hdiutil attach -nomount` as the block resource and requires the mount point directory to exist [B: macOS mount(8); C: KhaosT/FSKitSample README]. Apple DTS (Feb 2025): FSKit "is currently focused on supporting Old School file systems, where there's one underlying disk-like resource that maps to one user-visible volume" and `FSUnaryFileSystem` "is where it's at" [C: Apple Developer Forums thread 765424, DTS reply]. Meta: "FSKit is fairly new (introduced in 2024). We have not thoroughly investigated FSKit" [C: EdenFS macOS.md]. Rust reachability: FSKit is an Objective-C/Swift framework consumed from a signed, entitled `.appex` bundle; no Rust FSKit module was found; using it would mean an Xcode-built extension wrapping Rust, outside the pure-Rust cross-target build. Latency: no measurements exist in any source surveyed; macFUSE's own guidance ranks its FSKit backend below the kext for performance [C: macFUSE wiki]. Verdict: promising for 2027+, not usable as slates' macOS bridge today (unary/block-device orientation, packaging and entitlement burden, no performance data).

**NFS loopback: what EdenFS does.** "EdenFS is an NFSv3 server" on macOS [C: sapling eden/fs/docs/macOS.md]. The implementation lives in `eden/fs/nfs/` (`Nfsd3`, `Mountd`, `NfsServer`, `NfsDispatcher`, `rpc/`, `xdr/`, `portmap/`) [C: sapling tree]. Topology: for n mounts the daemon runs n `nfsd3` servers plus one `mountd`, each an RPC server on a TCP socket; TCP is used because "the macOS NFS client is buggy for UDS" [C: macOS.md]. The root `privhelper` process performs `mount(2)` with an XDR-serialised `nfs_mount_args`: version 3; `rsize`/`wsize`; optional `dsize` (readdir size); `readahead`; lock mode `NFS_LOCK_MODE_LOCAL` (locks handled client-side); socket type tcp4/tcp6; nfsd and mountd ports; request timeout in deciseconds; retransmit count; dead timeout; flags `NFS_MFLAG_RESVPORT | NFS_MFLAG_RDIRPLUS | NFS_MFLAG_SOFT | NFS_MFLAG_INTR | NFS_MFLAG_MUTEJUKEBOX` (configurable soft/hard and readdirplus); `MNT_NOSUID`; after mounting it calls an undocumented `fsctl(FSCTL_SET_FSTYPENAME_OVERRIDE)` so the volume reports type "edenfs:" to Watchman [C: sapling eden/fs/privhelper/PrivHelperServer.cpp]. The code comments: "while in theory we would always want the mount to be soft, macOS force a maximum timeout of 60s, which in some case is too short for files to be fetched", and `NFS3ERR_JUKEBOX` is returned deliberately for backpressure with kernel logging muted [C: PrivHelperServer.cpp]. On Linux the same daemon uses `addr=,vers=3,proto=tcp,port=,mountvers=3,mountproto=tcp,mountport=,noresvport,nolock[,nordirplus],{hard|soft},retrans=,timeo=,rsize=,wsize=` [C]. Unmount on macOS is `unmount(path, MNT_FORCE)` [C]. Documented limitations, quoted from Meta: no xattrs in NFSv3 (Finder copies and Xcode break); no client pid in requests (crawler detection now uses `lsof`/`fs_usage`); "Tricky invalidation... NFS has no direct way to do this. EdenFS uses a no-op chmod" on parent directories so the client's `SETATTR` reply carries changed attributes and the client drops cached entries, yet "there are reports of stale content being seen after checkout"; `readdir` returns names only, so clients issue n `LOOKUP`+`GETATTR` calls (Buck2 hit this; a Thrift `readdir` endpoint was added); "No forget calls", so loaded inodes grow without bound and a garbage collector was added; "disconnected mounts hang. If EdenFS crashes, IO in FUSE repos will return ENOTCONN errors. However, IO in NFS mounts will hang"; the macOS client "does not support close-to-open guarantees"; deleting an open file yields `.nfs-xxxx` files; the client sometimes sends NFSv4 requests to the v3 server; case-insensitivity keeps the first casing seen [C: macOS.md]. Performance: "generally performance on macOS is pretty close between the two [FUSE and NFS]... When we rolled out NFS perf impacts across the board were pretty much a wash" [C: macOS.md]. Meta considered and rejected NFSv4 (RFC 7530 is 323 pages against v3's 126; "serialized open calls"; lease loss after sleep forces remount), Ganesha, SMB ("Windows first"), and FileProvider (built on fsevents, which "frequently drops events" at their repo sizes and has no ordering guarantees) [C: macOS.md].

**NFS loopback: what bb_clientd does.** bb_clientd exposes one mount (`~/bb_clientd`) with `cas`, `outputs` and `scratch` subtrees; FUSE on Linux, NFSv4 on macOS [C: buildbarn/bb-clientd README]. Its shipped config sets `useNFSv4: os == 'Darwin'`, `enforcedLeaseTime: '120s'`, `announcedLeaseTime: '60s'`, and on Darwin a `socketPath` under the cache directory (a Unix-domain socket inode on disk), on Linux `mountOptions: ['vers=4.1']`; the FUSE branch uses `directoryEntryValidity` and `inodeAttributeValidity` of 300 s and `allowOther` [C: bb-clientd configs/bb_clientd.jsonnet]. The ADR explains the choice: NFSv4.0 (RFC 7530) because "clients such as the one shipped with macOS don't support" 4.1/4.2; NFSv3 rejected because "due to its lack of compound operations, it is far more 'chatty' than NFSv4. This would lead to unnecessary context switching"; FUSE "will remain supported and recommended for use on Linux" [C: buildbarn bb-adrs 0009]. Note the disagreement with Meta on Unix sockets (bb_clientd's macOS NFSv4 mount is configured with a socket path; Meta says "NFS over UDS is broken" for its v3 server) - to be tested, not assumed.

**Does mounting NFS on macOS require root?** XNU's `mount_common` reads: "If the user is not root, ensure that they own the directory onto which we are attempting to mount" (otherwise `EPERM`), and "For non-root users, silently enforce MNT_NOSUID and MNT_NODEV, and MNT_NOEXEC if mount point is already MNT_NOEXEC" [C: apple-oss-distributions/xnu, bsd/vfs/vfs_syscalls.c]. A non-root process can therefore mount an NFS export onto a directory it owns; rclone relies on this: `rclone nfsmount` on macOS "spins up an NFS server using serve nfs command and mounts it", needing neither macFUSE nor root, with `mount -t nfs -o port=$PORT,mountport=$PORT,tcp $HOSTNAME:/ <mountpoint>` [C: rclone serve nfs and nfsmount docs]. EdenFS still uses a root helper; one concrete reason visible in its mount flags is `NFS_MFLAG_RESVPORT`, which asks the client to bind a reserved (<1024) source port, itself a root-only operation, and which our own server would not require [C: PrivHelperServer.cpp; inference]. Relevant `mount_nfs` options: `vers`, `tcp`, `port`, `mountport`, `soft`/`hard`, `intr`, `timeo`, `retrans`, `deadtimeout`, `rsize`/`wsize`, `readahead`, `actimeo`/`acregmin`/`acregmax`/`acdirmin`/`acdirmax`, `nolocks`/`locallocks`, `noac`, `nocallback`, `nfc`, `resvport`; hard mounts hang until the server answers, soft mounts fail after `retrans` timeouts, `intr` makes delayed calls fail with `EINTR` [B: macOS mount_nfs(8)]. Performance numbers for loopback NFS on macOS: none published by Meta or Buildbarn; must be measured (Section 5).

**SMB loopback.** The macOS `mount_smbfs` URL syntax `//[domain;][user[:password]@]server[/share]` has no port field in the man page, and Apple says "You should always use the system mount command and never call mount_smbfs directly" [B: macOS mount_smbfs(8)]; Meta rejected SMB as "Windows first" [C: macOS.md]. Not a candidate.

**The mount-point directory requirement.** `mount(2)` needs an existing directory vnode, and for non-root callers XNU requires the caller to own it [C: xnu vfs_syscalls.c]; the FSKit sample does `mkdir` before mounting [C: FSKitSample README]. `/Volumes` is root-owned and populated by Disk Arbitration for auto-mounted disks, so a user-owned mount point must live elsewhere (for example under `$HOME`); `nobrowse` "indicates that the mount point should not be visible via the GUI" [B: macOS mount(8)]. Creating that one directory is a metadata write on APFS; it happens once per host and is the single documented exception on macOS. A RAM-only alternative exists: `hdiutil attach -nomount ram://<sectors>` creates a RAM-backed block device (example in the man page: ``mydev=`hdiutil attach -nomount ram://$NUMSECTORS` ``); if it is mounted, Disk Arbitration places it under `/Volumes` (the OS creates that directory, not slates), after which every directory created inside it is RAM-only [B: macOS hdiutil(1)]; the man page is silent on privileges, so whether an unprivileged user can do this must be verified at runtime.

### 2.3 Windows

**WinFsp architecture.** WinFsp comprises "a kernel mode FSD (File System Driver) and a user mode DLL"; the FSD registers `\Device\WinFsp.Disk` and `\Device\WinFsp.Net`; opening one creates a volume (an unnamed Fsvol device that handles file-system IRPs plus, for disk volumes, a named Fsvrt `\Device\Volume{GUID}` acting as the disk, or for network volumes an Fsvol registered with the MUP plus a symbolic link); user-mode threads block in `FSP_FSCTL_TRANSACT` (DeviceIoControl) to fetch IRPs through a pending queue, a process table and a retried queue; and "the Fsvol and Fsvrt devices will get deleted even if the user-mode file system suddenly crashes" because handles close with the process [C: WinFsp Design document]. Per-request transact buffers are at most `FSP_FSCTL_TRANSACT_REQ_SIZEMAX = 16*1024-64` bytes; pending IRPs time out after `IrpTimeout` (1-10 min, default 5 min) and are capped by `IrpCapacity` (100-1000, default 1000) [C: winfsp inc/winfsp/fsctl.h]. License: "licensed under the terms of the GPLv3" with "a special exception to GPLv3" granting FLOSS software permission to link with `winfsp-a64.dll`, `winfsp-x64.dll`, `winfsp-x86.dll` or `winfsp-msil.dll` and to redistribute the unmodified installer, provided the software is under an OSD/FSD-compliant license, shows the WinFsp copyright notice, and "Is not linked or distributed with proprietary (non-FLOSS) software"; commercial licensing is offered separately [C: winfsp License.txt]. Platforms: Windows 7 through 11, x86, x64 and ARM64 (the `winfsp-a64.dll` named in the license) [C: WinFsp README; C: License.txt]. Notify support exists in the Rust bindings (`winfsp/src/notify/`) [C: winfsp-rs tree].

**Drive letter versus directory mount, and what touches disk.** For a drive letter WinFsp calls `DefineDosDeviceW(DDD_RAW_TARGET_PATH, "X:", "\Device\Volume{GUID}")` (or asks the launcher to do it for a global letter) and broadcasts `WM_DEVICECHANGE`; removal uses `DDD_REMOVE_DEFINITION | DDD_EXACT_MATCH_ON_REMOVE` [C: winfsp src/dll/mount.c]. Microsoft: "MS-DOS device names are stored as junctions in the object namespace"; a caller that is not LocalSystem creates the name "in its own Local MS-DOS device namespace" (per logon session), LocalSystem in the Global namespace; a boot-persistent assignment is instead the job of `SetVolumeMountPoint`; boot-time letters are protected from redefinition unless the user is an administrator [B: Microsoft Learn, DefineDosDeviceW]. The object namespace is kernel memory, so a drive letter costs no disk write. A directory mount is different: WinFsp "creates the directory upon mounting and deletes it when unmounting", using a mount-point reparse point, and opens it with `FILE_FLAG_DELETE_ON_CLOSE` so a crash removes it; "NTFS disallows the creation of (mountpoint) reparse points on non-empty directories", so the target must not pre-exist as a non-empty directory [C: WinFsp FAQ]; the implementation goes through the Mount Manager (`FspMountmgrNotifyCreateDirectory`) or a private directory-reparse path [C: mount.c]. A directory mount is therefore an NTFS write (directory plus reparse data). Network-style mounts (`\\server\share` under `\Device\WinFsp.Net`) are visible in Explorer as network drives but "Network file systems cannot use directory mount points due to Windows limitations" [C: WinFsp API reference, FspFileSystemSetMountPoint]. The launcher service exists because the Service Control Manager "only allows a single instance of a particular service"; it runs file systems as services independent of user sessions so they can serve "all processes in the system" with global drive letters; its default SDDL restricts control to LocalSystem and Administrators [C: WinFsp Service Architecture]. Nothing in the WinFsp documentation says a non-administrator cannot create a per-session file system after the driver is installed; the installer itself needs administrator rights (driver installation) [C: WinFsp docs; inference].

**Cache timeouts and invalidation.** `FSP_FSCTL_VOLUME_PARAMS` carries `FileInfoTimeout` (FileInfo/Security/VolumeInfo, ms; -1 means infinite) and per-class overrides `VolumeInfoTimeout`, `DirInfoTimeout`, `SecurityTimeout`, `StreamInfoTimeout`, `EaTimeout` enabled by `...TimeoutValid` flags, plus behaviour flags `FlushAndPurgeOnCleanup`, `PostCleanupWhenModifiedOnly`, `AllowOpenInKernelMode`, `UmFileContextIsUserContext2` [C: fsctl.h; C: WinFsp API reference]. Change notification is bracketed: `FspFileSystemNotifyBegin` (returns `STATUS_CANT_WAIT` while a rename is in progress), zero or more `FspFileSystemNotify(FSP_FSCTL_NOTIFY_INFO*, Size)` with normalized names, then `FspFileSystemNotifyEnd` [C: inc/winfsp/winfsp.h]. The tutorial's passthrough example uses `FileInfoTimeout = 1000` (1 s) [C: WinFsp Tutorial].

**Measured performance.** WinFsp's own test (Dell XPS 13 9300, Core i7-1065G7, 32 GB LPDDR4x, 2 TB NVMe, Windows 11 21H2 build 22000.258, WinFsp 2022+ARM64 Beta3 v1.11B3) reports, normalized to NTFS = 1: MEMFS is fastest in file_create, file_open, file_overwrite, file_list and file_delete; NTFS is fastest in iter.file_open and file_list_single because "NTFS does a better job than WinFsp at caching directory data"; MEMFS and NTPTFS "outperform NTFS in cached and non-cached I/O tests and have equal performance to NTFS in memory mapped I/O tests"; the raw numbers exist only as chart images and a notebook [C/D: WinFsp Performance Testing]. The README's claim of being "1.5 to 9x times faster than Dokany" is a vendor statement without published conditions [D: WinFsp README]. No absolute per-operation latencies are published for WinFsp; they must be measured (Section 5).

**Dokany.** "A fork of Dokan 0.6.0"; kernel driver `dokan2.sys` plus `dokan2.dll`; LGPL for the library, driver, network provider, FUSE wrapper and installer, MIT for `dokanctl` and samples; Windows 7 SP1-11, Server 2008 R2-2022; x86, x64, ARM and ARM64 with signed drivers; v2.0.3.1000 vs v1.5.1.1000 improved 13-173% across operations [C: dokan-dev/dokany README]. Dokany's network-provider DLL "interferes with the WinFsp handling of network drives" when both are installed [C: WinFsp FAQ].

**ProjFS, and why it violates hermeticity.** ProjFS lets a user-mode "provider" project a backing store into the file system; Windows 10 1809+; it is "designed for use with high-speed backing data stores" and Microsoft points slow stores at the Cloud Files API [B: Microsoft Learn, ProjFS overview]. A provider "must use this API to designate the virtualization root": `PrjMarkDirectoryAsPlaceholder(rootPathName, ...)` converts an existing directory into a directory placeholder and fails with `ERROR_REPARSE_POINT_ENCOUNTERED` if the directory already has a reparse point, i.e. it stores a reparse point on the directory [B: Microsoft Learn, PrjMarkDirectoryAsPlaceholder]. Microsoft's glossary: a placeholder is "a file or directory that is not fully present on disk"; a hydrated placeholder is "a file whose content and metadata have been cached to disk"; a full file is one "created in the local file system, or a file that has been modified"; a tombstone is "a special hidden placeholder that represents an item that has been deleted" [B: ProjFS glossary]. EdenFS's engineers describe the consequences: "The state of files is fully managed by ProjectedFS and is stored directly in the working copy"; on first read `PRJ_GET_FILE_DATA_CB` is invoked and EdenFS writes the data with `PrjWriteFileData`, after which "subsequent reads bypass EdenFS entirely"; writes are reported via `PRJ_NOTIFICATION_CB` "after the write operation has taken place so importantly EdenFS cannot refuse the operation"; "PrjFS does not remember directory contents", so every listing is re-requested; invalidation uses `PrjDeleteFile` and `PrjMarkDirectoryAsPlaceholder` and "has proven the source of several bugs"; "Files that have already been read will still be readable after EdenFS is stopped!", so a filesystem check runs at every start; directory placeholders cannot be renamed; symlink bugs were only patched in 2024; and notification ordering is not guaranteed [C: sapling eden/fs/docs/Windows.md]. Meta chose ProjFS over the custom driver it began in 2018 to avoid "the extra risk of maintaining kernel code" [C: Windows.md]. For slates every hydrated read and every write would land on the NTFS volume and outlive the daemon: disqualified. The Cloud Files API (Windows 10 1709+) is the same placeholder-on-disk model for sync engines [B: Microsoft Learn, Cloud Files API portal]: disqualified for the same reason.

**Windows NFS client.** Microsoft's table: Windows client operating systems ship "Client for NFS" supporting "NFSv2 and NFSv3" only (Server for NFS adds 4.1) [B: Microsoft Learn, NFS overview]. The `mount` command "is available only if Client for NFS is installed"; options are `-o rsize=`/`wsize=` in KB with acceptable values 1-32 (default 32 KB), `timeout=` 0.8-60 s (default 0.8), `retry=` 1-10, `mtype=soft|hard` (soft by default), `anon`, `nolock`, `casesensitive`, `sec=sys|krb5|krb5i|krb5p`, mapping `\\server\share` to a drive letter [B: Microsoft Learn, mount command]. Microsoft's overview says NFS is in "all supported versions of Windows Server and Windows client operating systems", while third-party guides state Home editions lack the Windows Feature and Pro/Enterprise/Education include the client [D: netwrix, 4sysops guides]; treat the Home edition as unsupported until verified. The 32 KB transfer ceiling, v3-only protocol, and anonymous/UNIX identity mapping make it a poor fit even where present.

**SMB loopback on Windows.** The SMB client can connect to alternative TCP ports only on Windows 11 24H2 or later and Windows Server 2025, with administrator permissions, using `New-SmbMapping -LocalPath X: -RemotePath \\server\share -TcpPort <n>` or `NET USE X: \\server\share /TCPPORT:<n>`; "The SMB server in Windows and Windows Server only supports changing the SMB over QUIC listening port. You can't configure TCP or RDMA listening ports", so TCP 445 stays with the built-in server [B: Microsoft Learn, Configure alternative SMB ports]. A user-space loopback SMB server therefore needs a non-445 port, a 24H2+ client, and elevation to map: rejected.

**What drive-letter assignment touches on disk.** Nothing: `DefineDosDevice` edits object-namespace junctions in kernel memory, and Microsoft explicitly routes persistence to `SetVolumeMountPoint` [B: Microsoft Learn, DefineDosDeviceW]. NTFS directory mount points and junctions are reparse points and therefore disk writes [C: WinFsp FAQ; B: PrjMarkDirectoryAsPlaceholder reparse semantics].

### 2.4 Cross-cutting: one root mount, volumes as directories, and the chosen-path rule set

*Root mount* = the single kernel mount point per (host, user) under which every volume appears as a top-level directory. *Chosen path* = the path an agent names when it asks for a volume to appear somewhere specific.

**Precedents for one mount, many workspaces.** bb_clientd exposes one mount (`~/bb_clientd`) whose `cas`, `outputs` and `scratch` subtrees hold arbitrarily many lazily materialized trees [C: buildbarn/bb-clientd README]. Google's CitC presents every developer workspace as a directory under one FUSE mount, `/google/src/cloud/<user>/<workspace>`, "with their changes overlaid on top of the full Piper repository" and an average workspace holding fewer than ten changed files [A: Potvin & Levenberg, CACM 2016]. EdenFS instead mounts once per checkout, at the cost of a privileged helper round trip and a kernel mount per checkout [C: sapling eden/fs/docs/Process_State.md]. SOCK's measurements show mount-namespace and mount churn is a millisecond-class, mount-table-size-dependent operation [A: Oakes et al., ATC'18 §2.1-2.2]. The single-root model therefore places provisioning entirely inside the daemon: creating a volume is one directory entry in the root's namespace plus one catalog record, which is why the sub-50 µs target is reachable (see `low-latency-ipc-and-runtime.md` §4).

**Per-OS rule set for "attach at a chosen path" with zero disk writes.**

| OS | Default appearance | Chosen path that exists (a directory) | Chosen path that does not exist | Never |
|---|---|---|---|---|
| Linux | `<root>/<volume>` under the daemon's FUSE mount (root under `$XDG_RUNTIME_DIR`, a per-user tmpfs, or a user-owned directory created once) | The launcher (`slates exec`) creates a private mount namespace (`unshare(CLONE_NEWUSER|CLONE_NEWNS)` or `CLONE_NEWNS` when privileged), marks `/` `MS_REC|MS_PRIVATE`, and bind-mounts `<root>/<volume>` onto the path; only that process tree sees it; no inode is written [B: mount_namespaces(7); B: user_namespaces(7)] | Refuse with a typed error naming the missing directory, unless the missing component lies under a tmpfs the daemon owns, in which case it is created there (RAM only) | Create directories on a disk-backed parent; create symlinks |
| macOS | `<root>/<volume>` under the daemon's NFS loopback mount at a user-owned mount point (one `mkdir` at install time is the documented exception; or a RAM disk mounted by Disk Arbitration when `hdiutil attach -nomount ram://` is permitted for the user) [C: xnu vfs_syscalls.c; B: hdiutil(1)] | No mount namespaces exist; a second NFS mount of the same export at the chosen directory (user-owned, exists) is a kernel mount-table entry only; it is the only zero-write way to honour a chosen path, and it costs a mount syscall (ms-class, measured at runtime) | Refuse with a typed error | Rewrite argv/env (sylk's compensation machinery); create symlinks |
| Windows | `<letter>:\<volume>` under the daemon's WinFsp drive letter (object-namespace junction, kernel memory only) [B: DefineDosDeviceW] | A second drive letter or a subst-style `DefineDosDevice` name for the volume (kernel memory); directory mount points are NTFS reparse points and are refused [C: WinFsp FAQ] | Refuse with a typed error | Directory mounts; junctions; ProjFS |

Rationale: the launcher form on Linux is exactly what sylk's Tool VFS design reached ("`unshare(CLONE_NEWNS)` first, `mkdir -p` second — the directory only exists in the namespace, never on host disk") [C: sylk docs/TOOL_VFS.md:995-1011, via survey-sylk-docs-corpus.md]; macOS and Windows have no per-process mount namespaces, so the honest offer is "a second mount or drive letter that every process sees", and the SDK reports which form it got. Symlinks are rejected everywhere because they are disk inodes and because tools resolve them to the real mount path, defeating "invisible" [B: symlink(7)].

### 2.5 Cache coherence between the daemon and the kernel, per OS

- Linux FUSE: entry/attr timeouts are per-reply; infinite timeouts plus explicit `FUSE_NOTIFY_INVAL_INODE`, `INVAL_ENTRY`, `DELETE`, `EXPIRE_ONLY`, and (protocol 7.44+) `INC_EPOCH` give exact invalidation; writeback cache batches writes in the kernel and is the right mode for a sole-writer volume; readdirplus pre-fills attributes [C: libfuse fuse_lowlevel.h; C: linux include/uapi/linux/fuse.h; A: Vangoor et al. FAST'17]. EdenFS runs "infinite cache expiry and explicitly invalidates" [C: EdenFS Caching.md].
- macOS NFSv3: no server-to-client invalidation exists; attribute caching is governed by `actimeo`/`acregmin`/`acregmax`/`acdirmin`/`acdirmax` and weak cache consistency post-op attributes; EdenFS forces directory revalidation with a no-op `chmod` and still reports stale content after checkout; the macOS client lacks close-to-open guarantees [B: mount_nfs(8); C: EdenFS macOS.md]. slates must therefore keep attribute-cache timeouts short on writable volumes (derived from the measured RTT of a loopback GETATTR, not a constant), make mutations bump the file's change attribute (`mtime`/`ctime`/`fileid` stability) so revalidation sees them, and use the EdenFS chmod trick on parent directories after snapshot-level swaps.
- Windows WinFsp: per-class timeouts (`FileInfoTimeout`, `DirInfoTimeout`, …; `-1` = infinite) and `FspFileSystemNotifyBegin/Notify/End` change notifications [C: winfsp fsctl.h; C: winfsp.h]. Infinite timeouts plus notify is the FUSE posture.
- Multi-agent, multi-mount coherence: the daemon is the single authority for a volume; every mutation applied by the owning shard emits invalidations to every bridge that has the volume attached (FUSE notify, WinFsp notify, NFS attribute-change) before acknowledging the mutation to the caller, so a second process on the same host never observes a stale entry after the mutating call returns. Across hosts, coherence follows the lease model in `edenfs-scale-distribution.md` §2.4 (single writer, snapshot readers).
- mmap: shared writable mappings are coherent only when the kernel page cache is the single copy; with FUSE that means writeback-cache mode and no `direct_io`; with NFS the client page cache is authoritative per host; therefore shared-writable mmap across two hosts is not offered (typed refusal), and within one host it is offered on Linux and Windows and marked "best effort" on macOS NFS.

Every option adopting an existing crate would import tokio or `Arc` into the hottest path of the system; the protocols are small and stable; the bridges are the only components that talk to the kernel, so owning them is where control of latency and memory lives.

### 2.7 Failure behaviour and daemon restart

- FUSE: when the daemon dies, in-flight and later operations return `ENOTCONN`; the mount stays in the table until unmounted (lazily with `MNT_DETACH`); a new daemon can take over if the `/dev/fuse` fd is handed to it (EdenFS takeover passes the fd and the inode map over a Unix socket; libfuse accepts `/dev/fd/N`; XFUSE's monitor service does the same) [C: EdenFS Takeover.md; C: libfuse ChangeLog 3.3.0; A: Huai et al. ATC'21]. slates keeps the fd in the anchor process (see `database-design.md` §2.4) so a crashed daemon is restarted and re-attached without the kernel noticing more than a pause.
- NFS: a hard mount hangs until the server returns; a soft mount fails with `EIO`/`ETIMEDOUT` after `retrans` timeouts; EdenFS notes "IO in NFS mounts will hang" on crash [B: mount_nfs(8); C: EdenFS macOS.md]. Because the export's file handles are derived from stable inode ids, a restarted daemon on the same port answers the retried RPCs and the client recovers without remount; the anchor process holds the listening socket.
- WinFsp: "the Fsvol and Fsvrt devices will get deleted even if the user-mode file system suddenly crashes" [C: WinFsp Design]; there is no documented handoff, so on Windows a daemon crash unmounts the volumes; the anchor process re-creates them from the shared-memory state and processes with open handles see errors on their next call (a documented Degraded cell).

## 4. Recommendation for slates

1. **Bridge per OS**: Linux, our own /dev/fuse driver with the io_uring command path when the kernel is 6.14+ and `/dev/fuse` read/write otherwise, one queue per shard via `FUSE_DEV_IOC_CLONE`; macOS, our own NFSv3 loopback server (EdenFS's production choice) on a TCP loopback port, with FSKit re-evaluated yearly and macFUSE never required; Windows, our own thin binding over the WinFsp DLL. Runner-ups: `fuser`/`fuse-backend-rs` (Arc and thread pools on the hot path), NFSv4.0 on macOS (bb_clientd's choice: fewer round trips, but 2.5x the spec, serialized OPENs, lease-loss remounts per Meta), macFUSE (Recovery-mode reboot, closed kext, dead in CI), ProjFS and Cloud Files (disk hydration by design), Dokany (network-provider conflicts, no advantage).
2. **Mount model**: one root mount per (host, user), established once at daemon start and preserved across daemon restarts by the anchor process; volumes are directories under it; provisioning never calls mount(2). Runner-up: one mount per volume (EdenFS) — ms-class, mount-table-size-dependent, privileged on macOS.
3. **Chosen-path rules**: the table in §2.4; the SDK always returns the canonical path plus the form actually granted (root-relative, namespace-bound, second mount, or drive letter) so the agent never guesses.
4. **Coherence**: infinite kernel caches plus explicit invalidation on Linux and Windows; measured-short attribute timeouts plus EdenFS's directory-revalidation trick on macOS; the owning shard emits invalidations before acknowledging a mutation.
5. **Failure**: `ENOTCONN`/`EIO`-class errors are documented Degraded cells; the anchor process holds the FUSE fd, the NFS listening socket, and the WinFsp re-creation state so a daemon crash is a pause on Linux/macOS and a documented reconnect on Windows.

## 5. Risks, unknowns, and must-measure-at-runtime

- Mount(2)/fusermount3/unshare+bind latency and its dependence on mount-table size: no published number; measure per kernel with the method in §2.1 at boot and expose it as the cost of the launcher form.
- macOS loopback NFS per-operation latency (GETATTR, LOOKUP, READ 64 KiB) and the attribute-cache timeout that keeps two local processes coherent: unpublished; measure at boot and derive `actimeo` from it.
- Whether an unprivileged user may create a RAM disk with `hdiutil attach -nomount ram://` on current macOS: verify on first run; fall back to the one-time user-owned directory.
- WinFsp absolute per-operation latency on the target hardware: unpublished; measure.
- Ubuntu's AppArmor restriction on unprivileged user namespaces (23.10+): detect at launcher start; report the exact sysctl or profile needed; never silently fall back to a disk write.
- FSKit's capabilities beyond `FSUnaryFileSystem` and its performance: re-evaluate each macOS release.

## 7. FSKit examined in depth (2026-09-04)

Sources fetched this pass: Apple's documentation data for the FSKit framework, `FSVolume.Operations`, `FSVolume.Handler`, `FSVolume.ReadWriteOperations`, `FSVolume.ReadWriteHandler`, `FSGenericURLResource`, `FSPathURLResource`, `FSItem.Attributes`, `FSUnaryFileSystem`, `UnaryFileSystemExtension`, the `com.apple.developer.fskit.fsmodule` and `com.apple.security.application-groups` entitlements; the KhaosT FSKit sample; macFUSE's releases page and site.

**What FSKit is.** "Implement a file system that runs in user space"; the module is "an app extension that runs in user space, and is compatible with Mac App Store distribution"; FSKit "connects your module to the system's existing frameworks and tools, like Disk Arbitration, NetFS, and the mount(8) command"; introduced in macOS 15.4; "The current version of FSKit supports only `FSUnaryFileSystem`" (one resource, one volume) [B: Apple FSKit framework docs]. The extension is a Swift `@main` struct conforming to `UnaryFileSystemExtension` that returns a subclass of `FSUnaryFileSystem` implementing `FSUnaryFileSystemOperations` [B: Apple UnaryFileSystemExtension docs].

**Resources (what the volume is "backed" by).** `FSBlockDeviceResource` (macOS 15.4): a disk partition; the sample creates one with `hdiutil attach -imagekey diskimage-class=CRawDiskImage -nomount dummy` and mounts with `mount -F -t MyFS disk18 /tmp/TestVol` [C: KhaosT/FSKitSample]. `FSPathURLResource` (macOS 26.0): "a path in the system file space", may be security-scoped [B: Apple docs]. `FSGenericURLResource` (macOS 26.0): "a completely abstract resource. The only reference to its contents is a single URL, the contents of which are arbitrary ... some sort of network address for a remote file system. FSKit leaves interpretation of the URL and its contents entirely up to your implementation"; schemes are declared in `Info.plist` under `FSSupportedSchemes` [B: Apple docs]. macFUSE's release notes match: FSKit backend since 5.1.0 (2024-10-30) for "local" volumes on 15.4+, and "non-local" volumes (distributed file systems) on macOS 26 [C: macFUSE releases]. Consequence: a RAM-only volume with a URL identity (`slates://volume/<id>`) needs macOS 26; on 15.4 through 15.x the only route is a block-device resource, which can be a RAM disk (`hdiutil attach -nomount ram://<sectors>`) whose contents the module ignores.

**Operation set.** `FSVolume.Operations` (15.4, deprecated in 27) and its replacement `FSVolume.Handler` (27, beta) cover activate/deactivate, mount/unmount, lookup, create (file/dir), remove, rename with `overItem`, hard link, symlink create/read, get/set attributes, `enumerateDirectory` with cookie, verifier and an attribute packer (readdirplus-shaped), `reclaimItem` (a forget), `synchronize`, capabilities and statistics; optional protocols add open/close, read/write, xattrs, access checks, pathconf, preallocate, item deactivation, and kernel-offloaded I/O (block devices) [B: Apple docs]. The Handler variants "add the ability to reply with `FSItem.Attributes` and free space from the relevant methods", i.e. fewer round trips [B: Apple FSVolume.Handler docs]. Attributes carry nanosecond `timespec` times, `fileID`/`parentID`, mode, uid/gid, link count, sizes, flags, and per-attribute validity; "FSKit internally maintains a unique sequence number for each set of attributes to determine the most up-to-date set" [B: Apple FSItem.Attributes docs]. Read delivers into an `FSMutableFileDataBuffer`; write receives `Data` (a copy); no I/O size limits or cache semantics are documented [B: Apple ReadWrite docs]. A `FSDataCacheError` type exists in the framework listing, which implies a data cache inside FSKit, but its behaviour is undocumented.

**Packaging, signing, sandbox.** The entitlement `com.apple.developer.fskit.fsmodule` (15.4) marks "an extension provides an FSKit filesystem"; the documentation states no approval requirement, and macFUSE ships an FSKit module under Developer ID outside the App Store, so the entitlement is available to ordinary developer accounts [B: Apple entitlement docs; C: macFUSE]. The user enables the module once under System Settings > General > Login Items & Extensions > File System Extensions [C: FSKitSample]; no reboot, no Recovery mode, no security downgrade ("no more rebooting into recovery mode", macFUSE site) [C: macfuse.github.io]. App extensions are sandboxed; apps and extensions in one app group "can communicate ... using IPC mechanisms including Mach IPC, XPC, POSIX semaphores and shared memory, and UNIX domain sockets", and on macOS a `<team identifier>.<group name>` identifier needs no registration [B: Apple application-groups entitlement docs]. So the shim can share slates' ring region with the daemon if both are signed by the same team and use group-prefixed names; the daemon must ship inside an app bundle that contains the `.appex`.

**Language.** The entry point must be Swift; the operations can be forwarded to Rust either by linking the Rust core as a static library into the extension or by a thin shim that hands each operation to the daemon over the ring. The shim is small (the operation set above, each method a marshal-and-forward).

**Performance.** No absolute numbers exist anywhere. macFUSE 5.3.0 reports that its FSKit backend became "up to 15 times faster" at reading files than its previous FSKit releases on the loopback reference file system, which says the first FSKit backends were slow and that the path can be tuned, not what it costs now [C: macFUSE releases]. The kernel-to-extension path crosses a system broker (XPC), so the per-operation floor is at least a FUSE-class pair of wakes; the daemon hop adds one ring round trip unless the core runs inside the extension.

**Coherence.** There is no documented invalidation API from the extension to the kernel; attributes are versioned by sequence number and `reclaimItem` is the forget; whether name and data caches can be invalidated on demand (needed when a write arrives through the SDK ring rather than through the mount) is unknown and must be established by experiment.

**API stability.** The Operations protocols were introduced in 15.4 and deprecated in 27 in favour of Handler protocols; two generations in three releases. Building on FSKit means tracking Apple's yearly changes behind a thin shim.

**Verdict.** FSKit is the right macOS bridge to bet on for macOS 26 and later: no kext, no reboot, a one-time toggle, a complete operation set (xattrs and hard links included, which NFSv3 lacks), per-volume mounts identified by URL (which makes chosen-path attaches a separate mount with a URL rather than a second mount of one export), and, decisively, our own code on the whole path, so coherence problems are ours to fix. NFSv3 stays as the fallback for macOS 14.4 through 15.x and as the differential oracle. What NFSv3 cannot give us is exactly what the user's question targets: the client's cache behaviour is Apple's kernel code and cannot be fixed server-side; with FSKit it can. Go/no-go for FSKit-first is a Phase 4 spike with measured numbers (§8).

## 8. FSKit spike plan (go/no-go, Phase 4)

1. Build the minimal Swift extension against `FSVolume.Handler` (27) and `FSVolume.Operations` (15.4-26) behind one shim interface; link the Rust core statically for the spike (the in-process form) and also run the forwarding form (ring to the daemon).
2. Measure, on macOS 26 with a `slates://` URL resource and on 15.x with a RAM-disk block resource: lookup, getattr, readdir of 10k entries, read and write at 4 KiB and 64 KiB, create, rename, mmap read; compare with the NFSv3 loopback and with an APFS RAM disk.
3. Establish cache behaviour by experiment: after a write through the SDK ring, does a second process see the new size and contents without remount; does `reclaimItem` fire under memory pressure; does a snapshot swap (new root) invalidate names.
4. Run fsx and the NFS-trimmed pjdfstest over the FSKit mount; record the expected-failure list.
5. Confirm a non-root user can run `mount -F` for the module (the sample does not say), and whether `hdiutil attach -nomount ram://` is permitted unprivileged.
6. Measure the shim overhead (in-process form versus forwarding form) and decide where the core runs on macOS.
Go criteria: per-operation latency within a fixed factor of the NFSv3 path or better; coherence controllable for the SDK write case; fsx clean; non-root mount works. No-go: NFSv3 remains primary and FSKit is re-evaluated next macOS release.
