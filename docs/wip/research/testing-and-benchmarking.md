# Testing and benchmarking a hermetic in-memory VFS + distributed metadata service "by use and functionality"

Status: WIP research note. Written incrementally; sections are appended as each sub-question is finished.
Date: 2026-09-03. Author: research agent for the slates project.

Evidence tiers used throughout: [A] peer-reviewed paper / PhD thesis; [B] textbook, standard, official docs; [C] widely deployed tool and its docs/source; [D] blog or talk (gap-filler, flagged).

## 1. Questions answered

1. **POSIX/filesystem conformance by behaviour.** Which existing suites (pjdfstest, xfstests, fsx, fsstress, LTP) apply to a FUSE/NFS/WinFsp mount, what they cover, what breaks on FUSE, and how the research oracles (SibylFS, Metis, Hydra, Janus, CrashMonkey/ACE) and differential testing against tmpfs/APFS/NTFS can be turned into behavioural tests for slates.
2. **Real-workload functional tests.** How to run git, cargo, npm, python/pytest, ripgrep, rsync, editors, file watchers, and mmap-heavy tools (sqlite, rustc) inside a volume and assert on outcomes and on parity with the host filesystem; the precedents (EdenFS integration tests, Buildbarn, gVisor, virtio-fs, Firecracker) and how to keep such tests hermetic and deterministic.
3. **Property-based and model-based testing, and fuzzing.** How the QuickCheck lineage and proptest's state-machine testing let us generate operation sequences against an executable model of the VFS with shrinking; where to fuzz (wire protocol, FUSE/NFS/WinFsp request parsers, archive format).
4. **Concurrency correctness.** What loom, shuttle (PCT), ThreadSanitizer, Miri, Kani and Verus each buy for the lock-free cores, and how to check the metadata service's histories for linearizability (Herlihy–Wing; Horn–Kroening P-compositionality; Lowe; Porcupine; Elle).
5. **Distributed fault tolerance and chaos.** Deterministic simulation (FoundationDB, madsim, turmoil, Antithesis), Jepsen's nemeses, a TLA+ model of replication, and the empirical failure studies that tell us which faults to inject first; the slates-specific injection list.
6. **Benchmarking methodology and CI regression gates.** The measurement-bias and rigour literature (Mytkowicz, benchmarking crimes, Kalibera–Jones, Georges, Traeger), coordinated omission and HdrHistogram, criterion/divan/iai-callgrind, change-point detection; the exact metrics slates must track, including the sub-50 µs provisioning histogram, soak and scale tests, and the platform matrix.
7. **A test taxonomy for slates.** For each category: purpose, tooling, plain-English pass criteria, cadence (CI / nightly / release), and 3–5 example cases including error and edge cases.

Short version of the recommendation (Section 4 has the full argument): a five-layer pyramid — (i) an executable model plus proptest state-machine tests and differential checks against the host filesystem, (ii) the borrowed conformance suites run over every mount type (pjdfstest, xfstests generic, fsx, fsstress, LTP), (iii) hermetic real-tool workloads (git/cargo/npm/pytest/rg/rsync/sqlite/editors/watchers) asserting on outcomes and parity, (iv) concurrency and distributed checks (loom/shuttle for cores; a deterministic simulator with a linearizability checker and a nemesis library for the metadata service; TLA+ for the replication protocol), and (v) a benchmark suite with instruction-count gates in CI and change-point-detected wall-clock/latency gates nightly. Everything is a behaviour check ("did the tool succeed and is the result byte-identical to the host?") rather than a static assertion on internals.

## 2. Findings by sub-question

Conventions: each claim ends with `[tier: source]`; sources are expanded in Section 6. Terms of art are defined in one line where first used.

### 2.1 POSIX/filesystem conformance by behaviour

*Conformance suite* = a fixed set of scripted system-call sequences with expected return values and errno. *Oracle* = the program that decides whether an observed behaviour is acceptable. *Differential testing* = run identical inputs through two or more implementations and treat disagreement as a failure to adjudicate [A: McKeeman 1998].

**pjdfstest.** The original suite (Pawel Jakub Dawidek, FreeBSD) contains 238 test scripts (`tests/<syscall>/NN.t`) across 17 directories: chflags, chmod, chown, ftruncate, granular, link, mkdir, mkfifo, mknod, open, posix_fallocate, rename, rmdir, symlink, truncate, unlink, utimensat (counted from the repository tree) [C: pjd/pjdfstest]. Each script drives a small `fstest` binary and asserts the exact return value/errno, so the suite is behavioural by construction: it exercises the call and checks what the kernel reports back. The Rust rewrite (GSoC 2022) is configured with a TOML file: opt-in feature toggles per filesystem (e.g. `posix_fallocate`, `chflags`), a `naptime` that must exceed the filesystem's timestamp granularity, an `allow_remount` flag for read-only tests, dummy users (`nobody`, `tests`) for privilege tests, and rootless execution with reduced coverage (user-switching tests are skipped) [C: saidsay-so/pjdfstest README]. It is invoked as `pjdfstest -c pjdfstest.toml -p /mnt <pattern>` [C: saidsay-so/pjdfstest README]. Practical notes for FUSE/NFS mounts: (a) BSD `chflags` is not part of the Linux FUSE protocol, so the chflags tests are disabled by configuration; (b) an NFS-trimmed fork (`pjdfstest_nfs`) exists precisely because several tests are meaningless over NFS (e.g. those depending on local uid switching and immediate timestamp updates) [C: Barre/pjdfstest_nfs]; (c) production FUSE filesystems keep explicit known-failure lists — SeaweedFS was reported to fail many chmod/unlink/utimensat cases [C: seaweedfs issue #1588], and JuiceFS documents that the FUSE kernel module only supports traditional record locks, not OFD locks [C: JuiceFS POSIX compatibility docs]. The lesson for slates is to keep a per-mount-type expected-failure list that is itself reviewed, not to skip the suite.

**xfstests.** The `generic/` directory holds 797 tests at the time of counting [C: kdave/xfstests mirror]. xfstests has first-class support for FUSE-type filesystems: `FSTYP=fuse` with a `FUSE_SUBTYP` (the mount is performed as `-t $FSTYP$FUSE_SUBTYP`), the mkfs/scratch steps are no-ops for fuse ("do nothing for fuse"), and fuse is grouped with nfs/cifs/ceph/overlay/9p/virtiofs as a filesystem class that has no block device (the 9p/fuse/virtiofs/afs mount "device" is a plain tag string) [C: xfstests common/rc, common/config]. This means the generic suite can be pointed at a slates mount with `TEST_DEV=<tag> TEST_DIR=<mount>` and a scratch mount of a second volume; tests that need features slates does not offer (quotas, fallocate modes, dm-flakey power-fail, mkfs) report `notrun` rather than fail. The tests that matter most for a copy-on-write in-memory FS are the ones that wrap fsx and fsstress (generic/075, generic/112, generic/127, generic/263 run fsx variants; generic/013 and generic/070 run fsstress), the rename/link/unlink races, the mmap/truncate interaction tests and the `holes`/sparse-file tests [C: xfstests tests/generic; group tags `rw`, `mmap`, `stress`]. Hydra's authors note that only about 5% of xfstests tests attempt to stress crash scenarios, so xfstests is a functional suite, not a crash-consistency suite [A: Kim et al. SOSP'19].

**fsx.** Written at Apple starting in 1998 by Avadis Tevanian Jr., rewritten and extended 1998–2003 by Conrad Minshall, with the explicit feature "checks for mmap last-page zero fill" [C: apple/fstools fsx.c header]. It applies a pseudorandom sequence of read, write, mapped read, mapped write, truncate (shrink and grow), and — in the Linux/xfstests version — fallocate/punch-hole/zero-range/collapse/insert and clone/dedupe/copy_file_range operations to one file, keeps an in-memory "good buffer", verifies every read against it, and is fully reproducible from a seed with a log of the last operations on failure [C: apple/fstools fsx.c; C: lib.rs/crates/fsx (Rust rewrite by Alan Somers, configured via `fsx.toml`, "100% reproducible according to a seed value")]. WinFsp's maintainers describe the Windows port of fsx as "very good at finding problems with read/write and memory-mapped I/O" [C: WinFsp testing doc]. Why it finds copy-on-write bugs: it interleaves page-granular mmap writes with byte-granular truncate/extend and overwrites straddling page and extent boundaries, which is exactly where a CoW implementation must split, copy, zero-fill or unshare pages; the canonical symptom is stale bytes beyond EOF after truncate+write, which EdenFS had to regression-test explicitly for clang's reliance on zero-filled tail pages [C: facebook/sapling eden/integration/mmap_test.py].

**fsstress.** A multi-process random-operation generator from LTP/xfstests that, per process, repeatedly picks a weighted operation (creat, mkdir, rmdir, unlink, rename, link, symlink, read/write/pread/pwrite, mmap read/write, truncate, fsync/fdatasync, chown, getdents, stat, readlink, mknod, fallocate/punch/zero/collapse/insert, xattr set/get/remove, sync, splice, copy_file_range, clone/dedupe range and more) over a directory tree it grows and shrinks, with a seed for reproduction [C: xfstests ltp/fsstress.c]. It has no oracle of its own: it finds crashes, hangs and assertion failures, and it is combined with a post-run consistency check (fsck, or for slates, the model/differential comparison in 2.3). LTP additionally ships growfiles (gf01–gf30), rwtest, iogen/doio, fs_inod, openfile, ftest and lftest in `runtest/fs` (86 entries) and 1,897 entries in `runtest/syscalls`; the runner is `runltp -f <file>` and tests can be pointed at a directory with `-d`/`TMPDIR` [C: linux-test-project/ltp runtest/fs, runtest/syscalls, README].

**SibylFS (Ridge et al., SOSP'15).** A mathematically rigorous model of file-system behaviour (written in Lem/OCaml) that "specifies the range of allowed behaviours of a file system for any sequence of the system calls within our scope" and "can be used as a test oracle to decide whether an observed trace is allowed by the model"; it has POSIX, Linux, OS X and FreeBSD modes [A: Ridge et al. SOSP'15]. The suite has 21,070 traces; executing it on Linux tmpfs takes 152 s and checking all traces takes about 79 s (266 traces/s, 4 processes, Core i7-3520M) — the checker is faster than the run, so it is CI-suitable [A: Ridge et al. SOSP'15]. The tests cover 98% of the model's lines [A: Ridge et al. SOSP'15]. The model covers path resolution (including trailing-slash and symlink corner cases), permissions (chmod/chown/umask, real and effective uids), timestamps, open file descriptors and directory handles, and concurrent calls via state sets (nondeterminism) [A: Ridge et al. SOSP'15]. Around 40 configurations were tested, including exactly the mount types slates cares about: fusexmp/tmpfs (the FUSE pass-through example over tmpfs), NFSv3/tmpfs, NFSv4/tmpfs, SSHFS, overlay and bind mounts on Linux; HFS+, NFSv3/HFS+, fusexmp/HFS+ and OpenZFS on OS X [A: Ridge et al. SOSP'15]. Findings: on Linux ext2/3/4 all but 9 of the 21,070 traces were accepted (the 9 are chroot artefacts); OS X 10.9.5 had an integer-underflow bug in `pwrite` with a negative offset; Btrfs, SSHFS/tmpfs and Linux HFS+ do not maintain directory link counts; FreeBSD violates the POSIX invariant that a failing call leaves state unchanged (open with O_CREAT|O_DIRECTORY|O_EXCL on a symlink to a directory returns ENOTDIR *and* replaces the symlink with a file); posixovl/VFAT leaked storage; OpenZFS on OS X entered an infinite busy loop [A: Ridge et al. SOSP'15]. Tooling: `fs_test` runs trace scripts on a mounted filesystem and `fs_check` validates the recorded traces against the model for a chosen platform; failing steps are annotated with diagnostics [C: sibylfs.github.io]. How slates should use the approach: run the SibylFS scripts against a slates mount on each OS and check against that OS's model; where the toolchain is too old to build (the project has been dormant since ~2016 — a risk, see Section 5), reuse the *method*: record `(call, args) -> (return, errno, observable state)` traces and check them against an executable model that is allowed to be nondeterministic where POSIX is.

**Metis (Liu et al., FAST'24).** A differential model checker: it "runs two file systems" on the same nondeterministically generated syscall sequence and after each operation compares (a) return values and error codes and (b) an *abstract state* — an MD5 hash over file data, directory structure and essential metadata, deliberately excluding timestamps to avoid false positives [A: Liu et al. FAST'24; C: sbu-fsl/Metis README]. Input coverage is engineered: numeric arguments (write sizes) are partitioned into power-of-two ranges with weights so that 512- and 4096-byte boundaries are hit, bitmap arguments (open flags) get per-bit probabilities, and categorical arguments are enumerated [A: Liu et al. FAST'24]. State exploration uses SPIN with snapshot/restore of full filesystem state between operations, and Swarm verification distributes independent verification tasks across cores and nodes with near-linear scaling [A: Liu et al. FAST'24]. RefFS, their in-memory FUSE reference filesystem, is explored 3–28x faster than in-kernel Ext4/XFS/Btrfs because snapshot/restore is cheap in RAM [A: Liu et al. FAST'24]. Scale: one month of Ext4-vs-RefFS runs totalled 557 compute-days and over 3 billion operations; 11 bugs were found in RefFS during its development and 12 in five other filesystems (five confirmed, one fixed in Linux) [A: Liu et al. FAST'24]. Limitations for direct adoption: it needs a Linux 4.4–6.6.1 kernel, a patched ramdisk driver and a custom SPIN fork [C: sbu-fsl/Metis README]. Slates should adopt the abstract-state differential method (hash of the tree after every op, compared to tmpfs/APFS/NTFS and to our own model), and its snapshot/restore trick maps directly onto our cheap CoW clones.

**Hydra (Kim et al., SOSP'19) and Janus (Xu et al., S&P'19).** Hydra is an extensible fuzzing framework (input mutators, coverage feedback, a Linux Kernel Library executor that starts from a clean state per test, a reproducer with test-case minimisation) with four checkers: crash consistency (SymC3), POSIX conformance (using SibylFS as the oracle), logic assertions, and memory errors; it found 91 new bugs in Linux filesystems, including one in the verified FSCQ, plus four POSIX violations [A: Kim et al. SOSP'19; C: sslab-gatech/hydra README]. Janus mutates the two-dimensional input (a disk image's metadata plus an image-directed syscall sequence), found 90 bugs in upstream Linux (62 acknowledged, 43 fixed, 32 CVEs), covered 4.19x and 2.01x more code paths than Syzkaller on Btrfs and ext4 after 12 hours, and reproduced 88–100% of crashes because each run starts from a fresh library-OS instance [A: Xu et al. S&P'19]. Mapping to slates: there is no on-disk image, so the "image dimension" becomes (i) the archive/snapshot serialisation and (ii) the wire-protocol messages; the "syscall dimension" becomes FUSE/NFS/WinFsp request streams and SDK operation sequences (Section 2.3).

**CrashMonkey and ACE (Mohan et al., OSDI'18).** Bounded black-box crash testing: ACE exhaustively generates workloads within a bound (sequences of at most three operations on a fresh filesystem, each followed by fsync/fdatasync/sync as the persistence point) and CrashMonkey records block I/O, constructs the crash state at each persistence point, and checks it against an *oracle* image — files and directories persisted before the crash must survive with correct data and metadata [A: Mohan et al. OSDI'18]. Scale and results: 3.37 million workloads were tested in two days on a 65-node Chameleon cluster running 12 VMs per node; the tools reproduced 24 of 26 bugs reported in the previous five years and found 10 new bugs in mature Linux filesystems (seven present since 2014; one in the verified FSCQ); ACE generates about 150 workloads/s; the seq-1 space is 300 workloads [A: Mohan et al. OSDI'18]. Adaptation to slates: replace "power loss after fsync" by "daemon or replica killed after an acknowledged commit", and the oracle by "everything acknowledged before the kill is present and byte-identical after recovery; nothing unacknowledged is half-present". The bounded exhaustive enumeration (all 1–3 operation sequences over a two-file, two-directory namespace) is cheap and directly reusable; the observation that most historical bugs need three or fewer operations justifies starting small.

**Differential testing against the host filesystem.** McKeeman's original formulation: feed the same inputs to several implementations of the same specification and inspect disagreements; combined with random input generation it is an efficient bug-finder even without a full oracle [A: McKeeman 1998]. Metis is this method for filesystems, and SibylFS's survey shows what the reference will disagree about (timestamps, link counts, error-code choice among POSIX-allowed alternatives, symlink/trailing-slash resolution) [A: Ridge et al. SOSP'15; A: Liu et al. FAST'24]. Recommendation: for each platform, run identical operation sequences on a slates mount and on the native in-RAM reference (Linux tmpfs; macOS APFS on a RAM disk created with `diskutil`; Windows NTFS on a RAM-backed VHD), compare Metis-style abstract states after each step, and encode the tolerated differences in an explicit, reviewed equivalence policy (timestamps compared for ordering only; inode numbers ignored; errno compared against a per-platform allowed set as SibylFS does).

**What is known to differ or break over FUSE/NFS/WinFsp (to seed the expected-failure lists).** (1) FUSE's writeback cache delays size/mtime visibility and batches writes in the kernel — Vangoor et al. describe the optimised configuration as enabling writeback cache, 128 KiB writes, splice and multithreading, which changes observable timing of metadata [A: Vangoor et al. FAST'17]. (2) OFD locks are not supported through FUSE [C: JuiceFS docs]. (3) Directory link counts are optional in practice (Btrfs, SSHFS, Linux HFS+ omit them) [A: Ridge et al. SOSP'15]. (4) NFSv3 has no extended attributes and NFS has no client-pid information; EdenFS documents both as concrete limitations of its macOS NFS backend [C: facebook/sapling eden/fs/docs/macOS.md]. (5) Inotify only reports events triggered through the local filesystem API and "does not catch remote events that occur on network filesystems" [B: inotify(7)]. (6) NFS locking is flagged by SQLite as a corruption risk when lock primitives are buggy, and `close()` drops all POSIX advisory locks held by the process on that file [B: SQLite "How to Corrupt"]. Each of these becomes an explicit behavioural test (does slates behave as documented?) rather than a silent skip.


### 2.2 Real-workload functional tests

- Precedents: EdenFS keeps an integration suite that runs real tools against a mounted checkout (`eden/integration`: `mmap_test.py` for clang's zero-fill reliance, checkout/status/rename/unlink tests, Watchman tests) [C: facebook/sapling eden/integration]; Buildbarn runs Bazel builds against bb_clientd [C: buildbarn]; gVisor's test suite runs real programs (language runtimes, databases) inside the sandbox and compares against native [C: gVisor tests]; virtio-fs and Firecracker CI run xfstests and pjdfstest against the shared filesystem [C: virtio-fs, firecracker test suites].
- What to run inside a volume and what to assert: `git clone` (from a vendored bare repo), `checkout`, `status` (must be clean), `commit`, `rebase`, `gc`; `cargo build` cold then incremental (the incremental build must reuse artifacts, which only happens if mtimes and inode numbers are stable); `npm install` from a vendored offline registry (tens of thousands of small files, symlinks in `.bin`); `python -m venv` plus `pytest`; `rg` over the tree with identical output to the host; `rsync` in both directions with `--checksum` producing no diffs; editor save patterns (write temp, `fsync`, rename) and file watchers (`inotifywait`, `fswatch`, `ReadDirectoryChangesW` harness) seeing the events in order; `sqlite3` creating and querying a database with WAL mode (locking and mmap); `rustc` with `-C incremental` (mmap of large files). Pass = exit code 0, byte-identical outputs to the same run on the host filesystem, and clean `git status`. Hermeticity: pinned tool binaries and vendored inputs, no network (a fake registry served from a local socket), fixed locale and umask, and a fresh volume per run.

### 2.3 Property-based and model-based testing, and fuzzing

- QuickCheck's stateful testing (a model, a generator of commands, preconditions, postconditions, and shrinking) is the method [A: Claessen & Hughes ICFP'00; A: Hughes 2007/2016]; `proptest` with `proptest-state-machine` implements it for Rust [C: proptest docs]. The executable model for slates is a plain map from path to (kind, bytes, attributes) with explicit POSIX nondeterminism where allowed (errno choice, timestamp granularity), operations including create, write at offset, truncate/extend, sparse writes, rename (including cycles and over-existing targets), hard links, symlinks, snapshot, clone, concurrent clone-and-write (commands interleaved from two agents), ENOSPC on bounded volumes, archive-and-restore round trips; shrinking finds the minimal failing sequence.
- Fuzzing targets: the wire codec, the FUSE request parser, the NFS/RPC/XDR decoder, the WinFsp request translation, the archive reader, and the MCP JSON layer, with cargo-fuzz/libFuzzer and AFL++ [A: Manès et al. IEEE TSE 2019; C: cargo-fuzz]. Every parser of external bytes gets a hostile-input test (vorpal's convention) [C: survey-vorpal.md §8.2].

### 2.4 Concurrency correctness

- `loom` exhaustively explores interleavings of small lock-free cores under the C11 model (CDSChecker lineage) [A: Norris & Demsky OOPSLA'13; C: tokio-rs/loom]; `shuttle` uses PCT for larger task-level schedules with probabilistic guarantees [A: Burckhardt et al. ASPLOS'10; C: awslabs/shuttle]; ThreadSanitizer for data races in integration binaries [A: Serebryany & Iskhodzhanov WBIA'09]; Miri (Stacked Borrows, Tree Borrows) for undefined behaviour in `unsafe` code [A: Jung et al. POPL'20; A: Villani et al. PLDI'25]; Kani for bounded model checking and Verus for proofs of the arena, ring, and handle cores [C: Kani; A: Lattuada et al. SOSP'24]. Linearizability of the metadata service's history is checked with a P-compositional checker over recorded histories [A: Herlihy & Wing TOPLAS'90; A: Horn & Kroening CAV'15] and with Elle for transactional anomalies [A: Kingsbury & Alvaro VLDB'20].

### 2.5 Distributed fault tolerance and chaos

- Deterministic simulation (FoundationDB) is the primary tool: the whole cluster in one process on the simulation driver with seeded time, randomness, network and rings [A: Zhou et al. SIGMOD'21]; Jepsen's nemeses (partition, clock skew, pause, kill, membership change) run both in simulation and against real processes [C: Jepsen]; a TLA+ model of leases and replication is checked with TLC [A: Newcombe et al. CACM'15]. Priorities from the failure studies: error-handling paths first (most catastrophic failures need only a few nodes and are found by simple tests of error paths) [A: Yuan et al. OSDI'14]; single network partitions next [A: Alquraan et al. OSDI'18]; then gray and metastable failures under load [A: Huang et al. HotOS'17; A: Bronson et al. HotOS'21]; tail latency under hedging [A: Dean & Barroso CACM'13]; chaos engineering as a continuous practice [A: Basiri et al. IEEE Software 2016].
- slates-specific injections: daemon kill mid-operation while tools hold open files on each bridge; ENOMEM from the arena (allocation refusal injected per shard); OS memory pressure (cgroup `memory.max`, macOS memory-pressure simulation, Windows job limits); CPU starvation of a shard; clock jumps; replica loss during replication; slow replicas; partition during clone and during archive; duplicate and replayed requests (RIFL records must return the original result); malformed wire, FUSE, NFS, WinFsp and archive inputs; unmount under load; signal storms; anchor-process restart during a write burst.

### 2.6 Benchmarking methodology and CI gates

- Measurement bias and rigor: Mytkowicz et al. (environment size and link order change results by more than the effect studied), van der Kouwe et al. (benchmarking crimes: selective benchmarks, unstated conditions, no error bars), Kalibera & Jones (how many repetitions at which level), Georges et al. (statistically rigorous evaluation), Traeger et al. (nine years of storage benchmarking mistakes) [A: ASPLOS'09; A: EuroSec'19; A: ISMM'13; A: OOPSLA'07; A: ACM TOS 2008]. Filebench for workload models [C: Tarasov et al. ;login: 2016]. Coordinated omission is avoided by recording every intended request time and using HdrHistogram-style logarithmic buckets [D: Tene]. Instruction counts (`iai-callgrind`) give CI-stable microbenchmarks; wall-clock latency histograms are gated nightly with change-point detection (E-Divisive, as MongoDB does) rather than fixed thresholds [C: iai-callgrind; A: Daly et al. ICPE'20]. vorpal's discipline (release binaries, exact commands, stated hardware, load-average gating, "measured-and-rejected" write-ups) is adopted [C: survey-vorpal.md §8.1].
- What slates measures: provisioning latency histogram end-to-end from each SDK (p50/p99/p999/max; the 50 µs target is a ratchet on the first CI baseline, with the client-spinning form gated and the parked form reported); per-operation bridge latency versus the host filesystem per OS; git/cargo/npm/pytest/rg/rsync macro-benchmarks versus the host; bytes per file and per volume; snapshot and clone cost versus tree size (must be O(1) and O(paths) respectively); archive throughput and ratio; replication lag and recovery time; soak (24 h, RSS plateau with no growth); scale (millions of files, deep trees, 100k-entry directories); the full platform matrix.

## 4. Recommendation for slates

The five-layer pyramid of §1 with these gates: CI on every change = unit and model-based tests, loom on the lock-free cores, Miri on `unsafe` crates, hostile-input fuzz smoke (seconds), pjdfstest and fsx over a slates mount on the host OS of the runner, instruction-count microbenchmarks, the N=1 differential test; nightly = xfstests generic over FUSE, fsstress, the full real-workload suite on all three OSes, deterministic cluster simulation with the nemesis library for a fixed seed budget, linearizability and Elle checks, latency histograms with change-point detection, shuttle schedules; release = 24 h soak, scale runs, the full platform matrix including i686, TLA+ model check of the current protocol version, and a manual chaos day. Runner-ups: fixed numeric thresholds in CI (flaky; change-point detection instead), criterion wall-clock in CI (noise; instruction counts instead), skipping suites that "mostly don't apply" (keep them with reviewed expected-failure lists).

## 5. Risks and unknowns

- SibylFS's toolchain may not build on current OCaml; the method survives even if the tool must be re-implemented.
- Metis needs specific kernels; its differential method is reused without the tool.
- Windows and macOS runners in CI are scarcer; nightly and release matrices carry the full set.
