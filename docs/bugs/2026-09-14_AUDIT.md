## AUD-01 — NFS bypasses consumer and volume authorization

**Source-confirmed. Contract: §4.13; related GAP-A9-9 and GAP-A9-4.**

[The listener](../../crates/server/src/nfs.rs#L767) accepts TCP streams without establishing
an enrolled consumer. [Requester construction](../../crates/server/src/nfs.rs#L257)
trusts the UID carried in AUTH_SYS and assigns UID 0 when no usable credential is present.
[Every export](../../crates/server/src/nfs.rs#L162) receives the unconditional read/write
rights from `mount_rights`; it does not look up the catalog access list or a pre-existing
authorized attachment. `Export::new` creates a fresh attachment with those supplied rights.
[The shared bridge](../../crates/bridge-core/src/volume_bridge.rs#L215) checks that supplied
context, so it does not recover the missing authorization. Root enumeration also lists the
shard's volumes without filtering by consumer.

**Trigger and impact:** a local process that can connect to the listener can enumerate
volume names, obtain handles and issue reads or mutations without the capability the
normal client channel requires. Loopback reachability does not identify a consumer;
removing only AUTH_NONE would leave client-supplied AUTH_SYS identities and the ACL bypass.

**Regression required:** create a volume private to one enrolled consumer. An unbound TCP
client, another consumer, and a caller supplying that owner's UID must all be refused
before enumeration or data access. Verify the authorized mount still works.

## AUD-02 — FUSE invalidation cannot sustain the advertised cache lifetime

**Source-confirmed integration defect. Contract: §4.6 cache posture; GAP-A9-3/-4.**

[The seam](../../crates/bridge-core/src/volume_bridge.rs#L901) returns `CacheLifetime::Forever`
for owned objects, represented by [CACHE_FOREVER](../../crates/bridge-fuse/src/bridge.rs#L29).
But [serve_blocking](../../crates/bridge-fuse/src/channel.rs#L210) blocks in `read_request`
before asking for invalidations. An external mutation has no notification wake path in
this loop. If lookup, attributes and reads are answered from the kernel cache, there may
be no request to wake the loop and deliver the invalidation.

There is a second concrete loss in [serve_one](../../crates/bridge-fuse/src/channel.rs#L268):
an `invalidations` error is ignored and the request proceeds; its final unconditional
`cursor = bridge.seen(cx)` advances past the changes that were not successfully gathered.
The comment promising a retry does not match that control flow.

**Impact:** external changes can remain invisible; failed notification collection can
lose coherence permanently. Encoding notification bytes does not prove timely delivery.

**Regression required:** populate the real kernel cache, mutate through another attachment,
and read/stat through the mount without introducing an unrelated uncached request. Also
inject one notification-collection failure and require the missed change to be delivered.
The source defect is confirmed; a Linux mounted reproduction was not run here.

## AUD-03 — Empty RPC fragments evade the receive bound

**Source-confirmed. Contract: R3/R4, §4.2 and §4.9; GAP-A9-11.**

[read_record](../../crates/bridge-nfs/src/rpc.rs#L129) bounds each fragment's payload and
the sum of payload lengths. It does not bound fragment count or framing bytes. Repeating
the four-byte marker `00 00 00 00` supplies a zero-length, non-final fragment: `pos`
advances, `message.len()` remains zero, and parsing ends with `Incomplete`.
[serve_one](../../crates/server/src/nfs.rs#L819) then appends more bytes without bounding
the accumulated stream buffer or consuming those incomplete fragments.

**Impact:** a client can grow the connection buffer past the 2 MiB payload cap while every
payload check passes. Re-parsing the entire accumulated prefix also makes work grow with
the history of received markers.

**Regression required:** stream non-final empty fragments past the derived total framing
budget. Require a typed refusal, bounded memory and bounded parser work. Include many
small nonempty fragments and a valid fragmented maximum-size message.

## AUD-04 — Cross-shard mount requests can wait forever after admission loss

**Source-confirmed. Contract: §4.3 cancellation and bounded work; GAP-A9-4.**

[serve_remote](../../crates/server/src/nfs.rs#L448) checks whether the request entered
the control channel, then awaits `BridgeCall` without a deadline. Channel acceptance is
not task admission: [handle_control](../../crates/rt/src/shard.rs#L1000) can subsequently
drop the future when its arena is full, incrementing only `admission_refused`. The reply
task has the same admission hazard, and its `send_control` result is discarded.

The root-listing [gather](../../crates/server/src/nfs.rs#L688) has both failure forms:
a channel refusal drops that shard from the result through `filter_map`, producing an
apparently successful incomplete listing; a later task refusal leaves `EntriesCall`
waiting indefinitely. This is also why `run_on`'s claim that a successful send guarantees
completion is incorrect.

**Regression required:** fill the destination arena while leaving its control channel
available, then issue a mounted operation to that shard. Repeat for the return path.
Require bounded, explicit failure. A failed shard gather must not return an unqualified
complete root listing. Check that client disconnect/cancellation reclaims the pending call.

## AUD-05 — Publication exceptions still acknowledge unprotected effects

**Source-confirmed, previously recorded residual gap. Contract: §4.8/D-18; GAP-A9-6.**

[publish_shard](../../crates/server/src/verbs.rs#L5171) can skip a volume that cannot be
imaged; with no content object it returns an empty successful `Published`. The NFS
[barrier](../../crates/server/src/nfs.rs#L224) counts an omitted touched volume but sends
the original stable reply. For control verbs, [dispatch](../../crates/server/src/verbs.rs#L1637)
logs a publication error and still returns the successful operation result for completion
recording. These are acknowledged exceptions, not merely missing telemetry.

**Trigger and impact:** a stable mutation of an omitted overlay, or a successful snapshot
whose content publication failed, is followed by daemon restart. The response promised
more recovery than was published. Reopening the original base does not recover private
overlay edits. An unavailable content object must not be indistinguishable from a fully
captured shard.

**Regression required:** force skipped-volume, missing-content-object and image-capacity
failures separately; restart after each reply. A stability/success guarantee must either
survive or have been refused explicitly. Existing record:
[NFS publication bug](2026-09-13-nfs-write-acknowledged-without-publish.md).

## AUD-06 — Failed database commits leave a successful retry result in memory

**Source-confirmed failure path. Contract: §4.8 transactions, AC-2.3; GAP-A9-6.**

Inside a transaction, [Db::mutate](../../crates/db/src/replay.rs#L210) applies operations
to the partition immediately. [Db::commit](../../crates/db/src/replay.rs#L259) takes the
pending operations before the fallible log append/snapshot. A failed publication does
not undo the applied operations, including the completion record.
[run_recorded](../../crates/server/src/verbs.rs#L850) replaces the outgoing reply with a
refusal when commit fails, but the original success remains in the partition. The next
[completion lookup](../../crates/server/src/verbs.rs#L690) can return that success without
making another durable publication.

**Trigger and impact:** fill the log and make its replacement snapshot fail to publish.
The first call is refused; a retry can succeed from memory; restart then loses the
unpublished transaction. A post-append snapshot failure has different durability and must
not be confused with this pre-publication case.

**Regression required:** inject the failure before durable transaction publication,
retry the same request, then restart. Require effect and completion to survive together
or remain explicitly uncommitted. Also cover maintenance failure after a successful append.

**Closed 2026-09-18.** `Db::commit` rolls a transaction back (the partition re-derived from the
segment's durable state) when its record cannot be made durable, and defers a maintenance snapshot
that fails after a durable append; the verb is refused with the new typed `Refusal::Unpublished`
and the objects it built for the vanished record are released. Regressions exactly as required, at
the database and by use over one segment across a restart. Record:
`2026-09-18-unpublished-transaction-served-from-memory.md`.

## AUD-07 — Whole-pod restart can forget Raft state while retaining voter identity

**Correction (2026-09-14):** [fresh-member lifecycle and executed evidence](2026-09-14-raft-voter-state-loss.md).
The source references below describe the original audited defect. The 2026-09-15 follow-up
implements warm retention and explicit quorum-loss recovery; see the current record above.

**Source-confirmed integration defect. Contract: §4.8 restart-as-join and consensus safety;
GAP-A9-7.**

[Daemon initialization](../../crates/server/src/daemon.rs#L1470) derives the member ID from
the stable anchor and RAM-backed incarnation. A new pod with no retained segment starts
at incarnation zero, reusing the predecessor's seed ID. Initialization builds a fresh
`RegionalCouncil` and root group; [RegionalCouncil::new](../../crates/cluster/src/config_group.rs#L224)
uses [RaftNode::new](../../crates/cluster/src/raft.rs#L269), which resets term, vote and log.
The daemon's consensus reply path has no recovery-publication step preserving those fields.

**Counterexample to close:** B votes for A in term T. B loses its pod RAM and returns under
the same voter ID. A candidate C with an eligible log requests B's vote in T. The fresh
state can grant it, allowing A+B and B+C to support different leaders in one term. Forgetting
acknowledged entries similarly breaks the assumption that a reused voter retains its log.
The present rejoin failure may obstruct this history; it does not make identity reuse safe.

**Regression required:** preserve one-vote-per-term and committed-log safety across both
daemon-only and whole-pod restarts. A state-losing replacement must not count as its old
voter before the required identity/admission/state-transfer protocol completes. No disk
persistence exception is proposed by this audit.

## AUD-08 — Latest-state service is not fenced by a confirmed owner lease

**Source-confirmed integration gap. Contract: §4.8 “Leases and reads”; GAP-A9-7.**

[The NFS export path](../../crates/server/src/nfs.rs#L162) serves the local volume through
an attachment created for that request, without checking current distributed read
authority. [The control dispatcher](../../crates/server/src/verbs.rs#L1637) gates certain
mutations on a configured durability shortfall, not on a confirmed owner lease.
Raft CheckQuorum affects the consensus role; neither operation path tests that as a read
lease, and a consensus role alone would not establish the required lease proof.

**Trigger and impact:** isolate the old owner from the fleet while its local client remains
connected. Let the surviving quorum take over and advance the volume. The isolated owner
can continue answering its local live view without the design's `LeaseUnconfirmed`
boundary. Immutable, explicitly pinned snapshot reads are a different contract and are
not the failure claimed here.

**Regression required:** after takeover and a new committed write, a latest-state read on
the old owner's existing connection must refuse once its authority is uncertain. Include
a scheduling pause across expiry and takeover; an ordinary membership timeout is not a
substitute for this test.

## AUD-09 — The Raft core's ReadIndex uses stale contact evidence

**Source-confirmed core defect; no production caller found. Contract: §4.8 read safety.**

[read_index](../../crates/cluster/src/raft.rs#L996) returns the current commit index when
the node still calls itself leader, has a current-term commit, and its `contacts` set
contains a majority. Those contacts can predate the read. There is no read context,
post-request acknowledgement round or conservatively bounded lease attached to them.

**Counterexample:** A collects contacts and commits in T. Isolate A; B and C elect a leader
in T+1 and complete a later write before A's next local quorum check runs. A's `read_index`
can still return its old index using T's contacts. CheckQuorum eventually stepping down
does not make the intervening read linearizable.

**Regression required:** drive that ordering with delayed clocks/checks and require no
read index until fresh authority is established. The search found only the core method
and its unit tests, so this is not evidence that a live daemon invokes this faulty API.
AUD-08 is the separate deployed-service gap.

## AUD-10 — An existing record acceptor trusts the payload's owner identity

**Source-confirmed authorization defect. Contract: §4.8 authority, §4.13 authenticated transport.**

[accept_held_record](../../crates/server/src/fleet.rs#L1517) receives `peer_host` from the
authenticated session. For an existing acceptor it calls `acceptor.accept(record)` without
checking `record.owner == peer_host`. [Acceptor::accept](../../crates/db/src/register.rs#L1056)
compares the payload's owner with its installed authority; it does not know the session
identity. After success the caller tracks the object under `peer_host`.

**Trigger and impact:** rostered node B submits a record naming owner A for an object whose
acceptor already authorizes A. A correct generation, admissible epoch and unused position
pass these owner checks despite B being the sender. B can cause unauthorized acceptance
and misattribute the routing entry. This requires a rostered sender; it is not an
unauthenticated Internet attack or a claim that the system must tolerate arbitrary
Byzantine majorities.

**Regression required:** establish an object under A, then send A-labelled writes from
B's certificate. Refuse before changing records, fences or routing. Verify the owner path
and legitimate configuration-authorized takeover still work.

## AUD-11 — Submit publishes acceptance before fleet commit

**Source-confirmed contract violation. Contract: §4.16 “Commit”; GAP-A9-14.**

[submit](../../crates/server/src/verbs.rs#L3118) advances the engine, appends the local
`GreenAdvanced` operation, consumes the work journal and queues replication, then returns
`Submitted { version: Some(...) }`. [enqueue_record](../../crates/server/src/merge_service.rs#L908)
explicitly leaves f > 0 placement pending for the background record plane. The enclosing
`run_recorded` commits only the local database transaction; it does not await that fleet
placement. The durability-policy shortfall check estimates the configuration, not this
record's actual acknowledgements.

**Trigger and impact:** with f = 1, stop remote acceptance, submit, receive the accepted
version and lose the owner. The reply can name a version absent from a surviving commit
quorum. A separate `await placed` does not satisfy §4.16's meaning of an accepted commit.

**Regression required:** withhold remote inputs and then record acknowledgements separately.
Neither condition may produce committed acceptance. Once f+1 eligible holders accept, the
reply must resolve and an owner-loss retry must return the same committed result.

**Closed 2026-09-18** (the owner-loss retry lands with AUD-14's takeover recovery). At `f > 0` the
submit's acceptance waits for the record's commit at the quorum — no completion recorded, no reply
written until then; a retry meanwhile joins the wait — and resolves when it places. Regression with
both faults withheld separately, exactly as required. Record:
`2026-09-18-submit-acceptance-before-fleet-commit.md`.

## AUD-12 — A merge holder mutates its replica before refusing a stale record

**Source-confirmed. Contract: §4.8 guard-before-apply and §4.16 stale-epoch refusal.**

[accept_merge_record](../../crates/server/src/merge_service.rs#L1348) calls `recompute`
before `accept_held_record`. [recompute](../../crates/server/src/merge_service.rs#L1432)
removes the existing replica, submits the increment and installs the advanced replica.
Only afterward do the generation, owner and epoch checks run in the record acceptor.
An identity mismatch also removes/refuses a green before authenticating that record's
authority to advance it.

**Trigger and impact:** deliver a well-formed next-version increment whose bytes recompute
correctly but whose record has a stale epoch. The record is refused after the in-memory
replica advances. A subsequent legitimate version is then processed against altered state;
a rejected record has affected future decisions. An invalid stale record can also poison
the green's refusal state.

**Regression required:** deliver stale-generation, stale-epoch and wrong-owner records
carrying otherwise valid next-version inputs. Require refusal with no observable replica
change, then accept the legitimate record and read the expected version. Cover mismatch
and missing-input cases without allowing unauthorised state changes.

## AUD-13 — Merge replication waits for all candidates before advancing

**Source-confirmed liveness defect. Contract: §4.8 f+1 commit, §4.16 ordered holder apply.**

[next_merge_work](../../crates/server/src/merge_service.rs#L1047) selects only the lowest
pending version of each green. [record_merge_acks](../../crates/server/src/merge_service.rs#L1307)
removes that version only when every remote candidate has acknowledged it. Therefore
later versions are not offered even to holders already caught up. Candidate sets retained
in pending records are also used after the configuration changes.

**Trigger and impact:** candidates A/B/C at f = 1; A and B accept version N while C is
unreachable. N is placed but stays pending. Version N+1 never reaches B because N is always
selected first. Retirement of C does not itself rewrite the stored candidate lists.
This defeats progress with a surviving commit quorum.

**Regression required:** keep C silent, place successive versions through A+B, then restore
C and require ordered catch-up. Separately change the configuration while work is pending
and verify the required state transfer and candidate refresh without losing committed versions.

## AUD-14 — Green takeover does not recover a servable merge chain

**Source-confirmed existing integration gap. Contract: §4.16 owner-loss recovery; GAP-A9-14/-7.**

The daemon sends merge records into ordinary held-record acceptors. Its generic
[takeover completion](../../crates/server/src/fleet.rs#L4100) promotes a single adopted
head, records placement and removes the pending takeover. It schedules materialization
only if the value decodes as `HeadValue`. There is no corresponding branch rebuilding an
owned green, its chain/deltas/seen results and catalog from `MergeRecordValue` and its
retained inputs. The standalone `LedgerAcceptor`/ledger-promotion mechanism does not supply
that daemon integration automatically.

**Trigger and impact:** fully place a green and multiple increments, then lose its owner.
A surviving recomputed replica is not by itself a routable green that can serve version
reads, accept new work or answer old increment retries. Clearing generic takeover work
does not complete this recovery.

**Regression required:** lose the owner after several placed versions; through the public
client, read old and current versions on the successor, retry an accepted increment, then
submit another one. Preserve the full ledger prefix and original results. This gap is
also explicitly owed in [the merge-service record](../wip/merge-service.md).

## AUD-15 — The live SWIM path omits indirect probes

**Source-confirmed integration gap. Contract: §4.8 “Membership”; GAP-A9-7.**

[Detector::request_indirect](../../crates/cluster/src/detector.rs#L466) exists, but the
daemon's [probe_and_apply](../../crates/server/src/fleet.rs#L1121) sends a direct probe and
folds its acknowledgement or timeout. The daemon never calls the indirect-probe method.
The search found calls only in detector tests, not the live fleet path. Per-peer direct
detectors therefore cannot realize the specified direct → indirect proxies → suspicion
sequence merely because the pure detector supports it.

**Trigger and impact:** A cannot reach B directly, but A can reach C and C can reach B.
The implemented path can retire B without using the relay that would establish its liveness.
This is a missing SWIM stage, not a request to weaken eventual failure detection.

**Regression required:** impose that asymmetric path failure and require a real indirect
acknowledgement before the suspicion verdict; then remove both paths and require retirement.
Assert an indirect-probe counter so a direct-only implementation cannot pass accidentally.

**Closed 2026-09-18.** The stage is composed into the daemon as a hand-off between per-peer probe
tasks over bounded queues (`ShardState::indirect`), with a new `IndirectAck` wire message and the
regression exactly as required (counters `fleet.probe.indirect.acked` on the requester and `.relayed`
on the relay; the negative control with relays disabled fails with `acked=0`). Record:
`2026-09-18-swim-indirect-probes-not-wired.md`.

## AUD-16 — Conflicting submissions bypass merge-state admission

**Source-confirmed resource defect. Contract: §4.2, §4.16 retention, bounded growth; GAP-A9-1/-14.**

[Green::submit](../../crates/merge/src/engine.rs#L1357) inserts every unique increment's
result into `seen`, including conflicts. The service checks the prospective accepted
increment against [green_chain_bytes](../../crates/db/src/partition.rs#L467), but a conflict
does not append a chain record or consume that budget. There is no bound, eviction or
admission charge on the engine's rejected-result cache.

**Trigger and impact:** keep submitting distinct conflicting edits against one old base.
The head and accepted-chain charge stay fixed while `seen` retains more identities and
conflict windows. Request-completion-window reclamation does not reclaim this independent
engine cache. A related cost gap is the full-file copy retained for each accepted content
change in [commit](../../crates/merge/src/engine.rs#L1341), outside the encoded-increment
byte charge; this amplification is acknowledged in the engine's module documentation.

**Regression required:** exceed the derived rejected-result budget while keeping accepted
history fixed. Require a typed bound and balanced accounting. Separately measure resident
growth for small edits to a large file and charge retained content, not just wire increments.

**Closed 2026-09-18.** The rejected-result cache is byte-bounded by the derived green-chain cap
with oldest-first eviction and balanced accounting; retained history is accounted, folded below
the oldest reachable version and charged to the shard's budget as retention (secured before the
verdict, refused typed). Regressions at the engine (the flood and the measured amplification) and
by use. Record: `2026-09-18-merge-rejected-results-and-retained-copies-unbounded.md`.

## AUD-17 — Cross-shard call cancellation leaks its pending entry

**Source-confirmed API defect. Contract: §4.3 cancellation safety and bounded task state.**

[CrossShardCall](../../crates/server/src/xshard.rs#L108) holds the registered pending ID
but has no Drop implementation. [call_within](../../crates/server/src/xshard.rs#L192)
forgets the entry after its internal timeout resolves; dropping the enclosing future
before that cleanup runs takes neither branch. If the remote result arrives later,
`deliver` stores it in the orphan entry rather than removing the entry. If it never
arrives, the empty entry and possible waker remain.

**Impact and scope:** cancellation while the origin shard stays alive can retain entries
and boxed results for that thread's lifetime. The audit did not establish how often current
daemon callers cancel this way. A full shard shutdown is a different case because its
thread-local storage is eventually destroyed.

**Regression required:** repeatedly poll calls until registered, cancel them while retaining
the origin shard, and deliver replies both before and after cancellation. Require all
call-owned resources reclaimed and no late reply delivered to a later call.

## AUD-18 — Invalid packets keep handshake confirmation alive past its budget

**Source-confirmed boundedness defect. Contract: §4.3/§4.9, bounded work and retries.**

[confirm_as_client](../../crates/transport/src/endpoint.rs#L733) increments its retry
budget only on a silent timeout. Every datagram that fails to decrypt causes an immediate
flight retransmission and another iteration without spending that budget.
[confirm_as_server](../../crates/transport/src/endpoint.rs#L780) similarly resets its
silence count and backoff on a datagram that fails to authenticate. Neither loop has an
absolute deadline or a total invalid-packet budget. The partial-fragment limits elsewhere
in establishment do not cover these confirmation loops.

**Trigger and impact:** keep delivering invalid datagrams before each timeout. Confirmation
need never return, so the caller's retry/redial policy cannot advance and a session/task
remains occupied. The server case requires an already-authenticated handshake; this
finding does not claim unauthenticated creation of unlimited established sessions.

**Regression required:** continuously inject invalid packets during confirmation and
require a bounded typed outcome. Valid retransmitted handshake flights must still recover
loss within the derived budget; invalid traffic must not count as protocol progress.

## HYP-01 — KIND rejoin: retirement can close the replacement's new session

**Unconfirmed incident explanation, not an executed reproduction.**

The reported 2026-09-14 KIND observation was 120 seconds without rejoin: replacement
`peers_probed = 0`, survivors `peers_probed = 1`, retirement in about 7 seconds and successful
takeover. Source inspection supports this possible ordering:

1. The replacement authenticates a new incoming probe session using the same certificate.
2. A survivor's outgoing session still targets the old pod IP and reaches retirement.
3. [Retirement cleanup](../../crates/server/src/fleet.rs#L1328) calls certificate-wide
   [close_peer](../../crates/transport/src/demux.rs#L283), which now selects the replacement.
4. The replacement keeps its outgoing endpoint on every failed probe
   ([probe_once](../../crates/cluster/src/swim.rs#L505)), eventually retires the survivor,
   and both sides idle waiting for the other's authenticated return.

The final probe count is insufficient to establish that no session ever formed: the set
is populated on establishment and cleared on retirement. Likewise, an unknown source
address is already accepted by the demultiplexer; a new pod IP alone is not proof of an
address-routing defect. Existing same-address restart and fresh-port redial tests do not
force the ordering above.

**Required discrimination:** record establishment, first valid probe acknowledgement,
retirement and session closure with a generational session ID and close reason. Force
replacement authentication before, during and after old-session retirement. If the failing
run has no completed replacement handshake, investigate DNS, admission and handshake
progress instead; do not label this race the incident's root cause without that evidence.

## Coverage limits and closure order

This is a source audit, not a conformance or performance certification. It did not exercise
the mounted Linux/macOS/Windows implementations, restart processes, run the KIND lane,
revalidate the TLA models, or prove every interval-algebra case, unsafe site or memory-order
interleaving. The FSKit and virtio-fs deployment paths, Windows driver, landing engine,
compression/archive algorithms and per-syscall POSIX equivalence were not exhaustively
audited. No clean bill of health is implied for those areas.

Existing limits relevant to the requested mount/merge scope also remain explicit: Work
and Green are not yet mounted VFS volumes in the reviewed service, and the per-volume
daemon attachment barrier and kernel writeback retrieval remain recorded gaps. The pure
bridge, merge and ledger tests do not establish these missing integrations.

Suggested closure order, without implementing any fix in this change:

1. Establish the missing failure tests for authorization and publication/commit safety
   (AUD-01, AUD-05–08, AUD-10–12).
2. Exercise mount coherence, receive bounds and task-admission failure (AUD-02–04), then
   quorum-progress and complete green takeover (AUD-13–14).
3. Close the core ReadIndex, indirect-probe, admission, cancellation and handshake-budget
   cases (AUD-09, AUD-15–18), and reproduce HYP-01 separately.

Each closure needs its failing test first, the minimal authorized implementation change,
and an update to this report's status and the corresponding gap-ledger entry. There are
no closures or new runtime guarantees in this documentation change.
